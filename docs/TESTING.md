# M1 — WebDAV Range и теги одного файла

## CI
- WebDavRangeReaderTest на MockWebServer: HTTP 206/Content-Range, RAM-кэш, EOF, отказ на 200/302, неверный ETag/диапазон, запрет вложенных путей, лимит 8 МиБ/128 GET.
- Остальные M0/M1 unit tests, Android lint, strict GMS-free scan, Room schema v1.

## Huawei после зелёного CI
1. Обновить APK из успешного GitHub Actions этого PR, не удаляя приложение/локальную Room.
2. Ввести email и пароль внешнего приложения. Поле тестового пути можно оставить пустым: берётся **один** подходящий файл из Room, предпочтительно MP3. Depth: infinity выключен.
3. **Один раз** нажать «Проверить теги одного файла (лимит 8 МиБ)».
4. Прислать только обезличенные показатели title/artist/album 0/1, число Range запросов/загруженных байт. Если ошибка — текст безопасной ошибки.
5. Не показывать в общедоступном GitHub имя/путь выбранного трека, ETag, пароль, e-mail или скриншоты, содержащие их.

Кнопка не записывает теги в базу и не выполняет массовое извлечение. Системный MediaMetadataRetriever нуждается в ручном тесте на устройстве.

## Huawei Preview #40 / RFC неизвестной полной длины
Предыдущий отчёт: `BAD_CONTENT_RANGE / FORMAT / HTTP 206 / 1 GET / 0 байт`. Новый PR:
- MockWebServer доказывает приём `bytes 0-65535/*` и второго блока без полного размера, с точным количеством байтов и без redirect.
- Даже при wildcard mismatch начала/конца строго отвергается. Nonstandard `bytes=...` и неизвестный unit продолжают отклоняться с фиксированным безопасным кодом.
- Только после зелёного CI и нового Preview снова импортировать список /AllMusic и проверить один файл. Отчёт исключительно обезличенный, без URL, названий, ETag и email.

## Huawei Preview #42 — тест Cloud.Mail.ru разделителя Content-Range
Предыдущий результат: `RANGE/BAD_CONTENT_RANGE/FORMAT_EQUALS_SEPARATOR/HTTP 206/1 GET/0 bytes`. Новый PR проверяет `bytes=<start>-<end>/<total|*>` строгим числовым парсером; не принимает `bytes==...`, искажения границ и короткий body.
