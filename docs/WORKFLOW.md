# WORKFLOW — координация разработки enoTone через GitHub

**Статус:** GOV-01, предложение для пилота. Действует только после одобрения владельцем и merge PR. Ограничения AGENTS.md, ADR и AUDIT_PROTOCOL не отменяет.

## 1. Единственные источники информации

| Вопрос | Источник |
| --- | --- |
| Утверждённые требования, безопасность и архитектура | AGENTS.md, docs/CURRENT_DECISIONS.md, индекс действующих ADR |
| Порядок этапов | docs/ROADMAP.md, docs/DESIGN_PLAN.md |
| Конкретная задача, её объём и зависимости | **Тело одной GitHub Issue** (по стабильному ID) |
| **Оперативное состояние и приоритет** | **GitHub labels Issue**: `state:*` и `P0`…`P3` |
| Проверяемый результат | Связанный PR, exact HEAD, CI, независимое ревью |
| Приёмка | Только автоматические проверки: PR слит, CI точного HEAD зелёный, ревью пройдено ([ADR-0104](DECISIONS/ADR-0104-auto-acceptance.md)) |
| Быстрый вход к исходникам | docs/MODULE_MAP.md и явные ссылки в Issue |
| Срез проекта | docs/STATUS.md (не реестр статусов отдельных задач) |

История чатов, комментарии, STATUS и ROADMAP не подменяют карточку Issue. Если источники противоречат, агент сообщает о конфликте и не расширяет задание по догадке. Важно: полное задание и утверждённые дополнения содержатся **в теле Issue** или в `docs/tasks/<ID>.md` с точной ссылкой из Issue; внешний чат или файл в проекте Claude не может быть единственным источником.

## 2. Роли и полномочия

- **Владелец:** утверждает направление, порядок, приоритеты, макеты, существенные ADR, изменения scope и разрешение на merge. Приёмка не требует отдельного подтверждения: она следует из зелёного CI и ревью ([ADR-0104](DECISIONS/ADR-0104-auto-acceptance.md)).
- **Диспетчер:** read-only выбор следующей доступной Issue. **Порядок задан в [QUEUE](QUEUE.md)** — он главнее labels приоритета при расхождении. Ничего не начинает, не назначает и не меняет без команды владельца.
- **Исполнитель:** одна закреплённая Issue, каноническая ветка, Draft PR, самостоятельное исправление собственных CI-ошибок в границах scope.
- **Ревьюер:** независимый от исполнителя анализ Issue, diff, exact HEAD, тестов и регрессий; **при явном назначении PR-ревью** публикует комментарии/review в PR. Не коммитит в чужую ветку без отдельного поручения. Простой внешний аудит не разрешает писать комментарии от лица владельца (AUDIT_PROTOCOL §2). Отклонения от утверждённого не разрешает: описывает и передаёт владельцу (AUDIT_PROTOCOL §2.13).
- **Архитектор:** предлагает ADR, состав задач и технические границы; не изменяет утверждённые владельцем приоритеты.

Это роли задач, а не неизменные права конкретных ИИ. Общий GitHub-аккаунт `metravolokos` **не идентифицирует** разных агентов: поле Executor включает модель и обозначение сессии/чата.

## 3. Очередь и состояния (только labels)

Для **открытых** задач разрешена **не более чем одна** метка `state:ready`, `state:in-progress`, `state:review` или `state:blocked`. Отсутствие state-метки означает «не готова» (backlog). Завершение определяется закрытой Issue с причиной completed и ссылкой на результат, отдельная `state:done` не нужна. При закрытии метку текущего состояния удалить.

Приоритет — ровно одна метка `P0`, `P1`, `P2`, `P3`. Назначает/меняет владелец. Поля State/Priority в теле Issue **не вести**; PR, STATUS и ROADMAP не дублируют оперативный статус. Метки создаются после принятия этого процесса; немаркированные старые задачи не становятся ready автоматически.

`state:ready` допустим только если владелец разрешил этап, критерии сформулированы, вся обязательная информация доступна в GitHub, все `Depends on` завершены по обязательным условиям и нет открытого PR на ту же работу. Метки `state:device-test` нет: приёмка выполняется автоматическими проверками ([ADR-0104](DECISIONS/ADR-0104-auto-acceptance.md)), поэтому после merge Issue закрывается, а найденный на устройстве дефект заводится отдельной Issue.

## 4. Диспетчер: «какая следующая задача?»

Общие журнальные документы — `CHANGELOG.md`, `docs/STATUS.md`, `docs/REQUIREMENTS.md`, `docs/SCENARIOS.md`, `docs/KNOWN_ISSUES.md`, `docs/DECISIONS/README.md` — **не считаются пересечением по Scope**: их дописывает каждый PR. Конфликт в них сводит тот, кто сливается вторым, сохраняя записи обоих PR. Пересечением считаются только код, ресурсы, схемы, CI и тематические документы задачи.

1. Получить SHA текущего `main`, **все** открытые GitHub Issues и PR (с пагинацией) и разрешённые этапы ROADMAP/DESIGN_PLAN. Искать также совпадения стабильных ID в названиях Issue, PR и веток; не дублировать работающий ID.
2. Отобрать открытые Issue с `state:ready` и одной меткой `P0`…`P3`. Проверить завершённость каждой `Depends on`, отсутствие занятой канонической ветки и открытого PR, пересекающего задачу по `Scope`; общие журнальные документы из правила выше не считаются таким пересечением.
3. Занятость: не предлагать исполнителю вторую `state:in-progress`, кроме явно разрешённой владельцем непересекающейся по файлам и контрактам работы.
4. Сортировать строго: **P0 → P1 → P2 → P3**, при равенстве **номер Issue по возрастанию**. Порядок этапов уже обеспечен тем, какие Issue владелец разрешил как ready. Нельзя использовать произвольные предпочтения модели.
5. Вернуть одну Issue, её ID/URL, исполнителя, зависимости, scope, критерии и основание выбора. Если готовых задач нет — так и сказать; не назначать backlog самостоятельно.

Диспетчеру не требуется изучать все исходники, всю историю и все ADR.

Перед созданием Issue постановщик ищет открытые PR и ветки по ID задачи. Если работа уже идёт, Issue создаётся сразу с `state:review` и ссылкой на PR.

## 5. Исполнитель: шаг 0 «Взять задачу» (до изменения кода)

**Метки и комментарии не являются атомарной блокировкой:** особенно потому, что все агенты используют один GitHub-аккаунт. Надёжная точка взаимного исключения — **создание одной канонической ветки**, которое GitHub допускает лишь один раз для её имени.

0.1. Определить стабильный ID из карточки (`GOV-01`, `D4b`, `BUG-search`, `M6-0/8b`) и нормализовать в нижний регистр, заменяя `/` и пробелы на `-`. Имя ветки строго `<type>/<id>-<кратко>` (например `docs/gov-01-agent-workflow`, `feature/d4b-artists`, `fix/bug-search-drop-fts`). Имена и тип — часть карточки Issue. Суффикс `-v2` вместо занятой ветки запрещён.

0.2. Повторно найти открытые Issues/PR по ID, проверить `git ls-remote origin 'refs/heads/*<id>*'` либо GitHub API branches (включая пагинацию), `state:ready`, `Depends on` и отсутствие конфликта по `Scope`. Общие журнальные документы из §4 не являются пересечением; пересечением считаются код, ресурсы, схемы, CI и тематические документы задачи. При чужом активном захвате — остановиться и сообщить владельцу.

0.3. Записать намерение в комментарий Issue: `Беру в работу: <модель, идентификатор сессии>, <время UTC>, ветка <каноническое имя>`. Убедиться повторным чтением комментариев/Issue, что не существует более раннего претендента. При наличии более раннего намерения — остановиться; не перезаписывать чужого Executor.

0.4. **Атомарно создать именно каноническую ветку от свежего main только вызовом GitHub REST API создания ссылки:** `gh api -X POST repos/metravolokos/enoTone-android/git/refs -f ref=refs/heads/<имя> -f sha=<sha main>` (либо эквивалентным прямым `POST /repos/{owner}/{repo}/git/refs`, который создаёт новую ссылку и не обновляет существующую). Код ответа `422 Reference already exists` означает, что захват принадлежит другому исполнителю: **остановиться, запретить push и не создавать `-v2`**. `git push origin HEAD:refs/heads/<имя>` **нельзя использовать для захвата**: он может успешно завершиться при уже созданной ветке с тем же SHA, ошибочно подтвердив захват обоим агентам. Успешный ответ `201 Created` на `POST /git/refs` — единственный технический признак эксклюзивного создания ветки. При любом другом сбое или конфликте с порядком комментариев остановиться и сообщить владельцу. Никакие правки чужой ветки без передачи не допускаются.

0.5. Внести в Issue `Executor: <модель/сессия>`, комментарий с фактом успешного захвата и сменить `state:ready` на `state:in-progress` одним обновлением меток. Ещё раз прочитать Issue и ветку. Если захват конфликтует, остановиться и сообщить владельцу, даже если ветка уже создана; самостоятельно чужие ветки не удалять.

0.6. Перед началом правок прочитать AGENTS.md, карточку Issue, относящиеся ADR, сценарии и строку MODULE_MAP. Соседние исходники открывать лишь по необходимым зависимостям. Draft PR с указанием Issue и точных base/HEAD SHA; scope не расширять молча. CI exact HEAD и независимое ревью обязательны.

0.7. Передача ответственности: явная запись в Issue `Передано от X к Y; причина; ветка; дата` и подтверждение владельца. Только после неё другой агент может продолжать существующую ветку. Если нет коммитов и комментариев **24 часа** в `state:in-progress`, диспетчер сообщает владельцу, но **не захватывает** задачу автоматически.

## 6. Ревью, дизайн и merge

- Ревьюер в назначенном PR может и должен публиковать замечания в PR; исправляет **основной исполнитель**. Проверки — по AUDIT_PROTOCOL, включая ограничения доступа.
- **Класс риска R** (поле Issue; ревьюер может повысить с обоснованием, второе ревью назначает владелец). R, если PR **меняет**: (1) владельца, scope, время жизни или контракт общего объекта (`ViewModel`, служба, `CompositionLocal`, `MediaSession`); (2) порядок, приоритет или доступность общих обработчиков (Back, фокус, аудиофокус); (3) путь или атомарность записи (Room, файлы, Keystore), миграцию; (4) вход или выход аккаунта. Простое **использование** `ViewModel`, `StateFlow`, `launch` без изменения перечисленного класс R не создаёт; отклонение от утверждённого само по себе R не создаёт, оно получает `OWNER` в любом классе (AUDIT_PROTOCOL §2.13). Для R — два независимых ревью разными агентами; второй не читает заключение первого; заключения публикуются в PR одновременно по команде владельца; расхождения разбирает архитектор, решение остаётся за владельцем.
- Для визуальных элементов действуют ADR-0090 и `design/AGENTS.md`: источники в `design/`, перенос ресурсов только `design/tools/sync_android.py`; если ресурса нет — отдельная Issue с `design-needed` и «заблокировано дизайном: #N», никакой заглушки.
- Дополнения владельца через любой чат попадают в текст Issue (или версионируемое `docs/tasks/<ID>.md`). Значительное изменение scope — новая зависимая Issue или ADR с решением владельца.
- Слияние только **по явной команде владельца для конкретного PR** при зелёном CI **точного HEAD** и завершённом ревью. Исполняет порученный агент; **по умолчанию, если поручение адресовано «архитектору», это Claude**, но должность сама по себе не даёт права на merge. Метод — **squash**.
- **Ветки удаляются после слияния.** Squash создаёт новый коммит, поэтому история ветки теряется; держать её дальше смысла нет. Порядок: слияние → тег `archive/<имя-ветки>` на tip → удаление remote-ветки. Тег сохраняет объекты, восстановление — `git checkout -b <имя> archive/<имя>`.
- **Ветка без слитого PR не удаляется** без ревью: сначала проверяется, есть ли в ней содержимое, которого нет в `main` (`tools/branch_report.py`), и только затем владелец решает судьбу. Отклонённые исследования удаляются с записью в `CHANGELOG.md`.
- Массовая уборка веток выполняется отдельной задачей с отчётом: сколько удалено по категориям, какие теги созданы, что осталось под вопросом.
- После merge: Issue закрывается после полного исполнения критериев — приёмка следует из зелёного CI точного HEAD и ревью ([ADR-0104](DECISIONS/ADR-0104-auto-acceptance.md)). Найденный на устройстве дефект — отдельная Issue. Не выдавать CI за проверку на устройстве и наоборот.

## 7. Пилот GOV-01

1. После ревью и утверждения владельцем создать labels и заполнить **две** канонические задачи с полным текстом в GitHub: `BUG-search` (предложено P0) и `M6-0/8b` (предложено P1); приоритеты и начало только по команде владельца. Убедиться, что задачи ещё не реализованы в main.
2. Чистый чат-диспетчер предлагает первую по P0, не читая чужих бесед.
3. Два чистых чата пробуют начать одну задачу: ровно один может создать каноническую ветку, второй обнаруживает конфликт и не пишет код.
4. Затем проверить выполнение одной задачи и ревью по Issue без внешних вложений.
