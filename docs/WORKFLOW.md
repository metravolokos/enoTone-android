# WORKFLOW — единый порядок работы агентов enoTone

**Предложение GOV-01, 2026-11-14.** Этот документ вступает в силу только после ревью и одобрения владельца. До утверждения действуют существующие ограничения AGENTS.md и CURRENT_DECISIONS.md.

## 1. Источники истины

- **docs/CURRENT_DECISIONS.md** — утверждённые функциональные и продуктовые решения, ADR-индекс — действующий статус архитектурных решений.
- **docs/ROADMAP.md** и **docs/DESIGN_PLAN.md** — последовательность этапов и их зависимости. Утверждает владелец.
- **GitHub Issue** — единственный источник оперативного статуса, приоритета, ответственного, требований и блокировок *конкретной работы*. Issue ссылается на требования/ADR/сценарии; не копирует их целиком.
- **Pull Request** — фактическая реализация, точные SHA, результат CI и ревью. Слияние не равняется автоматической аппаратной приёмке.
- **docs/SCENARIOS.md** — ожидаемое поведение и доказательства (H — только от владельца на Huawei).
- **docs/STATUS.md** — краткая сводка базового состояния, не вторая очередь задач. Расхождение со слитым PR требует исправления сводки, не переоткрытия уже выполненной работы.
- **AGENTS.md** — обязательная политика безопасности и разработки; **docs/MODULE_MAP.md** — маршрутизатор к коду и предметным решениям.

Никакие сведения из истории бесед, личных заметок агентов или устаревших журналов не имеют приоритета над текущим GitHub. При противоречии источников исполнитель останавливает расширение задачи и указывает конфликт в Issue/PR; отменить продуктовый выбор может только владелец.

## 2. Роли и полномочия

| Роль | Ответственность | Ограничения |
| --- | --- | --- |
| Владелец проекта | Порядок работ, дизайн и требования, утверждение ADR, разрешение merge, Huawei PASS | Не обязан вручную сопровождать каждую попытку сборки |
| Диспетчер (любой чат/агент) | Находит следующую готовую Issue по утверждённой дорожной карте и зависимостям | Не создаёт новые задачи, не меняет приоритеты и не назначает себе разработку без разрешения |
| Исполнитель (Codex/Claude/другой агент) | Изменяет код в пределах Issue; тесты, сам исправляет CI, оформляет Draft PR | Не меняет утверждённый дизайн, API, архитектуру и область задачи молча |
| Ревьюер (независимый агент) | Сверяет Issue, diff, код, фактический CI, соседние регрессии и критерии | Не переписывает чужую ветку без отдельного поручения |

Архитектор может разрабатывать и ревьюировать ADR, рекомендовать зависимости и разделение задач. **Никакой агент, включая архитектора, не меняет утверждённые владельцем приоритеты самостоятельно.** Роль закрепляется за конкретной Issue, не за моделью навсегда.

## 3. Состояния и метки GitHub Issues

Для задач использовать ровно одну метку статуса:
- status:backlog — запланировано, но не разрешено;
- status:ready — можно брать;
- status:in-progress — один исполнитель ведёт ветку;
- status:review — реализация ждёт независимого ревью/условий merge;
- status:device-test — код может быть слит, необходимы определённые Huawei-сценарии;
- status:blocked — запрещено начинать или продолжать до снятия блокера;
- status:done — все обязательные условия завершены, Issue закрывается.

Отдельно: одна метка priority:P0 / P1 / P2 / P3, при необходимости area:ui / playback / library / artwork / network / infrastructure / docs. Метки — предложение; создать их после утверждения процесса. До создания меток диспетчер не должен считать немаркированные Issue готовыми.

**Ready** допустим только при выполнении всех условий: владелец разрешил этап; указаны цель и критерии; завершены обязательные зависимости; отсутствует конфликт с активной работой по тем же файлам/сценариям; не требуется неразрешённое архитектурное/продуктовое решение; назначен допустимый исполнитель или указан тип исполнителя.

**Done** требует ссылку на merged PR и выполненные критерии. Если Huawei-приёмка обязательна, после merge — status:device-test, не Done. Нет аппаратных тестов для конкретной задачи — зафиксировать «не требуется» и обоснование. Частичные результаты отражать явно.

## 4. Алгоритм «Какая следующая задача?»

1. Считать актуальную ветку main и последние слитые PR; посмотреть ROADMAP и DESIGN_PLAN — разрешённые этапы.
2. Получить открытые Issues и PR; исключить закрытые, backlog, blocked, in-progress, review и device-test. Проверить, что Ready не устарело из-за нового PR или изменившегося main.
3. Из оставшихся status:ready выбрать применимые к запрошенному агенту: выполнены зависимости; нет конфликтов изменяемых подсистем; всё нужное утверждено.
4. Сортировка: P0 → P1 → P2 → P3; затем порядок этапа/зависимостей в ROADMAP; затем стабильный порядок Issue number. При равенстве не выбирать по личным предпочтениям модели.
5. Вернуть одну основную задачу: Issue, причина выбора, исполнитель, зависимости, возможные конфликты и команды для начала. Разрешено предложить альтернативу, но не запускать исполнение автоматически.
6. Если ничего не готово — прямо ответить «готовых задач нет», показать причину (например, не проведена приёмка или не утверждено решение). Не выдумывать задачи ради продолжения работы.

**Не требуется** читать все исходники и все ADR для обычного выбора следующей задачи. Диспетчер не редактирует repo и не помечает Huawei PASS.

## 5. Минимальный контекст каждой задачи

GitHub Issue обязана содержать:
1. ID, этап, приоритет, цель и наблюдаемый результат.
2. Обязательные зависимости (Issue/PR), ответственного и независимого ревьюера.
3. Ссылки на релевантные R-/O- требования, ADR и сценарии SCENARIOS; только необходимые разделы.
4. Где начинать чтение кода (пакет/класс/модуль), допустимые файлы и границы изменений. Список путей — ориентир, а не запрет изучить необходимые зависимости.
5. Явное **не делать**: что нельзя менять и какие действия требуют нового согласования.
6. Проверку: JUnit/Robolectric/Roborazzi/CI/Huawei; точные критерии приёмки.
7. Решение о необходимости миграции Room, сетевого теста, сохранения данных или Android устройства; блокеры и вопросы владельцу.

Агент стартует с AGENTS.md, этой карточки, соответствующих разделов CURRENT_DECISIONS / ADR и SCENARIOS, затем с названных файлов. Не обязан целиком перечитывать историю, весь репозиторий и все старые PR. Если обнаружена скрытая связь или противоречие, читает необходимую смежную область и сообщает.

## 6. Исполнение и дополнительные указания

- Одна Issue — один ответственный исполнитель, одна рабочая ветка и основной Draft PR. Начинать от свежего main, назвать PR и branch по этапу. В PR обязательная ссылка на Issue и точные базовый/HEAD SHA.
- Исполнитель вправе без повторного согласования чинить собственную компиляцию, падение тестов, lint и detekt **только в границах Issue**. Не ослаблять тесты/гейты для зелёного CI.
- Другому агенту можно поручить анализ, отдельные тесты либо ревью. Нельзя параллельно изменять один функциональный участок без разделения ownership и согласования зависимостей.
- Дополнения владельца должны быть записаны в **основное описание Issue** как нумерованные критерии или отдельная зависимая Issue. Комментарии и история чатов — обсуждение, не заменяют спецификацию.
- Изменение архитектуры, новый модуль/dependency/настройка, отход от утверждённого макета — предложение ADR/решения владельца **до** расширения PR.
- Подготовка PR и успешный CI не дают права на merge: строго по AGENTS.md, по команде владельца.
- После merge проверить связанный Issue: status:device-test, если нужны ручные сценарии; иначе закрыть после доказанного выполнения критериев. Обновить STATUS/REQUIREMENTS/SCENARIOS только на основании реальных данных.
- При бездействии исполнителя другой чат берёт работу **только** после явной передачи ownership в Issue; параллельное «спасение» одних и тех же файлов запрещено.

## 7. Проверка и критерии вывода

Ревьюер опирается на docs/AUDIT_PROTOCOL.md: фактический base/HEAD SHA, изменённое поведение и соседние сценарии, точный CI, не проверенное отдельно; различает подтверждение по коду и проверку на Huawei. Открытый PR с зелёным CI не означает Done.

### Короткие команды для новых чатов

**Диспетчер:** «В enoTone найди по WORKFLOW.md следующую Ready Issue для Codex/Claude. Ничего не изменяй. Назови номер, зависимости и основание приоритета».

**Исполнитель:** «Выполни Issue #N в enoTone по AGENTS.md и WORKFLOW.md. Открой Draft PR. Не сливай. Не расширяй объём».

**Ревьюер:** «Проверь PR #N против связанной Issue, AUDIT_PROTOCOL и тестов на точном HEAD. Код не изменяй».

## 8. Ввод процесса GOV-01

Этот PR **не** делает существующие немаркированные Issues автоматически Ready и не начинает следующие этапы. После ревью владельца и архитектора:
1. утвердить набор меток и их создание;
2. сверить список незавершённых требований и текущих PR;
3. создать небольшую стартовую очередь Issues (без массового автоматического добавления);
4. проверить сценарий запуска через новый чат, не знающий историю проекта;
5. если пилот работает — расширять очередь по утверждённому ROADMAP.
