# WORKFLOW — координация разработки enoTone через GitHub

**Статус:** GOV-01, предложение для пилота. Действует только после одобрения владельцем и merge PR. Ограничения AGENTS.md, ADR и AUDIT_PROTOCOL не отменяет.

## 1. Единственные источники информации

| Вопрос | Источник |
| --- | --- |
| Утверждённые требования, безопасность и архитектура | AGENTS.md, docs/CURRENT_DECISIONS.md, индекс действующих ADR |
| Порядок этапов | docs/ROADMAP.md, docs/DESIGN_PLAN.md |
| Конкретная задача, её объём и зависимости | **Тело одной GitHub Issue** (по стабильному ID) |
| **Оперативное состояние и приоритет** | **GitHub labels Issue**: `state:*` и `P0`…`P3` |
| Проверяемый результат | Связанный PR, exact HEAD, CI, независимое ревью |
| Huawei PASS | Только отдельное подтверждение владельца и запись в docs/SCENARIOS.md |
| Быстрый вход к исходникам | docs/MODULE_MAP.md и явные ссылки в Issue |
| Срез проекта | docs/STATUS.md (не реестр статусов отдельных задач) |

История чатов, комментарии, STATUS и ROADMAP не подменяют карточку Issue. Если источники противоречат, агент сообщает о конфликте и не расширяет задание по догадке. Важно: полное задание и утверждённые дополнения содержатся **в теле Issue** или в `docs/tasks/<ID>.md` с точной ссылкой из Issue; внешний чат или файл в проекте Claude не может быть единственным источником.

## 2. Роли и полномочия

- **Владелец:** утверждает направление, порядок, приоритеты, макеты, существенные ADR, изменения scope, разрешение на merge и результаты Huawei.
- **Диспетчер:** read-only выбор следующей доступной Issue. Ничего не начинает, не назначает и не меняет без команды владельца.
- **Исполнитель:** одна закреплённая Issue, каноническая ветка, Draft PR, самостоятельное исправление собственных CI-ошибок в границах scope.
- **Ревьюер:** независимый от исполнителя анализ Issue, diff, exact HEAD, тестов и регрессий; **при явном назначении PR-ревью** публикует комментарии/review в PR. Не коммитит в чужую ветку без отдельного поручения. Простой внешний аудит не разрешает писать комментарии от лица владельца (AUDIT_PROTOCOL §2).
- **Архитектор:** предлагает ADR, состав задач и технические границы; не изменяет утверждённые владельцем приоритеты.

Это роли задач, а не неизменные права конкретных ИИ. Общий GitHub-аккаунт `metravolokos` **не идентифицирует** разных агентов: поле Executor включает модель и обозначение сессии/чата.

## 3. Очередь и состояния (только labels)

Для **открытых** задач разрешена **не более чем одна** метка `state:ready`, `state:in-progress`, `state:review`, `state:device-test` или `state:blocked`. Отсутствие state-метки означает «не готова» (backlog). Завершение определяется закрытой Issue с причиной completed и ссылкой на результат, отдельная `state:done` не нужна. При закрытии метку текущего состояния удалить.

Приоритет — ровно одна метка `P0`, `P1`, `P2`, `P3`. Назначает/меняет владелец. Поля State/Priority в теле Issue **не вести**; PR, STATUS и ROADMAP не дублируют оперативный статус. Метки создаются после принятия этого процесса; немаркированные старые задачи не становятся ready автоматически.

`state:ready` допустим только если владелец разрешил этап, критерии сформулированы, вся обязательная информация доступна в GitHub, все `Depends on` завершены по обязательным условиям и нет открытого PR на ту же работу. `state:device-test` — код реализован, но обязательное аппаратное принятие ещё не выполнено; такая задача не считается завершённой для зависящих от аппаратной приёмки задач, кроме отдельно утверждённого владельцем исключения.

## 4. Диспетчер: «какая следующая задача?»

1. Получить SHA текущего `main`, **все** открытые GitHub Issues и PR (с пагинацией) и разрешённые этапы ROADMAP/DESIGN_PLAN. Искать также совпадения стабильных ID в названиях Issue, PR и веток; не дублировать работающий ID.
2. Отобрать открытые Issue с `state:ready` и одной меткой `P0`…`P3`. Проверить завершённость каждой `Depends on`, отсутствие занятой канонической ветки и открытого PR, изменяющего файлы из `Scope`.
3. Занятость: не предлагать исполнителю вторую `state:in-progress`, кроме явно разрешённой владельцем непересекающейся по файлам и контрактам работы.
4. Сортировать строго: **P0 → P1 → P2 → P3**, при равенстве **номер Issue по возрастанию**. Порядок этапов уже обеспечен тем, какие Issue владелец разрешил как ready. Нельзя использовать произвольные предпочтения модели.
5. Вернуть одну Issue, её ID/URL, исполнителя, зависимости, scope, критерии и основание выбора. Если готовых задач нет — так и сказать; не назначать backlog самостоятельно.

Диспетчеру не требуется изучать все исходники, всю историю и все ADR.

## 5. Исполнитель: шаг 0 «Взять задачу» (до изменения кода)

**Метки и комментарии не являются атомарной блокировкой:** особенно потому, что все агенты используют один GitHub-аккаунт. Надёжная точка взаимного исключения — **создание одной канонической ветки**, которое GitHub допускает лишь один раз для её имени.

0.1. Определить стабильный ID из карточки (`GOV-01`, `D4b`, `BUG-search`, `M6-0/8b`) и нормализовать в нижний регистр, заменяя `/` и пробелы на `-`. Имя ветки строго `<type>/<id>-<кратко>` (например `docs/gov-01-agent-workflow`, `feature/d4b-artists`, `fix/bug-search-drop-fts`). Имена и тип — часть карточки Issue. Суффикс `-v2` вместо занятой ветки запрещён.

0.2. Повторно найти открытые Issues/PR по ID, проверить `git ls-remote origin 'refs/heads/*<id>*'` либо GitHub API branches (включая пагинацию), `state:ready`, `Depends on` и отсутствие конфликта по `Scope`. При чужом активном захвате — остановиться и сообщить владельцу.

0.3. Записать намерение в комментарий Issue: `Беру в работу: <модель, идентификатор сессии>, <время UTC>, ветка <каноническое имя>`. Убедиться повторным чтением комментариев/Issue, что не существует более раннего претендента. При наличии более раннего намерения — остановиться; не перезаписывать чужого Executor.

0.4. **Атомарно создать именно каноническую ветку от свежего main**. Если GitHub сообщает «ветка уже есть» либо creation fails — **не создавать альтернативную ветку, не писать код** и сообщить владельцу. Успешное создание — единственный технический признак захвата; при конфликте между порядком комментариев и созданием ветки остановиться и попросить владельца устранить рассогласование. Никакие правки чужой ветки без передачи не допускаются.

0.5. Внести в Issue `Executor: <модель/сессия>`, комментарий с фактом успешного захвата и сменить `state:ready` на `state:in-progress` одним обновлением меток. Ещё раз прочитать Issue и ветку. Если захват конфликтует, остановиться и сообщить владельцу, даже если ветка уже создана; самостоятельно чужие ветки не удалять.

0.6. Перед началом правок прочитать AGENTS.md, карточку Issue, относящиеся ADR, сценарии и строку MODULE_MAP. Соседние исходники открывать лишь по необходимым зависимостям. Draft PR с указанием Issue и точных base/HEAD SHA; scope не расширять молча. CI exact HEAD и независимое ревью обязательны.

0.7. Передача ответственности: явная запись в Issue `Передано от X к Y; причина; ветка; дата` и подтверждение владельца. Только после неё другой агент может продолжать существующую ветку. Если нет коммитов и комментариев **24 часа** в `state:in-progress`, диспетчер сообщает владельцу, но **не захватывает** задачу автоматически.

## 6. Ревью, дизайн и merge

- Ревьюер в назначенном PR может и должен публиковать замечания в PR; исправляет **основной исполнитель**. Проверки по AUDIT_PROTOCOL, в том числе ограничения доступа и Huawei PASS.
- Для визуальных элементов действуют ADR-0090 и `design/AGENTS.md`: источники в `design/`, перенос ресурсов только `design/tools/sync_android.py`; если ресурса нет — отдельная Issue с `design-needed` и «заблокировано дизайном: #N», никакой заглушки.
- Дополнения владельца через любой чат попадают в текст Issue (или версионируемое `docs/tasks/<ID>.md`). Значительное изменение scope — новая зависимая Issue или ADR с решением владельца.
- Слияние только **по явной команде владельца для конкретного PR** при зелёном CI **точного HEAD** и завершённом ревью. Исполняет порученный агент; **по умолчанию, если поручение адресовано «архитектору», это Claude**, но должность сама по себе не даёт права на merge. Метод — **squash**. Ветки **не удалять**.
- После merge: обязательные Huawei-сценарии → `state:device-test`; без них — закрыть Issue после полного исполнения критериев. Никогда не выдавать CI за аппаратную проверку.

## 7. Пилот GOV-01

1. После ревью и утверждения владельцем создать labels и заполнить **две** канонические задачи с полным текстом в GitHub: `BUG-search` (предложено P0) и `M6-0/8b` (предложено P1); приоритеты и начало только по команде владельца. Убедиться, что задачи ещё не реализованы в main.
2. Чистый чат-диспетчер предлагает первую по P0, не читая чужих бесед.
3. Два чистых чата пробуют начать одну задачу: ровно один может создать каноническую ветку, второй обнаруживает конфликт и не пишет код.
4. Затем проверить выполнение одной задачи и ревью по Issue без внешних вложений.
