# Cloud.Mail.ru WebDAV — проверенные факты и гипотезы

## Источник и границы проверки
2026-11-08: владелец установил debug APK M0 из успешного GitHub Actions run [#10](https://github.com/metravolokos/enoTone-android/actions/runs/42465355583), коммит `3ceed82abb446471a7d9b0f1449f90050fb5e1ee`, на Huawei и прислал **обезличенный экранный отчёт**. Применялись учётные данные для реального Cloud.Mail.ru, но они, а также конкретный путь проверенного музыкального файла, **не сохраняются в GitHub**.

Это один пользовательский тест, не гарантия постоянства поведения сервиса.

## Проверено на реальном устройстве

| Операция | Результат | Время | Что означает |
|---|---|---:|---|
| `PROPFIND /` с `Depth: 1` | HTTP 207 | 539 мс | Корень WebDAV отвечает Multi-Status |
| `PROPFIND /AllMusic` с `Depth: 1` | HTTP 207 | 1536 мс | Удалённая папка доступна |
| `PROPFIND /AllMusic`, `Depth: infinity` | Нет HTTP-кода, ошибка/тайм-аут | 15011 мс | Не удалось завершить проверку в лимите запроса; отсутствие поддержки **не доказано** |
| `GET` реального файла, `Range: bytes=0-0` | HTTP 206 | 477 мс | Сервер вернул Partial Content для байтового диапазона |
| ETag в заголовках ответа `GET Range` | присутствует | — | Может пригодиться для валидации кэша и инкрементальной синхронизации |
| `Accept-Ranges: bytes` в ответах | отсутствует | — | Отсутствие заголовка не опровергает подтверждённый HTTP 206 |

**Важно:** отсутствие заголовка `ETag` непосредственно у ответа `PROPFIND` не означает отсутствия `getetag` у элементов XML `207 Multi-Status`. Текущий M0 спайк **не разбирает XML-тело**; содержимое `DAV:getetag`, `getlastmodified`, `getcontentlength` в ответах не проверялось.

### Структура медиатеки — подтверждение владельца (2026-11-08)

Владелец сообщил отдельно от диагностического отчёта: папка `/AllMusic` содержит **только один уровень файлов, без вложенных папок**. Это известное правило организации музыкальной библиотеки, **не** вывод из HTTP-кода 207. Поэтому требование на рекурсивный обход из первоначального общего ТЗ для данной библиотеки **переопределено**: M1 перечисляет непосредственные элементы `/AllMusic` одним `PROPFIND Depth: 1` и не запрашивает вложенные пути.

### Рабочие следствия для M1
- Для индексации сделать один `PROPFIND /AllMusic` с `Depth: 1` и разобрать все непосредственные файлы. Рекурсивных запросов и параллельного обхода папок не делать. Учитывать отмену, прогресс, ошибки 429/5xx и возможную большую XML-выдачу; неожиданные директории пропускать с диагностикой.
- `Depth: infinity` не включать в штатное сканирование и не предлагать повторять на большой библиотеке; измеренный тайм-аут не доказывает запрет со стороны сервера.
- В WebDAV индексаторе разбирать `207 Multi-Status` по `href`, `propstat` и `DAV:getetag` **в XML-теле**; проверять ETag для отдельных файлов, не делать выводы только по заголовку ответа.
- HTTP 206 подтверждает запрос диапазона, но для playback ещё требуются тесты произвольного Range, `Content-Range`, смены сети, отмены загрузки, длинного воспроизведения и докачки.
- Поддержка кириллицы/Unicode/NFC/NFD, отсутствие ETag у иных файлов, ответ на `HEAD` и стабильность ETag между запросами **не подтверждены** этим отчётом.

## Безопасность
Никакие личные URL, имена треков, значения ETag, логин, пароль и HTTP Authorization в этот документ не перенесены. Экспорт M0 содержит только whitelisted метаданные. Оценка логов на других путях выполнения ещё нужна.

## Гипотезы для дальнейших проверок
Предположения: WebDAV endpoint `https://webdav.cloud.mail.ru/`, аккаунт по полному email с паролем внешнего приложения; возможны отличия в Unicode, Depth, ETag, прокси и поддержке Range. Факт этого пользовательского теста не заменяет интеграционные тесты M1.
