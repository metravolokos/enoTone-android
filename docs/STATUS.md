Владелец сообщил, что APK CI #33 нельзя установить поверх старого: **сертификаты подписей не совпадают**. Корень причины: автоматически генерируемый `~/.android/debug.keystore` на каждом временном CI runner. Старая Room с 3590 файлами **должна быть сохранена**.

Стабильного закрытого ключа подписи пока нет; он потребуется через GitHub Secrets до распространения повторных обновлений Preview. См. ADR-0019. Не предлагать удалять старую версию.

## Huawei Preview #38: точная ошибка Range (2026-11-08)
Владелец сообщил `RANGE / BAD_CONTENT_RANGE / HTTP 206 / 1 GET / 0 байт`. Ошибка до чтения тела, **не** предел 8 МиБ и **не** установленная ошибка формата аудио. В PR ADR-0021 добавлены безопасные тип и числовые границы несовпадения Content-Range; без вывода сырого HTTP-заголовка и без смягчения проверок. Требуются зелёный CI нового HEAD и повторный тест одного файла в изолированном Preview.

## Huawei Preview #40: Content-Range FORMAT (2026-11-08)
Пользователь сообщил `HTTP 206 / BAD_CONTENT_RANGE / FORMAT / 1 GET / 0 байт`, ожидалось `0-65535/10944026`. Это **не** доказательство ошибки аудиодекодера. Фактическая строка Content-Range не известна.
Новый PR ADR-0022 поддерживает RFC-совместимое `bytes x-y/*`, ранее ошибочно отвергавшееся парсером. Проверка точного диапазона, байтов и лимитов остаётся обязательной. Это проверяемая гипотеза, а не утверждение о поведении Cloud.Mail.ru.

## Huawei Preview #42 — причина синтаксической ошибки Range
Получен обезличенный отчёт `BAD_CONTENT_RANGE/FORMAT_EQUALS_SEPARATOR`, HTTP 206, один запрос, ноль байт. Классификатор подтвердил префикс `bytes=` у заголовка `Content-Range`, но не остальную строку. Создан PR совместимости (ADR-0023), принимающий ровно формы `bytes start-end/total` и `bytes=start-end/total` с прежней проверкой границ, тела и лимитов. До CI и Huawei **не считать поддержку подтверждённой**.

После принятия Stable Preview #181 с приоритетом Album Artist и merge PR #41 реализована **новая ветка**: отдельный Android dataSync foreground service для ограниченной индексации. Обоснование: прежний PR #41 проверял Wi-Fi-only и останавливал работу на Activity.onStop; оба условия переопределены владельцем. Новая служба стартует **только по нажатию**, работает при свёрнутом приложении/заблокированном экране, показывает постоянное уведомление и действия Пауза/Стоп, использует любую сеть. Credentials только в RAM процесса, никакой пароль в Intent. По убийству процесса Room сохраняет уже обработанные записи; новое выполнение — только по повторному нажатию. Существующие 62/3590 — последняя подтверждённая пользователем цифра, **не отчёт нового теста**. Бюджет 4 порции × 60 GET/4 МиБ и общий предел 240 GET/16 МиБ не изменены. **Работа в фоне, CI и Huawei ещё не подтверждены**.

## Draft ADR-0048 — параллельная индексация и повторные попытки (2026-11-09)
Владелец сообщил о первом управляемом запуске #194: 23 попытки, 22 с тегами, 1 временная ошибка, 26 GET, 1638400 байт, RETRY_BACKOFF, осталось 3506. Сообщил, что приложение сворачивалось и экран блокировался; это обнадёживающий аппаратный тест службы, но отдельное измерение роста счётчиков **именно под блокировкой** ещё нужно. Новый Draft: 4 одновременных reader по разным файлам, общий запросный бюджет через SharedRangeBudget; не более двух дополнительных попыток на файл с задержками; единичная временная ошибка не завершает весь сеанс, каскадная/429 и отказ авторизации обрабатываются отдельно. UI показывает только код последней ошибки без приватных данных. **CI и аппаратная проверка новой реализации пока не приняты.**

## Huawei #202: подтверждён повторяющийся внутренний STATE (2026-11-09)
В двух последовательных управляемых запусках пользователь показал `INDEX_BATCH / STATE`, без признаков HTTP/авторизационных ошибок. Во втором сохранён 1 успешный файл за 1 GET/65536 байт, затем `FAILED_INTERNAL`; в первом отчёт прогресса отсутствовал. Фактическое общее покрытие нужно сверять с Room: экран может не показывать все завершённые до исключения операции. **Причина пока не доказана**: диагноз `STATE` соответствует `IllegalStateException`, но не содержит stack/этапа worker. Начат Draft fix: параллелизм оставляем 4 только для независимых HTTP Range readers; все CAS-записи Room и `onProgress` последовательно обрабатывает ОДНА коллекторная корутина через bounded Channel(4). Прогресс remaining рассчитывается по числу успешно зафиксированных терминальных файлов и финально сверяется с Room, без полного SELECT 3500 строк после каждого файла. В случае повторного исключения показывается фиксированный этап `DB_SELECT`, `DB_WRITE`, `PROGRESS`, `DB_FINAL` или `POLICY` (без персональных данных). Пока не принят CI и hardware smoke. Предыдущая Stable #202 не исправляется на устройстве до выпуска новой версии.

## Draft M1 continuous scan (ADR-0049)
На базе принятого четырёхпорционного теста добавлен **отдельный добровольный** режим длинной индексации всех оставшихся MP3/FLAC: 4 параллельных HTTP worker, один последовательный Room collector, прежние 60 GET/4 МиБ на порцию, 1,5 сек пауза, до 80 порций и до 4 ч в одном запуске. До 2 пауз 30/60 сек при массовых 429/сетевых сбоях; отказ авторизации немедленно останавливает скан. Прогресс по каждому завершённому файлу сохраняется. **Ни CI нового режима, ни реальная работа на Huawei дольше 4 порций не подтверждены.**

## Draft M1 audit + refresh (ADR-0050)

## M2 navigation clarification — user decision (2026-11-10)
After full library audit, missing ALBUM (one) and missing ALBUM ARTIST (143) were confirmed as source metadata omissions, not indexing faults. The user requests **both** Artist and Album Artist pages and a **virtual Unknown Album**; previous album-artist-prioritized Artist tab is no longer correct. Draft ADR-0051 implements four visible pages with separate grouping rules and one Unknown Album for tagged missing-album tracks, plus stable page visibility IDs to support eventual hide/show preferences in Settings. Settings toggles and persistence intentionally deferred. No rerun of index, no Room schema or playback changes; not accepted until exact HEAD CI and Huawei.
