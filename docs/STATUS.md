## Huawei Preview #38: точная ошибка Range (2026-11-08)
Владелец сообщил `RANGE / BAD_CONTENT_RANGE / HTTP 206 / 1 GET / 0 байт`. Ошибка до чтения тела, **не** предел 8 МиБ и **не** установленная ошибка формата аудио. В PR ADR-0021 добавлены безопасные тип и числовые границы несовпадения Content-Range; без вывода сырого HTTP-заголовка и без смягчения проверок. Требуются зелёный CI нового HEAD и повторный тест одного файла в изолированном Preview.

## Huawei Preview #40: Content-Range FORMAT (2026-11-08)
Пользователь сообщил `HTTP 206 / BAD_CONTENT_RANGE / FORMAT / 1 GET / 0 байт`, ожидалось `0-65535/10944026`. Это **не** доказательство ошибки аудиодекодера. Фактическая строка Content-Range не известна.
Новый PR ADR-0022 поддерживает RFC-совместимое `bytes x-y/*`, ранее ошибочно отвергавшееся парсером. Проверка точного диапазона, байтов и лимитов остаётся обязательной. Это проверяемая гипотеза, а не утверждение о поведении Cloud.Mail.ru.

## Huawei Preview #42 — причина синтаксической ошибки Range
Получен обезличенный отчёт `BAD_CONTENT_RANGE/FORMAT_EQUALS_SEPARATOR`, HTTP 206, один запрос, ноль байт. Классификатор подтвердил префикс `bytes=` у заголовка `Content-Range`, но не остальную строку. Создан PR совместимости (ADR-0023), принимающий ровно формы `bytes start-end/total` и `bytes=start-end/total` с прежней проверкой границ, тела и лимитов. До CI и Huawei **не считать поддержку подтверждённой**.

Эксперимент в текущем Draft #27: начальный Media3 seed не больше пяти треков (выбранный ±2), затем после первого READY дозагрузка **остальной очереди в Media3** порциями по 32 (сначала следующие, потом предыдущие), точный порядок всех 3590 сохраняется согласно JVM StagedPlaylistPlanTest. Введены безопасные цифровые времена внутри playQueue (валидация, источники/кэш, seed, setMediaSources, prepare/play), число подготовленных источников в Media3 (не скачанных файлов). Контроль без кэша по-прежнему доступен. CI exact HEAD + Huawei smoke обязательны до merge.

## Draft M5-B — последовательная предзагрузка одного следующего (ADR-0037)
После текущего `COMPLETE` Media3 CacheWriter вызывает callback, который выбирает **один фактический следующий** элемент через nextMediaItemIndex с учётом shuffle/repeat и стадийной очереди. Один worker загружает файлы последовательно, не конкурируя за сеть перед первым звуком. Pause не отменяет ни текущий, ни следующий. Отмена при Skip/Stop, отдельный прогресс следующего, лимиты 256 МиБ/файл, LRU 512 МиБ и резерв 128 МиБ неизменны. До CI и Huawei — только Draft, не заявлять беззадержный Next.

## M6-A — измерение переходов и упрощённый экран (стандартные цвета)
Private MediaSessionService считает время от команды skip / native Media3 media item transition до READY и isPlaying; отдельно показывает был ли следующий файл полностью подготовлен в кэше. Первую загрузку очереди не считает handoff. Без media ID, путей, токенов, имён и логов. В основном UI подробная диагностика свёрнута, temporary cache включён по умолчанию; current/next имеют progressbar. После проверки Huawei #129 пользователь подтвердил работоспособность функций, но **отклонил перенесённую из другого проекта цветовую палитру**; пока дизайн Android не согласован, используем стандартные цвета Material Design без кастомной Compose-темы.
Функциональная проверка Huawei #129 пройдена; требуется полный CI на исправленном HEAD со стандартной палитрой. Подробнее ADR-0038.
