## Подтверждено кодом

B: холодный запуск начинает с `AppNavState()` (Home), а `AppNavigator.kt:43`
отвергает `push` вне `AppTab.Library`. `AppShell.kt:254–257` безусловно закрывает
плеер до вызова навигации. Это достаточный путь воспроизведения «закрылся и никуда
не перешёл», даже при найденной группе. Не доказано, что каждый отказ владельца
имел именно этот путь: данные конкретного устройства не читались.

A: у `RemoteTrackEntity.kt:14,17` уникальны ID и пара sourceKey/encodedPath.
`AlbumTagRefresher.kt:33`, `LibraryReindexCoordinator.kt:97,100` только ставят
существующие строки на повтор; `ParallelTagIndexer.kt:126`, `PilotTagIndexer.kt:241`
делают CAS UPDATE через `RemoteTrackDao.kt:128`, не INSERT. `LibraryViewModel.kt:270,287`
заменяет каталог целиком, список использует стабильный `track.id`
(`LibraryScreenContent.kt:431`); накопительного append в этом пути нет.
`AppLibraryRouteSnapshots` хранит неизменяемое состояние маршрута, активный маршрут
с совпадающим derivedRoute читает liveState. Владелец позднее проверил облачный источник
и подтвердил повторы файлов в `/AllMusic`; для этих позиций дублирование в UI не было
установлено как дефект приложения. Подмена исходных файлов `distinctBy` в UI недопустима.

Есть известное ограничение идентичности: `LibrarySnapshotPlanner.kt:30,54,61`
и `FlatWebDavListingParser.kt:198` различают текстовые варианты одного URL-пути.
Диагностика проверяет эквивалентность percent-escape и unreserved-символов,
но не объединяет разные файлы по одинаковым тегам, регистру имени или Unicode NFC/NFD.
Это проверяемая гипотеза, а не доказанная причина симптома A. Исправление идентичности
затронет ссылки очередей/плейлистов и не должно выполняться вслепую.

Все пути выше относительны: app-классы — `app/src/main/java/app/enotone/android/`,
library-классы — `data/library/src/main/java/app/enotone/library/`, DAO/entity —
`core/database/src/main/java/app/enotone/database/`, парсер —
`core/network/src/main/java/app/enotone/network/`.

## Дополнительное наблюдение владельца (2026-11-17)

На скриншоте поиска во вкладке «Песни» повторяющиеся строки из одного альбома видны вне
экрана деталей альбома. Счётчик результатов этого поиска относится только к запросу и не
является числом групп дублей или размером медиатеки.

Это сужает путь: `RoomLibraryRepository.load` читает все строки активного источника из
`remote_tracks` (`data/library/src/main/java/app/enotone/library/LibraryRepository.kt:65–69`,
`core/database/src/main/java/app/enotone/database/RemoteTrackDao.kt:9–10`);
`OfflineTrackCatalog.build` преобразует каждую строку по одной без дедупликации
(`data/library/src/main/java/app/enotone/library/OfflineTrackCatalog.kt:35–60`);
для `LibraryPage.TRACKS` `LibraryViewModel.calculateDerivedPages` берёт весь `snapshot.tracks`,
а поиск лишь фильтрует кандидатов
(`app/src/main/java/app/enotone/android/LibraryViewModel.kt:347–355`,
`data/library/src/main/java/app/enotone/library/OfflineTrackCatalog.kt:81–86`). Значит, повтор
не объясняется только отрисовкой `AlbumDetail`: дублированные представления уже приходят
в общий список каталога.

`remote_tracks` запрещает одинаковую пару `sourceKey + encodedPath`
(`core/database/src/main/java/app/enotone/database/RemoteTrackEntity.kt:12–19`). Скриншот сам
по себе не различал разные сохранённые пути, URL-варианты и две физические копии; владелец
затем подтвердил копии непосредственно в облачной папке. Числовая диагностика остаётся
полезной для URL-алиасов, но не пытается склеивать физически разные файлы по тегам.
Названия и пути из скриншотов в отчёт не переносились.

На двух скриншотах плеера один и тот же отображаемый трек находится в соседних позициях
очереди 11/19 и 12/19, с разными позициями воспроизведения. По сообщению владельца, после
подготовки первой копии и следующего трека переход на повторную запись воспроизводит тот же
трек ещё раз, но подготовка следующего отличающегося трека не начинается. Это наблюдение о
воспроизведении; экран не показывает ID/URL элементов или точное состояние фонового writer.

Кодовая проверка: `PlaybackQueue.create` требует уникальные ID элементов
(`playback/src/main/java/app/enotone/playback/PlaybackQueue.kt:46–55`), а ключ временного
аудиокэша включает ID, размер и ETag
(`playback/src/main/java/app/enotone/playback/TransientCachePolicy.kt:18–24`). В этой версии
одинаковый ID не мог бы попасть в две рабочие позиции очереди; разные ID дают разные ключи
кэша. Снимки не подтверждают, что это один физический ресурс, и не устанавливают причину
описанного поведения prefetch. Решение о следующем элементе и запуск его загрузки находятся в
`PreviewAudioPlayback.kt:110–147`. Изменений playback/cache в рамках #188 нет.

## Что установлено по источнику

Владелец проверил облачную папку `/AllMusic` и подтвердил, что повторные файлы уже есть в
источнике. Поэтому показ этих файлов в альбоме, общем списке и очереди сам по себе не
подтверждает программное размножение записей. Для этих треков приложение не должно удалять
строки или объединять их по названию/тегам; самоисцеление A не требуется для устранения
подтверждённых исходных копий. Это снимает исходное предположение о дефекте приложения A.

Отдельная тестовая сборка была side-by-side/с чистыми данными; первичная загрузка завершилась,
альбом был полным, но видимых повторов не было. Debug-вариант PR получает package suffix
`.preview.r<N>` (`app/build.gradle.kts:45–53`), и каждый per-run пакет имеет отдельную Room-базу
(`.github/workflows/ci.yml:399`). Эта проверка не читала основную базу; расхождение со снимком
облачной папки не установлено.

Кодовый путь общего каталога проверен для аудита: `RoomLibraryRepository.load` читает
`remote_tracks`; `OfflineTrackCatalog.build` преобразует каждую строку по одной; поиск лишь
фильтрует общий список. Импортный путь — `LibraryIndexingGateway.update` →
`LibrarySnapshotStore.save` → `LibrarySnapshotPlanner.plan` → Room `upsertAll`. Планировщик
схлопывает одинаковые текстовые `encodedPath`, а ID строит из исходной строки; отсутствующие
строки помечаются только при полном листинге. Эквивалентные URL-пути теоретически могут создать
разные записи, но для подтверждённых копий из облака этот механизм не нужен и не доказан.

`AlbumTagRefresher` и `LibraryReindexCoordinator` повторно читают теги по существующим ID;
`ParallelTagIndexer` делает CAS UPDATE. `LibraryReindexAuditTest` проверяет их очереди и CAS,
но не импортный листинг. Новая параллельная ошибка импорта остаётся возможной в общем случае;
сообщённые владельцем копии A для неё доказательством не являются. Числа диагностики N/M для
старой базы не получены; они не нужны, чтобы объяснить подтверждённые копии в `/AllMusic`.

## Диагностика на устройстве

«Настройки → Диагностика → Медиатека → Проверить дубли» читает все строки активного
аккаунта, исключает missingScans != 0, возвращает только два числа. Состояние
последнего показанного альбома дополнительно содержит число строк, число ID в шапке,
число повторяющихся ID. Без названий, путей, email; без HTTP, экспорта базы и записи в неё.

Исходные N/M старой Room-базы: **не получены**; после проверки облачной папки они не нужны
для классификации подтверждённых копий как содержимого источника. Диагностика считает URL-алиасы
по стабильному ключу; две реальные копии с разными путями не объединяются и не считаются одной
записью по названию.
