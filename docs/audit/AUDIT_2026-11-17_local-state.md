## 5. Находки

### F-01 — `EnoToneMigrationTest`: 7 из 7 падают на Windows (блокирующая для локальной работы)

**Симптом.** `java.lang.IllegalArgumentException` в каждом тесте класса, все 7
падают на первом же вызове `helper.createDatabase(...)`:

```text
java.lang.IllegalArgumentException: This driver is configured to open a database
named 'test-migrate-six-to-seven' but 'C:\Users\...\robolectric-...\
app.enotone.core.database.test-dataDir\databases\test-migrate-six-to-seven'
was requested.
  at androidx.sqlite.driver.SupportSQLiteDriver.open(SupportSQLiteDriver.android.kt:48)
  at androidx.room.testing.SupportSQLiteMigrationTestHelper$SupportTestConnectionManager
     .openConnection(MigrationTestHelper.android.kt:559)
```

**Причина.** `androidx.sqlite.driver.SupportSQLiteDriver` сопоставляет переданное
имя базы с уже настроенной базой драйвера и падает, когда вместо имени приходит
абсолютный путь. В окружении Robolectric на Windows
`InstrumentationRegistry.getInstrumentation().targetContext` отдаёт путь, а не имя.

**Что это не.** Не регрессия логики миграций и не следствие R-A7: каталог
`core/database` в этой ветке относительно `main` не изменён (`git diff --stat
main...HEAD -- core/database` — пусто), `androidx.room` = 2.8.5 в
`gradle/libs.versions.toml` тоже не менялся. Тот же класс в Linux CI проходит.

**Влияние.** Единственная проверка миграций Room v1→v7 не выполняется локально
полностью: ни одна миграция не проверена на этой машине. Зелёный CI не
подтверждает миграции локально, а локальный прогон их не подтверждает вообще.

**Направление решения (требует решения владельца, не сделано).**
1. Перевести класс на явный путь/имя, совместимые с драйвером на всех ОС, либо
   задать `targetContext` c `dataDir` без абсолютного пути.
2. Либо ограничить прогон миграций Linux CI и записать это в `docs/TESTING.md`
   как явное ограничение, а не выдавать за проверенное.
3. Проверка на Windows должна оставаться возможной: без неё локальная правка
   миграций не верифицируется до пуша.

### F-02 — `sync_android.py --check`: 32 ложных расхождения из-за CRLF (не дефект кода)

**Симптом.** 32 файла `не совпадает с манифестом` (иконки `ic_eno_*`, `eno_colors`,
`wordmark`, launcher).

**Причина.** `core.autocrlf=true` в глобальном конфиге Git, файла `.gitattributes`
в репозитории нет. На диск XmL-ресурсы выгружены с CRLF, в Git — LF.
[`check()`](../../design/tools/sync_android.py:123) сравнивает байты
(`dst.read_bytes() != src.read_bytes()`) и хеш из манифеста, поэтому видит различие.

**Доказательство.** Для всех 32 файлов одновременно:

| Сравнение | Совпадений |
|---|---|
| «на диске» ≠ «в Git» побайтно, но равно после нормализации CRLF | **32 из 32** |
| Содержимое отличается от Git после нормализации | **0** |
| Хеш в манифесте не совпадает | **32** |

Ручной правки ресурсов нет. В Linux CI этот шаг зелёный, потому что там рабочая
копия — LF.

**Влияние.** Блокирующий шаг CI нельзя воспроизвести локально на Windows;
сообщение об ошибке выглядит как нарушение ADR-0090, хотя нарушения нет.

**Направление решения.** Добавить `.gitattributes` с `* text=auto eol=lf` для
ресурсов дизайна (и `*.png -text`), либо сделать `sync_android.py` устойчивым к
CRLF для текстовых ресурсов, сохранив побайтную строгость для бинарных. Выбор
влияет на CI-контракт — нужно решение владельца.

### F-03 — CI предзагружает Kotlin-компилятор 2.3.10 при Kotlin 2.4.21

[`ci.yml`](../../.github/workflows/ci.yml:69) скачивает и проверяет по SHA-256
`kotlin-compiler-embeddable:2.3.10` и выставляет `ENOTONE_CI_COMPILER_MIRROR`.
В проекте `kotlin = "2.4.21"`, и в разрешённом дереве зависимостей
`org.jetbrains.kotlin:kotlin-stdlib` резолвится в **2.4.21**.

**Следствие.** В зеркале лежит другой артефакт, чем нужен сборке. Шаг не падает
(он только проверяет наличие и хеш), но и не подстраховывает: при сбое Maven
Central сборка будет искать 2.4.21 и не найдёт её в зеркале. Смысл шага в
текущем виде — нулевой.

**Направление решения.** Обновить версию и хеш в CI до 2.4.21 либо удалить шаг
как мёртвый. Требует проверки на стороне CI, локально не воспроизводится.

## 7. Рекомендуемый порядок

1. F-02 (`.gitattributes`) — дёшево, снимает ложный блокер локальных прогонов.
2. F-01 (миграции) — блокирует всякую локальную проверку Room; нужен выбор
   варианта (совместимость или явное ограничение).
3. F-04 (ROADMAP) — отдельным docs-PR, чтобы не расширять scope текущих PR.
4. F-03 (CI-зеркало) — вместе со следующей правкой `ci.yml`.
5. F-05 — приоритизация владельцем до следующего старта работ.

Каждое исправление F-01…F-03 меняет проверяемый контракт, поэтому требует
ADR или явного решения владельца, а не молчаливой правки внутри чужого PR.
