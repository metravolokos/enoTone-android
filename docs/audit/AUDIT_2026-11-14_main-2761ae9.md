### A-2026-11-14-01 — Атомарная запись файлов не перезаписывает существующий файл на Windows

| Поле | Содержание |
|---|---|
| Серьёзность | **высокая** (для процесса разработки; на устройстве не проявляется) |
| Подтверждение | **воспроизведено** |
| Условия | `main` `2761ae9`, Windows 11, JDK 17 |
| Ожидается | `./gradlew testDebugUnitTest` зелёный на любой поддерживаемой ОС разработчика |
| Наблюдается | 3 падения: `QueueStateFileStoreTest.completedPairWinsOverPreviousLayout`, `QueueStateFileStoreTest.processDeathBetweenLayoutAndPositionRestoresPreviousPair`, `QueueEditServiceTest.insertingNextChangesNativeSkipAndRecoversAfterServiceRestart` |

Причина: `java.io.File.renameTo` на Windows **не заменяет** существующий целевой файл
и возвращает `false`. Проверено изолированно:

```
rename на несуществующую цель     = true
rename на существующую цель       = false
Files.move(..., REPLACE_EXISTING, ATOMIC_MOVE) = успешно
```

Места, поражённые тем же шаблоном:

- `playback/src/main/java/app/enotone/playback/QueueStateFileStore.kt:123` —
  `if (!temporary.renameTo(target)) throw IOException(...)`. На втором сохранении
  очереди файл уже существует → исключение → откат к предыдущей паре. На Android
  (Linux) работает, на Windows — нет.
- `app/src/main/java/app/enotone/android/AccountArtworkFileCleanup.kt:76` —
  то же; бросает `IOException`, то есть **выход из аккаунта на Windows сломается**.
- `app/src/main/java/app/enotone/android/ArtworkPreviewRepository.kt:547` —
  `temp.renameTo(destination)` без проверки результата: молча возвращает `false`,
  обложка не сохраняется, ошибки нет ни в UI, ни в диагностике.

**Почему это не только «баг теста».** CI работает на `ubuntu-latest`, поэтому
дефект невидим; три критичных для сохранности данных места (очередь, обложки,
манифест выхода) нельзя проверить локально на Windows-машине владельца.
Плюс один сайт вообще не проверяет результат `renameTo`.

**Проверка исправления.** Замена на `Files.move(..., REPLACE_EXISTING, ATOMIC_MOVE)`
в трёх местах; `QueueStateFileStoreTest` и `QueueEditServiceTest` должны пройти на
Windows; для `ArtworkPreviewRepository` — тест «повторная запись того же ключа
обновляет файл».

**Статус 2026-11-15: исправлено** в PR волны 1 ([ADR-0090](../DECISIONS/ADR-0091-atomic-file-replacement.md)).
Общий `AtomicFileReplace` (`Files.move` с откатом на `REPLACE_EXISTING`), применён
в трёх местах; `ArtworkPreviewRepository.atomicWrite` возвращает фактический
результат. `QueueStateFileStoreTest` — 6/6, `QueueEditServiceTest` — 2/2 на Windows
(проверено трижды подряд). Отдельный тест на откат `ATOMIC_MOVE` не добавлен:
`AtomicMoveNotSupportedException` не воспроизводится в JVM без подмены ФС, а
строковые проверки исходников запрещены `AGENTS §4` — это осознанный пробел,
зафиксированный в ADR-0091.

### A-2026-11-14-06 — `runBlocking` внутри `suspend`-цепочки диагностики

| Поле | Содержание |
|---|---|
| Серьёзность | **средняя** |
| Подтверждение | **подтверждено кодом** |
| Ссылки | `core/network/.../WebDavDiagnostics.kt:110`, `app/.../DiagnosticsGateway.kt:24` |

`WebDavDiagnostics.inspect()` — синхронная функция, внутри которой `runBlocking`
на каждый запрос. Вызывается из `withContext(container.io)`, то есть уже внутри
корутины. Следствия:

- отмена корутины (уход с экрана «Диагностика», выход из аккаунта) **не
  прерывает** HTTP-запрос: поток остаётся занят до `requestTimeoutMillis = 15_000`;
- на плохой сети три последовательных пробы держат IO-поток до 45 с;
- `runBlocking` на `Dispatchers.IO` не создаёт дедлока (пул эластичный), но
  занимает поток, который в этот момент нужен индексации.

**Проверка исправления.** Сделать `inspect` `suspend`-функцией и убрать
`runBlocking`; тест на отмену: отменить job во время `inspect` → запрос
прерывается, а не доигрывает таймаут.

### A-2026-11-14-12 — Из состояния ERROR нет выхода

| Поле | Содержание |
|---|---|
| Серьёзность | **критично** |
| Подтверждение | **подтверждено кодом** (байткод `BasePlayer.play()` = `setPlayWhenReady(true)`, `prepare()` не вызывается) |
| Ссылки | `PreviewAudioPlayback.kt:741-747`, `PlaybackConnection.kt:223-229`, `EnoTonePlaybackService.kt:266-267` |

`fun resume()` вызывает `player.play()`; у ExoPlayer это **только**
`playWhenReady = true`. После `onPlayerError` плеер находится в `STATE_IDLE` с
несохранённой ошибкой, а `prepare()` в этом пути не вызывается — разве только
`deferredPrepare == true`, что бывает лишь при восстановлении очереди из
чекпоинта (`:714`). `playerError` нигде не сбрасывается.

Последствие: любая сетевая ошибка (обрыв, таймаут, смена Wi-Fi↔LTE, 5xx) —
и кнопка Play в мини-плеере, на «Сейчас играет», в уведомлении и на гарнитуре
**не возобновляет воспроизведение** до повторного выбора трека в списке.
Сообщение «Ошибка… код N» остаётся на экране навсегда.

**Проверка исправления.** Тест «ошибка → Play → воспроизведение продолжается»:
`prepare()` при `playerError != null` (или `STATE_IDLE`) + сброс
`playerError`; JVM-тест на фейковом плеере, Robolectric — на реальном.

### A-2026-11-14-13 — Кэш инициализируется на главном потоке

| Поле | Содержание |
|---|---|
| Серьёзность | **высокая** |
| Подтверждение | **подтверждено кодом** |
| Ссылки | `TransientMediaCache.kt:58-70`, `PreviewAudioPlayback.kt:517-519`, `:682-684` |

`TransientMediaCache.init` делает `directory.deleteRecursively()` для каталога,
который по политике может занимать **до 512 МиБ** (`TransientCachePolicy`), и

главного потока (binder). Первое воспроизведение после каждого перезапуска
сервиса = удаление тысяч файлов + открытие БД на UI-потоке: фриз, риск ANR.

**Проверка исправления.** Перенести создание кэша в `Dispatchers.IO` с
`withContext`, как это уже сделано для `readSavedQueue`.

## 1c. Что проверено по данным и сети (без отдельных замечаний)

Проверено вручную; **подтверждённых дефектов не найдено**, зафиксированы
защиты, на которые опирается остальной аудит:

- `WebDavRangeReader`: строгий `Content-Range` (включая `*` для неизвестной
  длины), отказ на 200, `Accept-Encoding: identity`, `If-Range` по строгому
  ETag, проверка `Content-Encoding`, `SHORT_BODY`/`OVERSIZED_BODY`, LRU на
  4 блока по 64 КиБ, глобальный бюджет GET/байт, `conn.disconnect()` в `finally`.
- `RemoteTrackDao`: CAS по `etag`/`size`/`modified` + `missingScans = 0`;
  `durationMs = COALESCE(durationMs, :durationMs)` (не перезаписывает известное);
  теги не стираются при ошибочном разборе (`CASE WHEN :code IN (...)`).
- `LibrarySnapshotStore`: один `withTransaction`, upsert без `DELETE`,
  `markMissing` только для полного разбора списка.
- `LibraryReindexCoordinator`: атомарная постановка в очередь, батчи ≤400
  параметров SQLite.
- Обложки: content-addressed SHA-256, ссылка пишется только после мастера,
  дедупликация по содержимому, отсутствие массовых GET.

Остаётся долгом (уже в KNOWN_ISSUES): три HTTP-стека без общего backoff,
ID трека без канонизации, жёсткий `/AllMusic`.
