# Продуктовый аудит 2026-11-22 — Kimi k3.1 pro

> **Точечный снимок, не текущее состояние.** Отчёт фиксирует находки продуктового аудита на коммите `a7545363`. Текущее состояние — [KNOWN_ISSUES](../KNOWN_ISSUES.md), работа — в GitHub Issues.
>
> **Чем отличается от кодового аудита** ([AUDIT_EXTERNAL_2026-11-22.md](AUDIT_EXTERNAL_2026-11-22.md)): тот проверял корректность реализации — гонки, атомарность, порядок очистки. Этот проверяет **что видит и чувствует пользователь**. Кодовый аудит нашёл 10 дефектов, невидимых глазами; продуктовый нашёл глюк, который владелец увидел сразу после первого полного цикла «выход → вход», и который не попал ни в один кодовый отчёт.

## Главная находка: тап по песне не запускает воспроизведение

**Симптом владельца:** после первого выхода и полноценного повторного входа песни не запускаются тапом по строке. Запускаются только после постановки в очередь.

**Корень.** Тап и очередь идут разными путями с разными проверками:

```kotlin
// LibraryScreenContent.kt:474 — тап молча игнорируется
onClick = {
    if (!selecting && state.playbackConnected) actions.onTrackClicked(track, visible)
}

// LibraryViewModel.kt:485-486 — очередь такую проверку не делает
override fun onAppendToQueue(tracks) = editQueue(tracks, playNext = false)
private fun editQueue(rows, playNext) { if (unavailable()) return; ... }
```

`playbackConnected` берётся из `PlaybackConnection.publish()`, который даёт `connected = true` только при живой привязке к службе (`PlaybackConnection.kt:289-296`). `connect()` вызывается **однократно** в `PlayerViewModel.init` (строка 131), а `disconnect()` — только в `onCleared()` (строка 422). Служба после выхода остаётся живой, `PlayerViewModel` переиспользуется, повторного `connect()` нет; если `onServiceDisconnected` сбросил `service = null` (строка 197-201), флаг остаётся `false` навсегда.

Постановка в очередь поднимает службу напрямую — после неё `connected` становится `true`, и тап начинает работать. Это объясняет наблюдаемое поведение полностью.

**Дополнительно:** молчаливый игнор — сам по себе дефект UX. Пользователь не понимает, почему приложение не отвечает.

## 4. Что реализовано корректно — не переделывать

Один лист действий «⋮» и долгое нажатие; полноэкранный лист очереди с N из M и приглушёнными прошедшими; единый лист ошибки с текстами Бандита и прокруткой при крупном шрифте; первый запуск как отдельный маршрут с плюрализованными счётчиками; пустые состояния D6-A; настройки из 4 карточек с «Диагностикой» только для чтения; возврат на ту же позицию прокрутки и стек деталей; восстановление очереди, позиции, repeat и shuffle.

## 5. Соответствие принятым ограничениям

Аудит не предлагал отменённое: TAG-EDIT (#200), удаление и перестановку очереди (Q2 #193), Wi-Fi-only, рекурсию `/AllMusic`, ландшафт, ИИ без ADR, регулятор громкости, LRU обложек, FTS.

**Требует ADR или решения владельца, а не просто PR:** П-2/И-5 (меняет утверждённый макет, design-needed), П-3 (новая пользовательская настройка — порог AUDIT_PROTOCOL §4), П-4 (этап M7), П-5 (ADR на pinning), П-9 (запланированный шаг), П-10 (владелец сам убрал сообщение), И-8 (состав действий).

## Что из этого сделано вне дизайна

Единственный пункт, который **не требует** решения владельца или дизайна и является чистым дефектом — **тап по песне** (ПП-5 / И-3). Он и берётся первым.
