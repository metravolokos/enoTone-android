## Высокая серьёзность

### H-1. Выход не гарантирует удаление аудиоданных до очистки Keystore

Цепочка нарушает fail-closed порядок [ADR-0080](../../docs/DECISIONS/ADR-0080-permanent-login-sign-out.md).

```kotlin
// core/model/.../AccountSignOut.kt:33 — вызывает и идёт дальше
execute(Step.PLAYBACK) { port.stopPlayback() }
// ...
execute(Step.CREDENTIALS) { port.deleteCredentials() }
```

`stopPlayback()` возвращается до завершения очистки: `EnoTonePlaybackService.kt:328-337` только ставит работу в IO-очередь `submitIo { ... }`, подавляет ошибки через `catch (_: Exception)` и **не закрывает открытый `SimpleCache`**. Keystore удаляется, пока файлы могут ещё лежать на диске.

Составляющие проблемы:

1. `QueueStateFileStore.kt:133-140` игнорирует результат каждого `delete()` — тихий сбой удаления не останавливает выход.
2. При отсутствующем binder (`AndroidAccountSignOutPort.kt:28-38`) очищается только очередь; аудиокэш не трогается вообще.
3. Следующий запуск воспроизведения может переиспользовать старый объект `SimpleCache` (`PreviewAudioPlayback.kt:622-629`).

**Требуется:** единая suspend-операция: остановить writers → дождаться → закрыть/release `SimpleCache` → удалить и **проверить отсутствие** файлов. При отсутствующем binder — файловый fallback. Любая ошибка останавливает выход на шаге `PLAYBACK`, vault сохраняется для повтора.

**Проверено исполнителем:** подтверждено чтением кода 2026-11-22.

### H-2. Первый запуск может показать «Всё готово» при необработанных треках

`ManagedTagIndexSession.kt:185-211` возвращает `SESSION_BATCH_LIMIT` или `SESSION_TIME_BUDGET` при исчерпании лимита сессии.

`IndexingRunner.kt:93-101` считает ошибкой только `AUTH_REJECTED`, `RETRY_BACKOFF`, `NO_PROGRESS`:

```kotlin
val error = final.stopCode in setOf("AUTH_REJECTED", "RETRY_BACKOFF", "NO_PROGRESS")
statusPort.update(if (error) ManagedScanState.ERROR else ManagedScanState.COMPLETE, ...)
```

`FirstRunRoute.kt:134-140` и `FirstRunPhasePlanner.kt:39-55` после снятия `terminating` показывают `DONE`, не проверяя `remaining > 0`.

**Последствие:** при 80 пачках или четырёхчасовом лимите пользователь видит «Всё готово», хотя часть библиотеки не прочитана.

**Требуется:** `COMPLETE` только при действительном отсутствии eligible-файлов. Лимиты переводят сессию в `PAUSED` или отдельное состояние с явным «Продолжить». Для первого запуска перед `DONE` дополнительно требовать отсутствие pending-записей.

**Проверено исполнителем:** подтверждено чтением кода 2026-11-22.

### H-3. Scoped sign-out оставляет legacy-обложки аккаунта

При наличии другого аккаунта `AndroidAccountSignOutPort.kt:84-96` вызывает только `removeAccount()`.

- `removeAccount()` чистит лишь постоянное хранилище (`ArtworkPreviewRepository.kt:312-327`);
- legacy `cacheDir/enotone-artwork-v2` удаляется только через `clearAll()` (`ArtworkPreviewRepository.kt:329-347`);
- после повторного входа `migrateLegacy()` снова восстанавливает старую обложку (`ArtworkPreviewRepository.kt:563-574`).

**Требуется:** включить legacy refs в account-scoped cleanup. При удалении legacy-мастеров учитывать ссылки обоих хранилищ, чтобы не повредить общий мастер другого аккаунта. Нужен сквозной тест «выход → повторный вход → старая обложка не восстанавливается».

**Проверено исполнителем:** подтверждено чтением кода 2026-11-22.

## Средняя серьёзность

### M-1. Бюджет восстановления очереди не работает — дефект исполнителя

Исправление, вошедшее в PR #253 для #252, не выполняет заявленного.

`PlayerViewModel.kt:260-261`:

```kotlin
restoredAccount = sourceKey
restoreAttempts = 0        // бюджет обнуляется ПЕРЕД каждой попыткой
```

Счётчик сбрасывается на входе, поэтому `MAX_RESTORE_ATTEMPTS` не ограничивает ничего. Кроме того, `StateFlow` не эмитит равные значения, поэтому при неизменном состоянии повторной попытки может не быть вовсе.

**Тест даёт ложный PASS.** `PlayerViewModelTest.kt:250-269` эмитит одинаковые снимки:

```kotlin
repeat(10) { connection.emit(PlaybackSnapshot(connected = true)); advanceUntilIdle() }
assertTrue(repo.reads <= 4)   // проходит, потому что повтора не было
```

**Требуется:** счётчик сбрасывать только при смене аккаунта или успехе; retry планировать `Job` с ограниченным backoff. Тест должен эмитить **различающиеся** снимки и падать без исправления.

**Проверено исполнителем:** подтверждено; это брак в собственной работе.

### M-2. Гонка отмены prefetch

`TransientMediaCache.kt:162-211`: отмена может пройти между проверкой tickets (строка 179) и публикацией `activeNextWriter` (строка 189). Worker затем запускает `writer.cache()` уже после Next/Stop.

**Требуется:** после публикации writer — согласованная повторная проверка и отмена до начала загрузки; тест с latch в этом окне.

**Проверено исполнителем:** подтверждено чтением кода.

### M-3. Invalidation возвращает старую legacy-обложку

`ArtworkPreviewRepository.kt:355-409` удаляет постоянный ref, но следующий запрос сначала мигрирует legacy-копию. Поскольку `remoteModified` не входит в ключ (`:579-582`), изменение файла с прежними ETag/size может снова показать старое изображение без GET.

### M-4. Открытая медиатека поздно видит успешно обработанные файлы без тегов

`LibraryDataRevision.kt:49-57` учитывает только `savedWithTags`, игнорируя `completedWithoutTags`. Терминальный `COMPLETE` публикуется с `terminating = true`, поэтому переход «активно → завершено» не обнаруживается до `onDestroy` (`IndexingRunner.kt:93-130`).

### M-5. Legacy-recovery может оставить невосстанавливаемый stale manifest

`AccountSettingsViewModel.kt:100-107` снимает marker до удаления manifest. Сбой между шагами оставляет stale manifest, который позднее принимается за валидный (`AccountArtworkFileCleanup.kt:102-105`). Расходится с порядком, записанным в [ADR-0103](../DECISIONS/ADR-0103-legacy-signout-recovery.md). Требует уточнения решения владельца.

### M-6. Возможна потеря сетевой загрузки обложки текущего трека

`LibraryViewModel.kt:596-678`: `artworkJob` ждёт `PLAYING/PAUSED`, но может быть отменён повторным `refreshArtwork()`, пока `selecting` удерживает `LOADING`. Последующий переход в `PLAYING` без смены `trackId` обложку не перезапускает.

## Улучшения (не дефекты)

1. **Таймаут bind без reconnect.** `PlaybackConnection.kt:204-239` показывает `ERROR`, но не переподключается; `retryCurrent()` при `service == null` возвращает `false` (`PlaybackErrorSheet.kt:34-40`). Нужен повтор `bind` с ограниченным backoff.
2. **Детали артистов строятся жадно.** `LibraryViewModel.kt:297-299` создаёт планы всех артистов на каждый reload; `ArtistDetailPlanner.kt:29-66` повторно разворачивает альбомы. Влияние на FPS требует замера.
3. **Двойной reload после обновления альбома.** `LibraryViewModel.kt:751-754` вызывает `reload()` и сразу `LibraryDataRevision.bump()`, что даёт второй reload.
4. **Album refs отсутствующих треков** не попадают в manifest: `OfflineTrackCatalog.kt:37-40` исключает `missingScans > 0`. Низкий риск — остаются хешированные служебные ссылки.
5. **Унификация HTTP-стеков** — уже известный архитектурный долг, не новая находка.
6. **Расхождения документов.** `REQUIREMENTS.md:154` утверждает «detekt пока не блокирует», `ROADMAP.md:31` — «detekt с базовой линией уже блокирует».

## Что аудитор признал корректным

- Строгий same-origin HTTPS, запрет редиректов, проверки Range/Content-Range, размера и ETag в `WebDavMedia3DataSource`.
- AES-GCM и версионированный формат учётных данных (`LocalCredentialVault`, `CredentialEnvelope`).
- Запрет backup и персональных данных в Intent.
- Атомарная запись отдельных файлов состояния и восстановление предыдущей пары queue/position.
- Process-scope `NetworkMonitor` с фильтрацией устаревших callbacks.
- `survivingReferences() ?: return` предотвращает удаление мастеров при неполном наборе ссылок.

## Рекомендованный порядок работ (аудитор)

1. Fail-closed выход и гонка prefetch.
2. Преждевременное `DONE`.
3. Legacy-обложки.
4. Восстановление очереди.
5. Обновление медиатеки.

Все исправления аккаунта и файловой атомарности — класс R, требуют поведенческих fault-injection и process-death тестов.

1. **Исполнитель шёл по `KNOWN_ISSUES`, а не по коду** — рамка документа ограничила поиск.
