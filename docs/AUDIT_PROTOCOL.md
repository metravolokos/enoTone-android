# Протокол аудита, ревью и сокращения

Обязателен для любого исполнителя — человека, Claude, ChatGPT, внешнего аудитора — при ревью PR, аудите этапа или повторной проверке замечаний. Сценарии для проверки лежат в [SCENARIOS](SCENARIOS.md), способы запуска — в [TESTING](TESTING.md).

## 1. Три режима

| Режим | Когда | Объём |
|---|---|---|
| **Ревью PR** | перед каждым слиянием | изменённое поведение и сценарии, которых оно касается (ID из SCENARIOS) |
| **Аудит этапа** | после архитектурного этапа или шага дизайна; перед контрольной сборкой | взаимодействие затронутых подсистем: аккаунт ↔ службы ↔ Room ↔ экраны ↔ восстановление |
| **Повторная проверка** | после исправления замечаний | исходный сценарий и связанные регрессии |

**Моменты проверки** — требования к процессу, автоматического запуска нет:
- перед слиянием PR — ревью;
- после этапа — аудит этапа;
- перед контрольной сборкой, которую владелец ставит на Huawei, — согласованный набор сценариев из SCENARIOS;
- после исправления дефекта — повтор исходного сценария и соседних.

## 2. Обязательные правила

1. **Версия.** В начале отчёта: репозиторий, ветка, **полный SHA**. Для PR — базовый и проверяемый SHA. Не смешивать выводы по разным коммитам.
2. **Границы.** Перечислить, что было доступно: исходники, CI-журналы, APK, устройство. Чего нет — то не проверено, и выводы ограничены.
3. **Старые отчёты — гипотезы.** Замечание из прошлого аудита проверяется заново на текущем SHA. Само его наличие ничего не доказывает.
4. **Весь путь сценария:** действие пользователя → состояние (ViewModel) → служба или репозиторий → запись (Room, файлы, Keystore) → обновление потребителей (экраны, уведомление, MediaSession) → восстановление после перезапуска.
5. **Перед регистрацией дефекта** найти существующую защиту, альтернативные пути и тесты, которые могут опровергнуть вывод. Сослаться на них.
6. **Дефект ≠ пожелание.** Большой файл, отсутствие паттерна, «не как принято» — не дефект, пока нет сценария с неверным поведением. Пожелания идут отдельным списком.
7. **Нормы находок нет.** «Подтверждённых замечаний нет в пределах проверенного объёма» — допустимый результат.
8. **Аудит не даёт права** на исправления, коммиты, комментарии в PR и слияния от имени владельца. Это отдельное поручение.
9. **Не выдавать анализ кода за запуск.** «Подтверждено анализом кода» и «воспроизведено» — разные вещи.

## 3. Формат замечания

| Поле | Содержание |
|---|---|
| ID и название | `A-<дата>-<номер>`, коротко |
| Серьёзность | критично / высокая / средняя / низкая — последствия для пользователя |
| Подтверждение | **воспроизведено** / **подтверждено кодом** / **предполагаемый риск** — независимо от серьёзности |
| Условия и шаги | что нужно и в каком порядке |
| Ожидается / наблюдается | или вывод по коду |
| Ссылки | строки **конкретного коммита** (`blob/<SHA>/путь#Lnn`) |
| Проверка исправления | ID сценария или тест, который должен пройти |

Отчёт отдельно перечисляет: что проверено, что не проверено, какие проверки выполнены (команды и CI), какие вопросы остались.

**Статусы повторной проверки:** исправлено / частично исправлено / не исправлено / недостаточно данных / первоначальное замечание не подтвердилось.

## 4. Механизм сокращения

Исполнители-ИИ не чувствуют «боли» от лишних модулей, настроек и документов, поэтому сложность может расти незаметно. Ниже — замена этому сигналу.

### 4.1. Пороги (жёсткие)

- **Новый модуль, внешняя runtime-зависимость или пользовательская настройка** — только через ADR с решением владельца. Для модуля в ADR перечислить не меньше двух уже сделанных PR, которым новая граница помогла бы.
- **Базовая линия detekt не растёт.** Добавление в неё — только с обоснованием в PR и ревью. CI проверку получит в ближайшем PR «Качество».
- **Строковые проверки исходников не добавляются** (AGENTS §4); существующие только убывают.
- **Изменение проверки в существующем тесте** внутри PR-исправления — только с отдельным обоснованием в описании PR. Тест нельзя подгонять под ошибку.

### 4.2. Метрики сложности

Ведутся в [REDUCTION_REVIEWS](REDUCTION_REVIEWS.md) на каждом ревью:
- модули;
- runtime-зависимости;
- ADR со статусом «Действует/Частично»;
- пользовательские настройки;
- строковые Python-проверки;
- замечания detekt (позже — размер базовой линии);
- неиспользуемые строки;
- строки кода в `main` и тестах.

Рост любой цифры между ревью требует одной строки причины.

**Модули — в обе стороны**, по последним 30 PR:
- сколько модулей затрагивает типичное изменение (если много — границы мешают);
- сколько PR затрагивает каждый модуль (модуль, который правят все, не является самостоятельной областью).

### 4.3. Ревью «что удалить»

- **Когда:** при закрытии каждого шага дизайна (D2–D6) и этапа, **но не реже раза в месяц — 1-го числа**.
- **Вопрос:** не «что улучшить», а «что удалить»:
  - модули и зависимости;
  - настройки и функции;
  - ADR для перевода в архив;
  - тесты-дубли;
  - код и строки без вызовов;
  - разделы документов, описывающие прошлое.
- **Результат:** таблица кандидатов в REDUCTION_REVIEWS с решением по каждому: «удалено» / «удалить в PR …» / «оставлено, потому что …». Удалить пользовательскую функцию можно только решением владельца.
- **Mutation-замер** (PIT) на чистой логике: первый — после PR «Качество», повтор раз в 3 месяца или после крупной переделки. Цифра с датой записывается в REDUCTION_REVIEWS.

### 4.4. Согласованность решений

[CURRENT_DECISIONS](CURRENT_DECISIONS.md) — единственный источник текущих решений. ADR — история. Статус ADR определяет индекс [DECISIONS/README](DECISIONS/README.md), а не строка внутри файла. Каждое ревью сверяет индекс со свежими слияниями. Автоматическая проверка покрытия индекса появится в PR «Качество».

## 5. Текст для инструкций обычного ChatGPT

Вставляется вручную в инструкции проекта ChatGPT. Обычный ChatGPT сам `AGENTS.md` не читает.

> Перед любым аудитом или ревью репозитория `metravolokos/enoTone-android`: прочитай `docs/AUDIT_PROTOCOL.md` и нужные разделы `docs/SCENARIOS.md` и `docs/TESTING.md`. В начале отчёта укажи ветку и полный SHA (для PR — базовый и проверяемый). Если нет доступа к исходникам, журналам CI или устройству — скажи об этом и ограничь выводы. Отличай «воспроизведено», «подтверждено кодом» и «предполагаемый риск». Старые замечания проверяй заново. Ничего не исправляй, не коммить и не комментируй без отдельного поручения.
