# Известные ограничения M1

- В приватной Room подтверждены 3590 аудиофайлов. Их теги пока не импортированы.
- Новый Range-клиент — **только для одного диагностического файла**, с лимитами 8 МиБ/128 запросов; поддержка конкретных форматов системой пока не проверена.
- На случай смены файла во время чтения используется If-Range с сильным ETag; при слабом ETag или его отсутствии эта гарантия ограничена.
- Временный лимит XML WebDAV 16 МиБ остаётся. Нет массового чтения тегов, FTS, UI альбомов/артистов и playback.
- Нельзя публиковать реальные значения тегов, пути, ETag, email и пароль. Android backup отключён.
- Лицензия исходников и Gradle Wrapper открыты.

- Debug APK из независимых GitHub Actions runs имеют **разные сертификаты**: установка поверх `app.enotone.android` может завершиться ошибкой подписи. Старая Room должна сохраняться; новый отдельный `.preview.r<номер CI>` пакет не содержит старую базу.
- Каждая новая CI Preview до настройки signing key имеет собственный applicationId, поэтому не обновляет предыдущий Preview и начинает с пустой Room. Для стабильных обновлений требуется защищённый ключ в GitHub Secrets; открытый debug.keystore запрещён.

- Huawei Preview #36 не прочитал теги одного файла; общая ошибка не раскрывает причину. Добавляется безопасная диагностика Range/экстрактора (ADR-0020). Массовое извлечение заблокировано до теста одного файла.

- На Huawei Preview #38 первый Range-запрос получил HTTP 206, но проверка Content-Range не прошла (0 прочитанных байт). Причина отличия границ пока неизвестна; ADR-0021 добавляет безопасную числовую диагностику. Не ослаблять Content-Range до выяснения отличий.

- Huawei Preview #40: Cloud.Mail.ru вернул HTTP 206, но заголовок не совпал с узкой числовой грамматикой `Content-Range` (`FORMAT`). Поддержка RFC 9110 неизвестного размера `/*` добавлена как гипотеза; реальная форма заголовка неизвестна. Без подтверждения на устройстве массовую загрузку не начинать.

- Huawei Preview #42 диагностировал `FORMAT_EQUALS_SEPARATOR` у `Content-Range` (HTTP 206, 0 байт). Поддержка точной формы с `bytes=` добавлена в PR (ADR-0023) с неизменными числовыми/байтовыми проверками, но реальный успешный тест на Huawei ещё не пройден.

- На Huawei Preview #45 успешно прочитаны теги одного файла, но цена составила 50 GET / 3,125 МиБ. Массовое чтение требует оптимизации и тестов на нескольких форматах.
- Новый one-track SQL UPDATE в Room защищён версией записи, но ещё не проверен инструментальными тестами на устройстве. Если у сервера нет сильного ETag, полная неизменность файла во время чтения не доказана.

- Huawei Preview #47 подтвердил `Сохранено в Room: 1`, но отдельное чтение тегов после перезапуска ещё не проверялось. Новый Draft по ADR-0025 добавляет офлайн-агрегаты.
- title=1 может означать запасное название из имени файла, а не обязательно реальный встроенный title; отсутствие artist/album у выбранного трека не является доказанной неисправностью.
- Временные Preview разных CI runs имеют разные applicationId и базы: нельзя проверить сохранность между разными Preview, нужно использовать одну установку.

- LRU до 256 КиБ может уменьшить повторные GET при скачках MediaMetadataRetriever назад, но не ускоряет чисто последовательный доступ; доказательства улучшения именно на Huawei пока нет.
- Постоянный signing key всё ещё отсутствует: каждый Preview run имеет собственный applicationId и отдельную Room. Это важно для сопоставимых тестов.

- Быстрый парсер первого среза поддерживает только частые разметки ID3v2.3/v2.4/ID3v1 и native FLAC Vorbis Comments. Несовместимые ID3 unsync/extended/compressed, OGG/Opus/M4A, а также большие комментарии возвращают `UNSUPPORTED_*` или `FAST_BUDGET_EXCEEDED`; **без** автоматического дорогостоящего fallback. Не считать название из имени файла встроенным тегом.
- Экономия HTTP на реальной медиатеке пока не измерена; целевые 1–3 GET — гипотеза для типичных файлов, не гарантия. Не запускать массовый обход до измерений.

- Room v2 AutoMigration v1→v2 пока не проверена отдельным инструментальным тестом на старой базе. На новом Preview БД создаётся заново; не удалять прежние приложения и не включать destructive migrations.
- Пилотные 10/20 треков не покрывают все возможные форматы и файлы. Retryable ошибки пока сортируются после новых, без автоматического планировщика повторов; текущий HTTP GET при отмене может закончиться по timeout.
- Встроенная проверка тегов MP3/FLAC подтверждена только на двух реальных файлах Huawei; массовое сканирование 3590 не запускалось.

- Preview r59: один файл пилота сообщил ошибку при 9 завершённых, но тип и имя файла неизвестны. Старый офлайн-индикатор объединяет временные ошибки и ещё не проверенные. PR #20 добавляет безопасные коды и отдельные счётчики; результат на Huawei ещё не проверен. Постоянный HTTP/Range/парсерный сбой должен блокировать повторную обработку той же версии, временный — оставаться доступным в последующих ручных пилотах. Без автоматического повторного цикла.

- M2 экран треков — локальный preview: большая часть списка пока отображает имя файла вместо встроенного title (теги прочитаны только у 30/3590 треков в проверенной Preview #67). Альбомная/исполнительская группировка и FTS не готовы; новые версии Preview имеют отдельную Room и не перенесут старый локальный список автоматически.

- M3 проба ExoPlayer до тестирования на Huawei: формат WebDAV Content-Range `bytes=...` нестандартный, совместимость потокового Media3 DataSource с seek и длительностью неизвестна. Фоновая служба, MediaSession, очередь, временный кэш текущего и следующего трека, пульт гарнитуры ещё не реализованы. Отправка приватных URL/секретов в логи или включение redirect запрещены.

- Первый M3 эксперимент с OkHttp заблокирован строгим GMS-free APK scan из-за опционального TLS provider probe `com.google.android.gms.org.conscrypt`. Использовать только заменяющий HTTPS Media3 DataSource при полностью зелёном CI; не белить маркер в сканере.

- Draft M3 MediaSessionService: приложение ещё не проверено на Huawei при сворачивании, блокировке экрана, Bluetooth-управлении, паузе из шторки. Проигрыватель служебный и однотрековый: нет авто-next, списка воспроизведения, долговременного восстановления после гибели процесса, двойного кэша и подписанного обновления старой Preview.

- M4-A: очередь существует только в RAM, пользовательская сортировка — порядок текущего списка/поиска. Окончание трека автоматически переводит к следующему только в прототипе; на Huawei ещё не проверено. Нет skip-next/previous через MediaSession кнопки гарнитуры или шторки, shuffle/repeat, сохранённой очереди после убийства процесса, кэша двух файлов или постоянного signing key. При открытии новой Preview придётся один раз сохранить перечень /AllMusic.

- M4-B нативный Media3-плейлист: поведение системных skip-кнопок и гарнитуры на Huawei ещё не проверено; отображение конкретных кнопок зависит от System UI. Заполнение плейлиста MediaSources в RAM не равно сетевой загрузке всей библиотеки, но Media3 может заранее буферизовать следующий элемент — измерить отдельно перед M5. Shuffle, repeat, стабильный сертификат Preview, восстановление после убийства процесса и кэш двух файлов всё ещё не готовы.

- M4-C: repeat/shuffle действуют только пока существует процесс Media3 службы и пока не проверены на Huawei. После убийства процесса настройки вернутся к значениям по умолчанию. Собственное уведомление enoTone на Huawei работает; интеграция в отдельную системную мультимедиа-панель для сторонних приложений на этом устройстве не поддерживается по сообщению владельца и не является регрессией.

- M5-A кэш: возможны параллельные сетевые чтения для streaming и full-current download, так что до измерений реальная экономия трафика не доказана. Уже открытое сетевое соединение не обязательно мгновенно переключается в кэш после 100%; локальные сегменты будут использованы при новых чтениях/seek. Нет prefetch next, Wi-Fi only, полосы буферизации по времени или сохранения offline. Ограничение full-current 256 МиБ, общий LRU 512 МиБ; при ошибке fallback в streaming. До Huawei это Draft.

- Huawei Preview #96: замедление первого звука после добавления кэша — около 6 с подключения плюс 1 с буферизации. Причина пока не подтверждена профилированием; в Draft PR #27 устранён наиболее вероятный конкурентный запрос на весь файл до первого READY. Это ещё не доказательство решения: требуются сопоставимые повторные измерения на Huawei. Не повышать сетевой параллелизм, не снимать TLS/Range/ETag проверки.

- Huawei Preview #102 не ускорила начальный старт по сравнению с #96 (примерно 6 с подключения плюс 1 с буферизации). Причина НЕ определена. Вместо дополнительных таймеров теперь в Draft #27 режимы cache-off/cache-on и числовые временные отметки очереди/Media3/BUFFERING/READY/playing. Локальную Room/URL-подготовку переносим на открытие библиотеки; наблюдаемую экономию времени ещё нужно подтвердить. Не принимать M5-A до сравнения.

- Huawei Preview #111 диагностировала ~3,3 секунды **синхронно внутри playQueue** до первого BUFFERING: без кэша Room 4 мс / Media3 3347 мс / isPlaying 3793 мс; с кэшем Room 3 мс / Media3 3279 мс / isPlaying 3873 мс. Не считать 6 с «подключения» доказательством 6 с реальной WebDAV задержки. Экспериментальный staged Media3 timeline в Draft #27 уменьшает начальную очередь до выбранного ±2, после READY добавляет оставшиеся треки частями. До проверки Huawei возможны проблемы переходов/прогрузки полного списка: PR не объединять. Прогресс Media3 sources не означает скачивание файлов.

- M5-B Draft: next prefetch запускается только после 100% текущего, только при включённом cache-on и наличии реального следующего Media3 item. Для repeat-one и конца очереди prefetch отсутствует. Возможен лишний трафик при частом изменении shuffle или переключении файлов, но одновременно работает максимум один CacheWriter worker. Реальная скорость Next с уже готовым файлом и поведение в фоне ещё не подтверждены на Huawei. Кэш не сохраняется после завершения службы.

- M6-A Draft: READY/isPlaying метрики переходов — события Media3, **не акустическое gapless измерение**; при смене в фоне данные сохраняются только в RAM службы, читаются по возврату на экран. В Huawei отдельная медиапанель для сторонних приложений не поддерживается по наблюдению владельца, но собственное уведомление enoTone ранее работало. Цвета берутся из утверждённой дизайн-палитры; настоящие иконки/wordmark/типографика пока не импортированы, произвольные замены запрещены. Нужна проверка контраста, читабельности и кнопок в светлой/тёмной теме на устройстве.
