## 1. ЦЕЛЬ ПРОДУКТА

Android-приложение — аудиоплеер, который проигрывает музыку из папки `AllMusic` в облачном хранилище Cloud.Mail.ru, подключаясь по WebDAV. Приложение должно полностью работать на устройствах БЕЗ сервисов Google (Huawei/HarmonyOS-совместимые, de-Googled ROM, GrapheneOS без Play Services и т. п.).

Целевой экран для проектирования UI: 1320×2856 px (вытянутый, около 19,5:9), портретная ориентация как основная; планшеты и ландшафт — адаптивно, но вторым приоритетом.

## 2. ЖЁСТКИЕ ОГРАНИЧЕНИЯ (нарушать нельзя)

1. Никаких зависимостей от Google Play Services / Firebase / GMS / FCM / Google Fonts (downloadable fonts) / Google Cast / ML Kit / Play Core / Play Billing / Crashlytics / Google Maps. Допускаются библиотеки AndroidX (Jetpack, в т. ч. Media3, Room, WorkManager, DataStore) — они не требуют GMS. Для WorkManager и Media3 проверь, что код не тянет GMS транзитивно.
2. CI обязан содержать проверку, которая падает, если в дереве зависимостей (`./gradlew :app:dependencies`) или в итоговом APK/манифесте встречаются `com.google.android.gms`, `com.google.firebase`, `com.google.android.play`.
3. Только HTTPS. Cleartext-трафик запрещён (`networkSecurityConfig`), исключение допускается только для debug-сборки и локального mock-сервера.
4. Секреты (пароль внешнего приложения Cloud.Mail.ru, API-ключ ИИ) не попадают в репозиторий, логи, бэкапы и crash-отчёты. Хранение — Android Keystore (AES-GCM) поверх DataStore/файла. Библиотеку `androidx.security:security-crypto` не использовать (deprecated), реализовать тонкую обёртку над Keystore либо взять поддерживаемую альтернативу и обосновать выбор в ADR.
5. `android:allowBackup="false"` либо правила `dataExtractionRules`/`fullBackupContent`, исключающие хранилище секретов и кэши.
6. Приложение не отправляет телеметрию и не делает сетевых запросов, кроме: (а) к WebDAV-серверу пользователя, (б) к ИИ-эндпоинту, если пользователь его включил.
7. Минимальная версия Android: minSdk 26 (обоснуй в ADR, можно предложить иное), targetSdk — актуальная на дату разработки (проверь по официальной документации, не по памяти).
8. Лицензии зависимостей должны быть совместимы с публикацией исходников и сборкой для F-Droid (предпочтительно Apache-2.0/MIT/BSD). Составь `docs/THIRD_PARTY_LICENSES.md`.

## 3. ТЕХНОЛОГИЧЕСКИЙ СТЕК (предложение; отклонения — только через ADR)

- Язык: Kotlin, корутины и Flow.
- UI: Jetpack Compose + Material 3, edge-to-edge, тёмная/светлая/системная тема. Шрифты — только системные или вшитые в APK.
- Воспроизведение: AndroidX Media3 (ExoPlayer + MediaSessionService + MediaLibraryService) с собственным `DataSource.Factory` поверх OkHttp для WebDAV.
- Сеть: OkHttp. WebDAV-клиент — собственный тонкий слой (PROPFIND/GET с Range/HEAD) поверх OkHttp с парсингом multistatus XML; сторонние WebDAV-библиотеки (например, Sardine) допускаются только после проверки их пригодности для Android без GMS и обоснования в ADR.
- Локальная БД: Room (SQLite) + FTS для поиска.
- Настройки: DataStore (Proto или Preferences).
- Фон: WorkManager (синхронизация библиотеки), Foreground Service типа `mediaPlayback` (воспроизведение).
- Картинки: Coil (с собственным дисковым кэшем нужных размеров) либо собственный загрузчик — выбери и обоснуй.
- DI: Hilt или Koin (выбери одно, обоснуй; учти время сборки и простоту для других агентов).
- Теги аудио: сначала проверь возможности Media3 `MetadataRetriever`/`MediaMetadataRetriever` с кастомным `MediaDataSource` на HTTP Range; при недостаточности — jaudiotagger-форк или собственный лёгкий парсер ID3v2/Vorbis comment/MP4 atoms/FLAC PICTURE. Выбор зафиксируй в ADR.
- Сборка: Gradle Kotlin DSL, version catalog (`libs.versions.toml`), многомодульность (см. раздел 4).
- Качество: ktlint или spotless, detekt, Android Lint, JUnit5/JUnit4 + Turbine + MockK, Robolectric/инструментальные тесты там, где оправдано, Compose UI-тесты для ключевых экранов, скриншот-тесты — по желанию.

## 4. АРХИТЕКТУРА

Чистая многомодульная архитектура, зависимости направлены строго внутрь:

```
:app                     — точка входа, навигация, DI-сборка
:core:common             — утилиты, результат/ошибки, диспетчеры, логирование без секретов
:core:model              — доменные модели (Track, Album, Artist, Playlist, QueueItem...)
:core:database           — Room, DAO, миграции, FTS
:core:network            — OkHttp, WebDAV-клиент, аутентификация, ретраи
:core:datastore          — настройки, защищённое хранилище секретов
:data:library            — репозиторий медиатеки, индексатор, синхронизация (WorkManager)
:data:source             — абстракция MusicSource + реализации (WebDavSource, SafSource, LocalSource-заглушка)
:data:cache              — кэш обложек и аудио, политики вытеснения
:data:playlist           — плейлисты (модель и БД сейчас, UI позже)
:playback                — MediaSessionService, очередь, shuffle/repeat, прелоад
:feature:library         — экраны: Треки / Альбомы / Артисты
:feature:player          — мини-плеер, экран «Сейчас играет», экран очереди
:feature:settings        — аккаунт, кэш, синхронизация, диагностика, ИИ-настройки
:feature:ai              — ЗАГОТОВКА под ИИ-агентов (интерфейсы и настройки, без UI-функций)
```

Принципы:
- Источник музыки скрыт за интерфейсом `MusicSource` (список/метаданные/открытие потока/получение обложки/ETag). Благодаря этому возможны источники: WebDAV (основной), SAF/DocumentsProvider (запасной), локальные файлы (на будущее).
- Состояние UI — однонаправленный поток данных (MVI/MVVM + StateFlow). Бизнес-логика не живёт в Composable.
- Единственный источник истины для медиатеки — БД Room; UI читает только из неё. Сеть пишет в БД.
- Идентификатор трека стабилен и не зависит от порядка сканирования: хэш от нормализованного удалённого пути + запись ETag/size/mtime. При переименовании/перемещении файла предусмотри эвристику повторного сопоставления (размер + длительность + теги), чтобы не терять плейлисты.

## 5. ИНТЕГРАЦИЯ С CLOUD.MAIL.RU И «МАКСИМУМ ВОЗМОЖНОСТЕЙ СИСТЕМЫ ПО ФАЙЛООБМЕНУ»

Исходные сведения (ГИПОТЕЗЫ, проверить на устройстве в M0 через диагностику):
- Endpoint WebDAV: `https://webdav.cloud.mail.ru/`.
- Логин — полный e-mail; пароль — отдельный «пароль для внешнего приложения», созданный в настройках аккаунта Mail.ru (основной пароль, вероятно, не подойдёт, особенно при 2FA).
- Возможны: отключённый `Depth: infinity`, ограничения скорости, отсутствие/своеобразие ETag, особенности поддержки `Range`, нестандартные заголовки, URL-кодирование кириллицы, нормализация Unicode (NFC/NFD) в именах.

Требования:
1. Основной канал — прямой WebDAV (PROPFIND `Depth: 1`, рекурсивный обход папки `AllMusic` с ограничением параллелизма, GET с `Range` для потоковой передачи и чтения тегов).
2. Использовать возможности системы по работе с файлами насколько это осмысленно:
   - Storage Access Framework: опциональный источник `SafSource` через `ACTION_OPEN_DOCUMENT_TREE` с `takePersistableUriPermission` — на случай, если на устройстве есть иной клиент облака, предоставляющий `DocumentsProvider`. Не считать его основным путём.
   - Intent-фильтры `ACTION_VIEW`/`ACTION_SEND` для audio/*, чтобы плеер открывал отдельные файлы из других приложений (read-only).
   - Системные механизмы сети: `ConnectivityManager.NetworkCallback`, учёт метрированных сетей (настройка «кэшировать только по Wi-Fi»), уважение системного прокси/VPN, `NetworkSecurityConfig`.
   - Системное хранилище кэша: `cacheDir`/`externalCacheDir` с учётом `StorageManager.getCacheQuotaBytes()` и сигналов нехватки памяти.
   - Системные медиа-интеграции: MediaSession, уведомление с обложкой, медиа-кнопки гарнитуры и Bluetooth, Audio Focus, `ACTION_AUDIO_BECOMING_NOISY`, экран блокировки, (опционально) Android Auto без GMS-зависимостей.
   - Опционально, отдельным этапом после MVP: собственный read-only `DocumentsProvider`, отдающий кэшированные/удалённые файлы другим приложениям. Только после ADR о рисках безопасности.
3. Продумай и запиши в ADR, почему именно такой набор и порядок источников, а что отложено.
4. Загрузку файлов выполнять потоково, без загрузки целого файла в память. Поддержать докачку по Range. Корректно обрабатывать 401/403/404/429/5xx, таймауты, обрывы сети (экспоненциальный backoff с джиттером), смену сети Wi-Fi↔мобильная.

## 6. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 6.1 Подключение и настройки аккаунта
- Экран настройки: логин, пароль внешнего приложения, путь корневой папки (по умолчанию `/AllMusic`), кнопка «Проверить подключение» с понятной диагностикой ошибок (неверный пароль, нет папки, нет сети, TLS).
- Секреты — только в защищённом хранилище.

### 6.2 Индексация медиатеки
- Первичное сканирование с прогрессом (число папок/файлов, текущая папка) в виде уведомления и экрана; прерываемое и возобновляемое.
- Инкрементальная синхронизация: по ETag/`getlastmodified`/размеру; теги читаются только для новых и изменённых файлов; удалённые файлы помечаются, а не стираются мгновенно (на случай временной ошибки сервера).
- Периодическая синхронизация через WorkManager + ручной «потянуть для обновления».
- Поддержка форматов: mp3, flac, ogg/opus, m4a/aac, wav; остальные — игнорировать с записью в диагностический лог.
- Теги: title, artist, album artist, album, track/disc number, year, genre, длительность, встроенная обложка. Фоллбэк, если тегов нет: разбор структуры `Артист/Альбом/NN - Название.ext`. Файлы обложек в папке: `cover.jpg`, `folder.jpg`, `front.jpg` и т. п.
- Кириллица и Unicode: нормализация NFC для сравнения, сортировка с учётом локали (русская коллация), игнорирование артиклей «The/A/An» при сортировке (настройка), корректное объединение артистов с разным регистром/написанием; обработка сборников (Various Artists).

### 6.3 Представление медиатеки
- Три раздела: Треки, Альбомы, Артисты. Навигация — нижняя панель или вкладки (обоснуй выбор для экрана 1320×2856, зона досягаемости большого пальца).
- Треки: плоский список с быстрой прокруткой и сортировкой (название/артист/альбом/дата добавления).
- Альбомы: сетка обложек (2–3 колонки адаптивно), экран альбома со списком треков по дискам.
- Артисты: список → экран артиста (альбомы + все треки).
- Поиск по библиотеке на FTS (по названию, артисту, альбому), устойчивый к регистру и ё/е.
- Paging для больших библиотек (десятки тысяч треков), без загрузки всего списка в память.

### 6.4 Обложки и их кэш
- Размеры кэша исходят из экрана 1320×2856: 
  - «большая» версия для экрана «Сейчас играет»: квадрат до 1320×1320 px (формат WebP/JPEG, качество ~85);
  - «средняя» для сетки альбомов: ~512 px по большей стороне;
  - «малая» для списков/уведомления/мини-плеера: ~192 px.
- Алгоритм: исходник читается один раз (из тега или файла папки), из него генерируются нужные размеры; большая версия генерируется лениво (только для проигрываемого и ближайших в очереди альбомов), чтобы не раздувать кэш.
- Дисковый LRU-кэш обложек с настраиваемым лимитом (по умолчанию предложи значение и обоснуй), ключ — стабильный ID альбома + хэш содержимого/ETag.
- Показ плейсхолдера, отсутствие «прыжков» вёрстки, поддержка Palette/динамических цветов из обложки (без GMS) — по желанию.
- Учти плотность экрана и `Bitmap.Config`, избегай OOM (downsampling при декодировании, `inSampleSize`).

### 6.5 Кэширование аудио (временное)
- Всегда держать в кэше полностью «текущий» и «следующий» трек очереди (с учётом режима shuffle/repeat, т. е. «следующий» вычисляется по фактическому порядку воспроизведения).
- Реализация на базе Media3 `CacheDataSource` + `SimpleCache` (или иной — через ADR), «закрепление» (pinning) текущего и следующего треков, остальные записи вытесняются по LRU с настраиваемым общим лимитом.
- Пересчёт прелоада при смене очереди, включении/выключении shuffle, смене режима повтора, пропуске трека, ручном выборе трека.
- Прелоад отменяется/приостанавливается при отсутствии сети либо при политике «только Wi-Fi».
- Поддержка бесшовного перехода (gapless) для форматов, где это возможно.
- Опциональная настройка «Сохранить трек/альбом офлайн» — ТОЛЬКО как задел в архитектуре, не в MVP.

### 6.6 Очередь, shuffle и повтор
- Очередь формируется по контексту запуска: «по трекам» (вся библиотека/текущий список/результаты поиска), «по альбому», «по исполнителю».
- Shuffle: честная перестановка (Fisher–Yates) с фиксацией порядка на время жизни очереди; текущий трек остаётся текущим при включении shuffle; при выключении — возврат к исходному порядку без потери позиции; опционально избегать подряд идущих треков одного артиста (настройка).
- Повтор: выкл / повтор всей очереди / повтор одного трека. Переключение — циклически одной кнопкой; состояние сохраняется.
- Экран очереди: просмотр, переупорядочивание перетаскиванием, удаление, «играть следующим», «добавить в конец».
- Сохранение и восстановление состояния (очередь, позиция, режимы) между запусками приложения и после убийства процесса системой.

### 6.7 Плейлисты (задел на будущее)
- Сейчас: полностью спроектированная модель данных и репозиторий (`Playlist`, `PlaylistItem` с позицией, датами, ссылкой на стабильный `trackId`), миграции Room, unit-тесты. Один служебный плейлист «Избранное» допустим как проверка модели.
- UI создания/редактирования плейлистов — следующий этап, но API репозитория и точки расширения в очереди («добавить в плейлист») должны быть предусмотрены.
- Продумай экспорт/импорт плейлистов (M3U8) как будущую возможность (в ADR — только заметка).

### 6.8 Подключение ИИ-агентов (задел на будущее)
- Сейчас реализуются ТОЛЬКО: экран настроек и безопасное хранение параметров совместимого с OpenAI API: Base URL, API-ключ, имя модели, таймауты, флаг «включено» (по умолчанию выключено). Кнопка «Проверить соединение» (минимальный запрос, например список моделей или короткий chat/completions) — по желанию.
- Интерфейсы (без реальной логики): `AiAgentGateway` (запросы chat/completions в OpenAI-совместимом формате, стриминг SSE), `AiToolRegistry` (описание инструментов function calling: поиск по библиотеке, чтение/изменение очереди, создание плейлиста, управление воспроизведением), политика приватности.
- Принципы: агенту передаются только метаданные (названия, артисты, альбомы), НИКОГДА аудио, пути в облаке и учётные данные; любые действия агента, изменяющие данные, требуют подтверждения пользователя (настройка); все вызовы логируются без секретов; без явного включения сеть не используется.
- Любой Base URL допускается только с HTTPS (кроме явного режима разработчика для localhost).

### 6.9 Диагностика (обязательна, т. к. разработка идёт без доступа к реальному облаку)
- Экран «Диагностика»: результат проверки WebDAV (статус, заголовки ответа, поддержка Range, наличие ETag, поддержка `Depth: infinity`, время ответа), статистика индексации, размеры кэшей, последние ошибки.
- Экспорт диагностического отчёта в файл/буфер с автоматическим вырезанием секретов, чтобы владелец мог приложить его к issue и передать следующему агенту.
- Режим подробного логирования (выключен по умолчанию), кольцевой буфер логов.

## 7. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

- Производительность: холодный старт до интерактивного списка из БД — быстро (цель: до ~1 с на среднем устройстве); прокрутка 60 fps на 10 000+ треков; запуск воспроизведения — без видимой задержки при прогретом кэше.
- Энергопотребление: корректные WakeLock/WifiLock через Media3 (`setWakeMode(WAKE_MODE_NETWORK)`), синхронизация только при подходящих условиях.
- Надёжность: воспроизведение переживает смену сети, блокировку экрана, Doze, давление по памяти; корректное поведение при уходе приложения в фон (Android 14+ типы foreground service, Android 13+ разрешение на уведомления, Android 15/16 ограничения фона).
- Доступность: контентные описания, поддержка TalkBack, масштабирование шрифта, достаточный контраст.
- Локализация: русский (по умолчанию) и английский через `strings.xml`; без хардкода строк.
- Размер APK и время сборки: следить, включить R8/minify и shrink resources для release.

## 8. ТЕСТИРОВАНИЕ БЕЗ РЕАЛЬНОГО ОБЛАКА

- Mock-сервер WebDAV: OkHttp `MockWebServer` для unit-тестов и локальный контейнер (например, WsgiDAV/Apache/nginx dav) с генератором тестовой музыки (короткие синтетические файлы с тегами и обложками, кириллические имена, вложенные папки, сборники, файлы без тегов) для интеграционных тестов в CI.
- Сценарии, обязательные в тестах: ответ 401/403/404/429/5xx, обрыв посреди потока, сервер без поддержки Range, сервер без ETag, `Depth: infinity` запрещён, NFC/NFD в путях, пустые теги, огромные обложки, битые файлы.
- Тесты очереди: shuffle (корректность перестановки, фиксация порядка, возврат к исходному), repeat all/one, «следующий» трек при разных режимах, восстановление состояния.
- Тесты кэша: закрепление текущего и следующего, вытеснение по лимиту, пересчёт при изменении очереди.
- Тесты БД: миграции (схемы Room экспортируются в репозиторий), FTS, плейлисты.

## 9. CI/CD И ПРОЦЕСС РАЗРАБОТКИ НА GITHUB

- GitHub Actions: сборка `assembleDebug`, unit-тесты, lint, detekt/ktlint, проверка запрета GMS-зависимостей (см. раздел 2), публикация debug-APK как артефакта workflow; по тегу — release-APK в GitHub Releases (подпись ключом из GitHub Secrets; ключ в репозитории не хранить; описать процедуру в `docs/RELEASE.md`).

## 11. ПРАКТИКИ ДЛЯ «ВАЙБКОДИНГА» (обязательно соблюдать)

- Работай маленькими, проверяемыми шагами; после каждого шага сборка и тесты должны быть зелёными. Не оставляй репозиторий в нерабочем состоянии между коммитами.
- Сначала контракты (интерфейсы, модели, схема БД, спецификации в `docs/`), потом реализация. Сначала тест/фейк, потом интеграция.
- Не пиши «заглушки, которые выглядят как готовые функции». Недоделанное помечай явно (`NotImplementedError` + запись в `STATUS.md`/`KNOWN_ISSUES.md`).
- Не изобретай API библиотек: проверяй по актуальной документации и фактическим версиям в `libs.versions.toml`; при сомнении пиши минимальный проверочный тест/спайк.
- Не добавляй зависимости без необходимости; каждая новая — с мотивировкой, лицензией и проверкой на отсутствие GMS.
- Не делай масштабных рефакторингов «заодно». Не меняй форматирование всего проекта в функциональных PR.
- Фиксируй версии (Gradle wrapper, AGP, Kotlin, Compose BOM, Media3) и обновляй осознанно.
- Каждый экран — с превью Compose и состояниями: загрузка / пусто / ошибка / данные.
- Все долгие операции — отменяемые, с прогрессом и обработкой ошибок. Никаких блокировок главного потока (включить StrictMode в debug).
- Логи — структурированные, без секретов; один централизованный логгер.
- Перед завершением этапа: самопроверка по Definition of Done (ниже) и краткий отчёт.

- [ ] Код собирается, тесты и lint зелёные в CI.

- Инициализация репозитория: структура модулей, Gradle, version catalog, CI, шаблоны PR/issue, проверка запрета GMS.

**M1 — Индексация:** WebDAV-клиент, обход, теги, БД, инкрементальная синхронизация, экран прогресса.
**M2 — Медиатека (UI):** треки/альбомы/артисты, поиск, кэш обложек трёх размеров.
