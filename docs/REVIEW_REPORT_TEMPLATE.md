# Бланк отчёта ревью

**Запрос «проведи ревью PR N» — всё, что нужно сказать агенту.** Он открывает этот бланк и протокол, проводит ревью и заканчивает одним из трёх итогов (раздел 6): предложение на слияние, задание исполнителю или вопросы владельцу. Слияние выполняется только по команде владельца.

Ревьюер **начинает с этого бланка**, а не со свободного текста: копирует в файл, заполняет по порядку разделов 0→1→2 **до** поиска замечаний, затем раздел 3. Правила — [AUDIT_PROTOCOL](AUDIT_PROTOCOL.md); бланк только не даёт пропустить обязательное. Перед публикацией:

```bash
python3 tools/review_helper.py triggers <BASE_SHA> <HEAD_SHA>   # шаг 1: кандидаты по всем семи триггерам
python3 tools/review_helper.py check report.md                  # шаг 4: форма отчёта полная
```

Публиковать отчёт, пока `check` выдаёт ошибки, нельзя. Скрипт проверяет наличие частей, а не качество рассуждения. Совпадение детектора в diff — только подсказка: решает ответ на поведенческий вопрос (правило 10).

Порядок работы, в котором ошибаются: сначала искать дефект, потом оформлять. Здесь наоборот: бланк заполняется раньше, замечания вносятся по мере нахождения, в готовой форме.

---

```markdown
# Ревью PR #<N>: <название>

## 0. Версия и границы
- Репозиторий / ветка: 
- Base SHA (полный): 
- Проверяемый HEAD SHA (полный): 
- Доступно: исходники / CI-журналы / устройство (что именно)
- Не доступно (и значит не проверено): 

## 1. Триггеры
Заполнить по выводу `review_helper.py triggers`: **все семь строк**, у каждой «да/нет» и что именно сверено.

| Триггер | Срабатывает? | Что сверено / где артефакт |
|---|---|---|
| T-NAV | да/нет | |
| T-VM | да/нет | |
| T-LIFE | да/нет | |
| T-PERSIST | да/нет | |
| T-AUTH/NET | да/нет | |
| T-CONC | да/нет | |
| T-PLAYBACK | да/нет | |

Для каждого «да» — раздел ниже с артефактом по таблице AUDIT_PROTOCOL §2.1 (описывает поведение, не результат поиска). Для общих ресурсов — обратный обход `git grep` по ресурсу (правило 11).

### Артефакт T-<…>
(таблица)

## 2. Новое поведение и тесты (правило 12)
Одна строка на каждое новое или изменённое поведение. Слой: JVM / Compose UI / Roborazzi / Huawei / нет. Для исправлений «критично/высокая» — был ли тест красным до исправления.

| Поведение | Тест | Слой | Красный до исправления | Заглушка вместо механизма? |
|---|---|---|---|---|
| | | | | |

Если поведение не менялось: фраза «нового поведения нет» и что сверено.

## 3. Замечания
Каждое замечание — отдельный подраздел `### <ID> — название` со **всеми** полями. Серьёзность: критично / высокая / средняя / низкая. Подтверждение: воспроизведено / подтверждено кодом / предполагаемый риск. Решение: BLOCK / VERIFY_REQUIRED / OWNER / FOLLOWUP / INFO.

### R-1 — название
- **Серьёзность:** 
- **Подтверждение:** 
- **Решение:** 
- **Отклонение от утверждённого:** нет / ссылка на пункт Issue, ADR, спецификации (тогда решение OWNER)
- **Условия и шаги:** 
- **Ожидается / наблюдается:** 
- **Ссылки:** `blob/<полный SHA>/путь#Lnn`
- **Опровержение (правило 5):** где искал защиту (вызывающие, соседние обработчики, тесты, документы, код вне diff) и что нашёл
- **Проверка исправления:** ID сценария или тест

(Честный результат «подтверждённых замечаний нет в проверенном объёме» допустим.)

## 4. Отклонения от утверждённого
Список с решением OWNER, или «нет».

## 5. Что проверено / не проверено
Команды и CI (с номером), что не запускалось, открытые вопросы.

## 6. Итог
**Вердикт:** MERGE_PROPOSED / FIX_REQUIRED / OWNER_DECISION

- MERGE_PROPOSED — нет замечаний с решением `BLOCK` или `VERIFY_REQUIRED`, нет ожидающих `OWNER`, CI точного HEAD зелёный (номер и URL), Huawei-сценарии названы. Слияние только по команде владельца.
- FIX_REQUIRED — есть `BLOCK` или `VERIFY_REQUIRED`. Ниже обязательно «Задание исполнителю».
- OWNER_DECISION — блокеров нет, но ждут решения владельца. Ниже список вопросов с вариантом по умолчанию.

### Задание исполнителю
(только при FIX_REQUIRED; самодостаточно, копируется агенту-разработчику как есть)
- PR и ветка, HEAD SHA, что слито и что нет.
- Список исправлений: ID замечания, что сделать, тест, который это докажет (слой по правилу 12).
- Что не менять и что не делать в этом PR (решения владельца, `FOLLOWUP`).
- Формат ответа исполнителя: что изменено, какой тест покрывает, что запущено локально и в CI, новый HEAD; без «Huawei PASS».
```
