# ADR-0036 — M5-A: временный полный кэш текущего трека

Дата: 2026-11-08. Статус: Draft до CI и теста Huawei.

## Контекст
Preview #94 успешно проверена на Huawei, PR #26 принят. M5 требует скачивать текущий трек полностью даже при паузе, затем загружать следующий, использовать локальный seek и удалять временные данные при завершении.

## Выбранное решение
- Использовать официальные Media3 SimpleCache, CacheDataSource и CacheWriter вместо отдельного самописного downloader. Upstream — действующий проверенный HTTPS GMS-free WebDAV DataSource: no redirects, HTTP 206/Content-Range, per-track ETag/size.
- Начать фоновой worker на **текущем** треке при Media3 onMediaItemTransition. Он работает независимо от play/pause. При переключении отменить старый worker. Предзагрузка следующего — только отдельный M5-B.
- Основной playback DataSource читает уже закэшированные сегменты, а отсутствующие — по сети; режим read-only не захватывает cache-hole lock фоновой загрузки и не задерживает первый звук. После полной загрузки новые открытия/seek могут читать локально. Гарантированное переключение уже открытого сетевого соединения посреди трека — отдельное улучшение, не заявлять его здесь.
- App-private cacheDir. Содержимое предыдущей сессии стирать при создании кэша, текущие файлы — после освобождения плеера и worker. Обычная Room и база списка /AllMusic не изменяются.
- Полный фоновый GET только для файлов до 256 МиБ, LRU максимум 512 МиБ, резерв свободного места не менее 128 МиБ. При недоступности места/ошибках продолжать обычный потоковый playback.
- Только SHA-256 от локального ID, размера, ETag в индексе кэша. Не передавать путь, filename, account, пароль или ошибки в публичные логи, телеметрию и GitHub.
- Счётчик прогресса в KiB обновлять локально раз в секунду на открытом экране.

## Ограничения
- Нет prefetch следующего, Wi-Fi only policy, гарантированного бесшовного переключения уже открытого HTTP-потока или доказанного сокращения трафика. Первый background GET параллельно playback может увеличить трафик: измерить на Huawei, не скрывать.
- Не запускать обработку или загрузку всех 3590 файлов. При файлах за пределом бюджета streaming остаётся доступным.

## Проверки
- JVM: TransientCachePolicyTest на размер, резерв места, непрозрачный versioned cache key.
- Android CI на точном HEAD: build/JUnit/lint, Room schemas, строгий GMS-free APK byte scan, Preview identity/signing и артефакт.
- Huawei новой Preview: один раз импортировать только список /AllMusic, включить короткий MP3, после 1–2 секунд нажать паузу и проверить, что число кэшированных KiB продолжает расти до COMPLETE. Продолжить/свернуть, удостовериться в прежнем воспроизведении. Ошибки/числа присылать без названий файлов или пароля. Seek без соответствующей кнопки UI отдельно не считается проверенным.

## Регрессия запуска и корректировка приоритета (Huawei #96)

Пользователь сообщил, что M5-A работает, но первая попытка воспроизведения стала занимать примерно **6 секунд «подключение к треку» + 1 секунду «буферизация»**. Это нежелательная регрессия по отношению к предыдущему ощущению запуска. Причина по одному измерению не доказана. По исходному коду есть проверяемая гипотеза: CacheWriter начинал конкурентный полноценный Range GET прямо из onMediaItemTransition, до того как ExoPlayer успевал получить первый буфер.

Изменение: переход к другому треку отменяет предыдущий запрос и создаёт **отложенное** задание; полнофайловый CacheWriter начинается только после первого `Player.STATE_READY` для выбранного mediaId и 900 мс окна приоритета аудио. При `STATE_BUFFERING` запланированное задание отменяется до повторного READY. Текущий `playWhenReady` / Pause **не участвует** в критерии запуска — когда трек стал READY, фоновая докачка продолжится, даже если пользователь поставил паузу. Во время переключения/остановки отложенный запуск отменяется.

Ожидаемое улучшение первого звука — гипотеза до Huawei; его нужно измерить на том же треке и сети. Возможны другие причины (холодный SimpleCache/Room, WebDAV latency), которые потребуют отдельной диагностики без публикации URL или секретов. Старую успешную #96 не удалять.

## Повторная отрицательная проверка #102; диагностика без догадок
Huawei Preview #102 не устранила задержку: пользователь вновь сообщил долгое подключение и около секунды буферизации. Поэтому выбран **A/B в одной новой Preview**. Контрольный режим cache-off — тот же GMS-free HTTPS Media3 transport без создания disk cache (по умолчанию), эксперимент cache-on — Media3 CacheDataSource + CacheWriter после READY. У обоих одинаковые локальные данные и сеть. Показаны только длительности в миллисекундах между нажатиями и переходами состояний, без URL/пароля/пути/ETag.
Оптимизация вне кэша: все 3590 записей читаются из Room **однократно при открытии экрана**; однократно валидируются пути и строится RAM индекс QueueTrack. На каждое нажатие выполняется только фильтрация уже готовых записей по текущему локальному поиску. Это не меняет WebDAV и не запускает сетевых запросов.
M5-A блокируется до реального A/B: если контрольный режим также медленный, анализировать Media3 timeline и HTTP latency; если только cache-on медленнее, исправлять SimpleCache initialization/read path. Дефолтный режим cache-off защищает быстроту базового воспроизведения до выяснения причины.

## Huawei A/B #111 — 3,3 секунды до начала работы декодера (2026-11-09)
На 3590 записях без кэша: Room 4 мс, playQueue/Media3 3347 мс, BUFFERING 3352 мс, READY 3792 мс, isPlaying 3793 мс. С кэшем: 3 / 3279 / 3284 / 3872 / 3873 мс соответственно. Кэш в этом A/B не объясняет **основную** задержку (разница READY ~80 мс); первая большая задержка уже происходит в синхронном `playQueue`, где было создание всех 3590 MediaSources и `setMediaSources`. Пока не доказано, какая именно часть (валидация/создание/установка/prepare) заняла основное время.

### Безопасный эксперимент очереди
Чтобы не задерживать первый звук из-за всего списка, `StagedPlaylistPlan` создаёт seed из выбранного трека плюс до двух предыдущих и двух следующих элементов. `setMediaSources(seed, selectedSeedIndex, C.TIME_UNSET)` и `prepare/play` стартуют быстро. Только **после первого Media3 READY** native timeline дорастает порциями по 32 элемента через `addMediaSources` (сначала следующие в исходном порядке, затем предыдущие блоками в обратной последовательности добавления, всегда с сохранением правильного порядка внутри каждого блока). Итоговый timeline совпадает с исходным локальным результатом поиска; при stop/новом выборе задачи отменяются. Восстановление полного набора проверяется на 3590 синтетических треках тестом; готовность на Huawei и отсутствие пропусков ещё не доказаны. Кнопки следующего/предыдущего для ближайших соседей доступны с первого seed; далёкие элементы добавляются позже. Во время стадийного заполнения не выполняется ни один новый PROPFIND/GET для *создания* очереди: сеть используется только Media3 для звучащего файла/кэша.

Были добавлены цифровые фазы внутри playQueue без логов/секретов: queue, routes/cache, seed, setSources, prepare/play. «Подготовлено в Media3» показывает число элементов timeline, **не** количество загруженных MP3. Если устранение 3,3 с не произойдёт, эти числа дадут точную точку следующего изменения. PR остаётся Draft до полного CI и реальной проверки.
