# ADR-0026 — Ограниченный RAM LRU для WebDAV Range во время чтения тегов

Дата: 2026-11-08 | Статус: Draft, проверка CI/Huawei требуется

## Реальные результаты M1
- Huawei Preview #45: успешное извлечение title=1, artist=1, album=1 у одного файла, 50 GET, 3 276 800 байт.
- Preview #47: успешная запись в Room, title=1, artist=0, album=0, 39 GET, 2 490 368 байт.
- Preview #49: локальный SELECT агрегатов Room **без сети**: 3590 записей, 1 с сохранёнными тегами, title=1, artist=1, album=1, albumArtist=1. Сам скриншот не подтверждает перезапуск перед проверкой.

Сравнивать #45 и #47 как прямое ускорение нельзя: файлы/условия могут отличаться. По этим результатам нельзя утверждать, что MediaMetadataRetriever возвращается к прошлым блокам, и нельзя предсказать выигрыш LRU на реальном устройстве.

## Изменение
- В WebDavRangeReader заменить один RAM-блок 64 КиБ на **четыре** 64-КиБ блока с LRU по факту последнего обращения, максимум **256 КиБ RAM**.
- Если MediaMetadataRetriever повторно обращается к ранее загруженному блоку, Range GET не выполняется; HTTP, ETag, контроль границ и байтовой длины продолжают действовать для любых новых блоков.
- При вытеснении и `close()` стирать ByteArray с аудиоданными в памяти; не писать эти блоки на диск.
- Счётчики в диагностическом отчёте: число повторных обращений к уже прочитанному **непоследнему** блоку и вытеснений. Без путей, ETag, значений тегов, паролей и сырых заголовков.
- Нет запроса дополнительных байтов по сравнению с 64-КиБ промахом; единица HTTP-запроса не изменилась. Жёсткие лимиты 8 МиБ, 128 GET, 40 секунд, 64-КиБ блока, запрет redirect, точные HTTP 206/Content-Range/If-Range и один файл **не изменены**.

## Риски и границы
- Если извлекатель читает последовательные блоки и к ним не возвращается, LRU **не уменьшит** число запросов.
- RAM может вырасти со 64 до 256 КиБ на одну добровольную однофайловую операцию.
- Нет массовой индексации 3590 файлов, автоматических повторных попыток или расширения срока жизни аудиоданных.
- Количество повторных обращений может быть > 0, но это не значит, что столько же GET реально было бы без LRU: точный эффект зависит от обращения к последнему блоку и размеров чтений; считать только непоследние возвращения.
- Перед массовым чтением нужны измерения на нескольких форматах и сравнение **одного и того же файла**, а не разных результатов Preview.

## Приёмка
MockWebServer: четыре блока, возврат к ранее прочитанному, LRU-вытеснение пятого, отсутствие повторных GET; 40 чередований двух блоков с двумя GET, неизменным пределом байт/запросов, точными байтами. Полный CI Android/JUnit/Lint/Room schema v1/GMS APK/Preview подписанность. Затем новый отдельный Preview на Huawei: импортировать один список, прочитать только один трек и передать обезличенные счётчики GET/байт/повторных RAM обращений/вытеснений. Не делать вывод об ускорении без сопоставимых измерений.
