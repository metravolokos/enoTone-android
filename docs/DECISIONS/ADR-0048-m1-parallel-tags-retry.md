# ADR-0048 — M1: четыре параллельных Range-читателя и повторные попытки

Дата: 2026-11-09. Статус: Draft до exact-HEAD CI и аппаратного теста.

## Основание
По запросу владельца необходимо уйти от последовательного чтения ~3506 оставшихся файлов. Ранний опыт MediaMetadataRetriever (39–50 GET на файл) уже привёл к переходу на быстрый MP3/FLAC-парсер (~1,1 GET на файл по двум реальным пилотам). Параллельная загрузка **предполагалась в первоначальной архитектуре**, но не реализовывалась в безопасных первых пилотах. В #194 23 попытки, 22 успеха, 1 временная ошибка, 26 GET, 1 638 400 байт: вся сессия остановилась с RETRY_BACKOFF, хотя единичный сетевой сбой не доказывает недоступность остальных файлов.

## Решение в первом проверяемом срезе
- В **управляемой foreground-службе** четыре `Dispatchers.IO` worker читают четыре разных файла параллельно. Внутри каждого файла HTTP Range-запросы последовательны, размер блока 64 КиБ, максимум 6 GET/384 КиБ на одну попытку. Старые отдельные пилоты 10/20/100 остаются последовательными и неизменными.
- У всех worker один `SharedRangeBudget` с атомарным резервированием перед открытием каждого GET. Лимит **60 GET и 4 МиБ на порцию**, общая сессия до четырёх порций (240 GET/16 МиБ), мягкая граница ~180 с на порцию, пауза 1,5 с между порциями — **без увеличения нагрузки по количеству запросов** по сравнению с #194. Неполученный ответ всё равно потребляет резерв: сервер уже мог обработать запрос.
- Временные сетевые ошибки (`RETRY_NETWORK`, `RETRY_HTTP`) получают максимум **две дополнительные попытки на том же файле** с задержками 1 и 3 с. Для HTTP 429 — 8 и 16 с, с общим охлаждением перед стартом новых попыток. Не игнорировать HTTP 429 и не делать мгновенный повтор. HTTP 401/403 — немедленная остановка всей порции без автоподбора credentials.
- После исчерпания попыток сохраняем `RETRY_*` в Room и **продолжаем** работу с остальными, не перечитывая успехи. Только 4 подряд финальных временных сбоя либо 2 финальных 429 останавливают порцию с `RETRY_BACKOFF`; это признак возможного общего отказа сервера. Неподдерживаемые форматы и ошибки структуры тегов не превращать в бесконечный retry.
- Пишем результат каждого файла через старый `recordFastScanIfUnchanged` с ETag, размером, modified и source key. Не меняем Room schema, парсер, сертификат Stable Preview, Media3, никакого PROPFIND для продолжения и без ограничений Wi-Fi. Данные для UI: только числа и фиксированные коды стадии/причины/HTTP.
- Обработка в фоне остаётся прямой `dataSync` foreground-службой (ADR-0047), только после явного нажатия; не обещаем автоматический перезапуск после убийства процесса. Без GMS и секретов в уведомлении.

## Производительность и критерии
3506 оставшихся файлов при 26 GET/23 файла и 60 GET/52 файла дают порядка 4 000 GET. При 4 параллельных HTTP-запросах, если средний запрос занимает 1 с, чистое сетевое время порядка 17 мин **вместо 67 мин**, без учёта CPU, записей, пауз, ограничений сервера и повторов. Это гипотеза, а не замер Huawei. Реальное ускорение может быть меньше из-за Cloud.Mail.ru, LTE/5G, TLS или системных лимитов.
- JUnit / mock: одновременный старт на разных файлах, общий счётчик запросов/байтов при конкуренции, 429/503/timeout, ограниченные retry, единичный сбой не останавливает остальные, каскад 401/403 останавливает, cancel/resume не теряет Room, список 3590.
- CI exact HEAD: Android/Lint/JUnit, безопасность Range/ETag/URL, GMS gate, схема Room и APK. Только затем merge в main и подписанная Stable Preview с тем же packageId/подписью.
- На Huawei сперва ограниченный запуск ≤240 GET, проверить параллельные счётчики и число сохранённых; затем свёрнутый экран, пауза/резюмирование, не удалять текущую Room. Никаких личных названий, URL или паролей в GitHub.
- **Массовая индексация всех 3506 за одно нажатие** и автоматическая стратегия после системных time budgets — отдельный этап после аппаратной приёмки параллельного среза: нельзя расширять количество запросов и покрытие одновременно, пока неизвестна устойчивость сервера.
