# ADR-0094: Старт воспроизведения — кэш вне главного потока и без права на отказ

**Дата:** 2026-11-15
**Статус:** принято в PR задачи `BUG-playback-cache-startup` (#159)
**Связано:** ADR-0074 (M6-0), ADR-0075 (очередь), аудит [AUDIT_2026-11-14](../audit/AUDIT_2026-11-14_main-2761ae9.md) находки A-13, A-14, A-15

## Контекст

Три находки аудита оказались одной проблемой — тем, что происходит при старте
воспроизведения и при завершении службы.

`TransientMediaCache` в конструкторе удаляет каталог кэша, создаёт его заново и
открывает `SimpleCache` с `StandaloneDatabaseProvider`. Каталог по политике
может занимать до 512 МиБ, то есть удаление — это тысячи файлов. Вызывался
конструктор из `playQueue` и `restoreQueue`, обе приходят с главного потока
через binder: холодный старт воспроизведения после перезапуска службы давал
фриз и риск ANR.

Любая из этих операций может упасть: каталог не удаляется, хранилище заполнено,
БД занята. Конструктор бросал `IllegalStateException`, вызывающий код его не
перехватывал — приложение показывало «Ошибка… код 0» и музыки не было вообще,
хотя потоковый режим (`useTemporaryCache = false`) полностью поддержан.

Отдельно: `onDestroy` вызывал `io.shutdown()`, но `handler` продолжал жить.
Отложенный `savePosition` (до 12 с) срабатывал после закрытия исполнителя и
вызывал `io.execute` без `try/catch` → `RejectedExecutionException` на главном
потоке → краш при закрытии. Если на момент `onDestroy` стоял
`layoutWritePending`, финальная позиция не сохранялась вовсе.

## Варианты

### A. Ждать готовности кэша перед стартом

`playQueue` запускает создание кэша, дожидается результата и только потом
готовит источники.

**Плюсы:** кэш гарантированно используется с первого трека.
**Минусы:** лечим ANR ценой задержки первого звука — ровно наоборот к цели
«мгновенный старт». Удаление 512 МиБ на медленном хранилище даст паузу в
секунды перед первым звуком.

### B. Готовить кэш в фоне при старте службы; играть без него, если не готов (принято)

`prepareTransientCache()` вызывается в `onCreate` службы на отдельном потоке.
`playQueue`/`restoreQueue` берут **готовый** кэш; если его нет — играют через
сеть и запускают подготовку для следующей очереди.

**Плюсы:** первый звук никогда не ждёт кэш; ANR устранён; сбой кэша — деградация
качества (сеть вместо диска), а не отсутствие музыки.
**Минусы:** первая очередь после запуска службы может играть без кэша, то есть
предзагрузка следующего трека начнётся со второй очереди.

### C. Ленивая инициализация при первом обращении

Кэш создаётся по первому требованию, но на `Dispatchers.IO`.

**Плюсы:** не создаётся, если не нужен.
**Минусы:** ровно то же ожидание первого звука, что в варианте A, только
замаскированное. Плюс сложнее гарантировать единственность экземпляра.

## Решение

Принят **вариант B**.

- `prepareTransientCache()` вызывается в `EnoTonePlaybackService.onCreate`,
  работает на отдельном потоке, ставит результат обратно на main через
  `cacheHandler`.
- `createTransientCacheSafely(context)` **никогда не бросает**: возвращает
  `Decision.UseCache(cache)` либо `Decision.PlayWithoutCache(reason)` с кодом
  `TransientCacheFailure` (`RESET_FAILED`, `DIRECTORY_UNAVAILABLE`, `OPEN_FAILED`).
  Текст исключения наружу не идёт — он содержит путь к приватному каталогу.
- `playQueue`/`restoreQueue` используют `temporaryCache`, только если он уже
  готов; иначе строят источник от `WebDavMedia3DataSource` напрямую.
- Режим кэша фиксируется **один раз** при сборке очереди:
  `CacheModeDecision.cacheEnabledForQueue(requested, cacheAvailable)`.
  `cacheEnabledForQueue`, `activeRoutes` и `upstreamFactory` включаются только
  при `useTemporaryCache && кэш готов`. До этого исправления флаг и маршруты
  выставлялись по одному `useTemporaryCache`: если кэш ещё не был готов, очередь
  всё равно считала кэш включённым, предзагрузка запускалась позже и скачивала
  трек повторно — при том что плеер этой очереди кэш не читал. То есть дефект был
  не в «молча ничего не делала», а в двойной загрузке.
- Если служба закрылась, пока кэш открывался, он сразу закрывается (`closed`).

Для A-15: флаг `destroyed` и единая функция `submitIo` с перехватом
`RejectedExecutionException`. `onDestroy` **не** сбрасывает `layoutWritePending`:
если запись структуры ещё ожидает, финальная позиция уже входит в пару
layout+position, и `savePosition` выходит по этому флагу сам. Сброс флага (первая
редакция этого ADR) ставил отдельную запись позиции прежней ревизии поверх новой
структуры — пара ломалась, и `read()` откатывался на предыдущую очередь, стирая
только что включённую. Исправлено по ревью PR #160.

## Обоснование

Вариант A и C переносят стоимость с UI-потока на первый звук, но не устраняют
её: пользователь всё равно ждёт. Вариант B убирает ожидание из критического
пути полностью и делает сбой кэша нефатальным — что и было второй половиной
находки. Кэш существует ради трафика и плавности последующих переходов, а не
ради первого трека, поэтому его отсутствие на старте — приемлемая деградация.

## Последствия

- Главный поток не выполняет файловых операций и не открывает SQLite при
  старте воспроизведения.
- Сбой кэша не лишает музыки: очередь играет через сеть. Код причины
  (`TransientCacheFailure`) сохраняется в `PreviewAudioPlayback` и пока **не**
  выводится в «Диагностику» — это отдельная задача.
- Краш при закрытии службы устранён. При ожидающей записи структуры финальная
  позиция не пишется отдельно: она уже в паре, а лишняя запись ломала пару.
- **Технический долг:** первая очередь после запуска службы может играть без
  кэша. Если это станет заметным на устройстве, правильное решение — прогрев
  при входе в приложение, а не ожидание в `playQueue`. Зафиксировано в
  KNOWN_ISSUES с условием пересмотра (после замера на Huawei).
- Политика `MAX_DISK_BYTES`, LRU и отсутствие закрепления current/next не
  менялись — это отдельные решения (R-6.5b).

## Как проверить

1. `TransientCacheFactoryTest` — коды отказов различимы и не содержат
   файловых деталей.
2. `:playback:testDebugUnitTest` и `:app:testDebugUnitTest` — `PLAY-01`,
   `PLAY-02`, `PLAY-07`, `PLAY-08`, `REST-01`…`REST-04` не регрессируют;
   `QueueEditServiceTest` подтверждает, что служба закрывается без исключений.
3. Устройство (после merge, отдельным подтверждением владельца): холодный старт
   воспроизведения после перезапуска службы — без заметной паузы и без ANR;
   старт при заполненном хранилище — играет через сеть.
