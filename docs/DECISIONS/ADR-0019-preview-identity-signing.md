# ADR-0019 — Изоляция диагностических APK при потере исходного debug-ключа

Дата: 2026-11-08. Статус: корректировка после отказа установки Huawei.

## Факт и причина

Владелец получил при установке APK из успешного CI #33 сообщение Android/Huawei «Подпись пакета и установленного приложения не совпадают». Проверка проекта выявила стандартную debug-подпись, создаваемую SDK отдельно на каждом временном GitHub Actions runner, без сохранённого keystore. Это объясняет несовместимость сертификатов.

Установленное приложение с applicationId `app.enotone.android` содержит локальную приватную Room медиатеку с 3590 файлами. Не удалять приложение, не очищать данные, не рекомендовать повторную установку поверх без оригинального подписывающего ключа. APK нельзя корректно «переподписать для обновления», если закрытого ключа прежней подписи нет.

## Немедленное решение

- Для CI `debug` использовать динамический `applicationIdSuffix = ".preview.r<run_number>"`, отдельный пакет наподобие `app.enotone.android.preview.r36` и имя `enoTone Preview #36`. Благодаря этому каждый новый CI APK можно установить независимо от других сгенерированных debug-подписей; никаких обновлений чужим ключом.
- APK можно установить **параллельно** со старым `app.enotone.android`; старая Room остаётся недоступной для нового пакета и не затрагивается.
- CI обязана проверить точный пакет с номером текущего запуска по Android AAPT, отображаемую метку и действительную APK подпись. Артефакт называется `enotone-preview-debug-apk`, чтобы пользователь не путал его с обновлением основного приложения.
- На Preview необходимо **один раз заново получить список /AllMusic через WebDAV**: новый пакет не имеет доступа к приватной БД старого. Аудиофайлы целиком при обычном импорте списка не скачиваются.
- Пока нет стабильного ключа, каждый новый preview run **отдельное приложение с собственной пустой Room**. Это предсказуемое, но неудобное ограничение; устройство может накопить тестовые установки. Не объявлять динамические preview сборки полноценно обновляемыми.

## Последующее обязательное исправление

Нужен отдельный долгосрочный закрытый signing key с сохранением **в GitHub Actions Secrets**, не в публичном репозитории и не в открытых артефактах. Подписывать им один постоянный ID для будущих обновлений, проверять сертификат и монотонно увеличивать versionCode. Из-за отсутствия действия записи GitHub Secrets в текущем коннекторе ключ не настраивается автоматически — нельзя объявлять подписи стабильными до реального provisioning.

Старый debug-приложение можно оставить как резерв данных. Восстановление Room из него требует отдельной явной процедуры переноса данных по ADB с правами доступа, а не простого совпадения имени пакета.

## Не выбранные альтернативы

- **Удалить старое приложение** — отказ: рискуем потерять подтверждённую локальную медиатеку.
- **Залить открытый debug.keystore в публичный Git** — отказ: любой сможет подписать вредоносную подмену программы с доступом к учётным данным пользователя.
- **Отключить проверку подписи Android** — невозможно и небезопасно.
- **Повторять старый ID с новыми ключами** — приведёт к тому же сбою.

## Приёмка

На GitHub Actions проверить Android build, JUnit, lint, Room schema v1, GMS scan, AAPT package ID `app.enotone.android.preview.r<run_number>`, соответствующую метку и APK signing verification. На Huawei установить Preview рядом с оригинальным enoTone; убедиться, что оба приложения присутствуют и прежний каталог не затронут. После явного импорта списка в Preview можно выполнить диагностику тегов **одного** файла.
