# ADR-0029: диагностика и классификация ошибок ручного пилота M1

Дата: 2026-11-08. Статус: предложено; реализация в Draft PR #20, issue #19.

## Контекст

На Huawei Preview r59 при ручном пилоте один файл дал ошибку. Локальный счётчик «9 завершено, 3581 ждут проверки или повтора» не позволял отделить ошибочный файл от ещё не проверенных. Прежний catch относил практически любой сбой к `RETRY_NETWORK`, включая постоянные ошибки HTTP и парсера; повторные ручные запуски могли опрашивать такой файл снова.

Медиатека плоская, 3590 файлов в `/AllMusic`; нельзя запускать массовое чтение ради диагностики.

## Решение

- На устройстве показывать только безопасные коды этапа `RANGE` / `PARSER`, тип `RangeReadIssue` либо `PARSER_FAILURE` и числовой HTTP-статус. Исключения, URL, имена файлов, ETag, учётные данные, содержимое тегов не логировать и не публиковать.
- HTTP 408/425/429/5xx, транспортные сбои, короткое тело и смена ETag — `RETRY_*`: возвращаются в конец следующего **ручного** пилота, после новых файлов.
- HTTP 401/403 останавливает пилот без записи кода неисправности трека.
- HTTP 4xx (кроме временных/авторизации), неверные Range-заголовки, превышение лимита и исключения парсера — `FAILED_*`: файл не повторяется автоматически. После нового успешного PROPFIND смена версии сбрасывает checkpoint.
- Локальная офлайн-диагностика отдельно считает завершённые, временные ошибки, постоянные ошибки и ещё не проверенные записи. Ответы быстрого парсера `INVALID_METADATA`/`FAST_BUDGET_EXCEEDED` считаются постоянными ошибками даже при старых checkpoint из r59; пустые или неподдерживаемые теги остаются завершённой проверкой без тегов. Room v2 не меняется.
- Пилот только вручную, 10/20 файлов; общие 30/60 GET и 2,5/4 МиБ не увеличивать. Никакой автоматической очереди повторов, таймеров и фоновых сетевых запросов.

## Альтернативы

1. Повторять каждый сбой — исключено: постоянная неисправность файла вызывает бесконечные повторные запросы при ручных запусках.
2. Писать полный exception/path в лог или публичный issue — исключено: риск утечки пользовательских данных.
3. Добавить Room v3 с retry counter/backoff — отложено: нет автоматических повторов, новая миграция ради одноразовой диагностики не оправдана.

## Проверка

Синтетические JUnit для HTTP 401/403, 404, 408/429/503, BAD_CONTENT_RANGE, NETWORK, PARSER_FAILURE, пропуска девяти успешных и одной постоянной ошибки; проверка Room SQL через KSP/Gradle и GMS-free APK gate. После зелёного CI — ограниченный ручной пилот на Huawei в **той же** Preview для достоверной проверки checkpoint. Новая Preview с отдельным applicationId имеет собственную БД.

## Ограничения

Это не доказательство исправления конкретного реального файла: причина инцидента пока неизвестна. Persistent автоматические повторы, инструментальная миграция Room v1→v2 и стабильная подпись Preview остаются отдельными работами.
