# ADR-0091: Атомарная замена файлов состояния — `Files.move` вместо `File.renameTo`

**Дата:** 2026-11-15
**Статус:** принято в PR волны 1 (внешний аудит 2026-11-14, находка A-01)
**Связано:** ADR-0075 (сохранение очереди), ADR-0067 (постоянные обложки), ADR-0080 (выход из аккаунта), аудит [AUDIT_2026-11-14](../audit/AUDIT_2026-11-14_main-2761ae9.md)

## Контекст

Три места приложения пишут состояние через временный файл и переименование:
`QueueStateFileStore` (чекпоинт очереди), `AccountArtworkFileCleanup`
(манифест выхода) и `ArtworkPreviewRepository` (мастер-обложка). Все три
использовали `java.io.File.renameTo`.

`File.renameTo` не перезаписывает существующий целевой файл на Windows и
возвращает `false`. Проверено изолированно: переименование на несуществующую
цель — `true`, на существующую — `false`. На Android (Linux) перезапись
происходит, поэтому дефект не проявлялся на устройстве и не виден в CI
(`ubuntu-latest`).

Последствия к моменту аудита:

- второй чекпоинт очереди бросал `IOException`, откатываясь к предыдущей паре —
  три JVM-теста падали на Windows, локальная проверка изменений была невозможна;
- `AccountArtworkFileCleanup.save` бросал исключение — выход из аккаунта на
  Windows не завершался;
- `ArtworkPreviewRepository.atomicWrite` возвращал `false` **молча**: обложка не
  сохранялась без единого сигнала в UI и в диагностику.

## Варианты

### Вариант A — общий помощник на `Files.move` (принято)

Один объект `AtomicFileReplace` с `Files.move(REPLACE_EXISTING, ATOMIC_MOVE)` и
откатом на `REPLACE_EXISTING` по `AtomicMoveNotSupportedException`.

**Плюсы:** одинаковый контракт во всех трёх местах; атомарность сохраняется там,
где ФС её поддерживает; откат покрывает старые/vendor-ФС Android;
`false` вместо исключения позволяет и бросать наверх (`QueueStateFileStore`,
манифест), и молча деградировать (обложки) — как и требовалось.
**Минусы:** новый общий класс в `:playback`, хотя обложки и выход живут в `:app`.

### Вариант B — `Files.move` в каждом месте отдельно

**Плюсы:** нет нового общего класса, нет вопроса о размещении.
**Минусы:** три копии одного и того же отката и обработки исключений; при
следующем изменении контракта (например, `fsync` каталога) правка снова
троекратная; именно копирование уже привело к тому, что в одном месте результат
проверялся, а в другом — нет.

### Вариант C — отдельный модуль `:core:io`

**Плюсы:** «правильное» место для общего файлового помощника.
**Минусы:** нарушает `AGENTS §4` — новый модуль только через ADR с решением
владельца и требует перечислить два уже сделанных PR, которым эта граница
помогла бы. Для десяти строк кода такой границы нет.

## Решение

Принят **вариант A**. Класс размещён в `:playback`, потому что `:app` уже от него
зависит — новых рёбер в графе модулей не появляется, а чекпоинт очереди был
исторически первым местом с этим контрактом. Переезд в `:core:*` возможен
отдельным ADR, если появится третий потребитель вне `:app`/`:playback`.

`ArtworkPreviewRepository.atomicWrite` теперь возвращает результат замены, а не
результат `renameTo`; вызывающий код сохраняет прежнее поведение (тихий пропуск
записи), но получает правдивое значение.

## Последствия

- Три падавших на Windows теста проходят; локальная проверка PR снова возможна.
- На Android поведение не меняется: `ATOMIC_MOVE` поддерживается, откат не
  срабатывает.
- Тест на откат не добавлялся: воспроизвести `AtomicMoveNotSupportedException`
  в JVM-тесте нельзя без подмены ФС, а строковая проверка исходников запрещена
  (`AGENTS §4`).
- Остаётся технический долг: `AtomicFileReplace` не делает `fsync` каталога
  после переименования. Для чекпоинта очереди это компенсируется `fd.sync()`
  временного файла; отдельное усиление — при следующем изменении.

## Как проверить

1. `gradlew testDebugUnitTest` на Windows: `QueueStateFileStoreTest` (6 тестов)
   и `QueueEditServiceTest` (2 теста) проходят.
2. `gradlew :app:assembleDebug` — компиляция трёх вызывающих мест.
3. На устройстве: сохранить очередь дважды (переключить трек два раза),
   выйти из аккаунта и вернуться — данные на месте.
