# ADR-0104 — Приёмка по автоматическим проверкам вместо проверки на устройстве

**Дата:** 2026-11-21. **Статус:** принято решением владельца 2026-11-21.
**Риск:** M — меняет модель приёмки и статусы сценариев, но не код, не данные
и не сетевой слой. **Связано:** AGENTS.md §4, `docs/WORKFLOW.md` §1/§2/§3/§6,
`docs/SCENARIOS.md`, `docs/TESTING.md`, `docs/AUDIT_PROTOCOL.md`, Issue #240.

## Контекст

Действовавшая модель требовала отдельного подтверждения владельца для каждого
сценария на устройстве: `AGENTS.md` §4 запрещал отмечать проверку на устройстве
пройденной без его сообщения, `WORKFLOW` §1 объявлял Huawei PASS единственным
источником результата, а `SCENARIOS.md` — единственным местом его записи. Из 107
сценариев 84 требовали ручной проверки на телефоне.

На практике это перестало работать по трём причинам:

1. **Владелец проверяет периодически, а не после каждого merge.** Сценарии
   накапливались в статусе «ожидает Huawei», хотя фактически были приняты: PR
   слит, CI зелёный, ревью пройдено.
2. **Статусы расходились с реальностью.** На 2026-11-21 в `SCENARIOS.md` пять
   записей содержали «Draft #N» для PR, слитых неделю назад (#133, #149), и
   восемь — «ожидает CI» после зелёного CI. Дашборд состояния честно показывал
   это как «ждёт слияния», создавая ложную картину незавершённой работы.
3. **Владелец сформулировал иную модель:** «если прошли все тесты и ревью, то
   вопросов нет, а когда появятся вопросы — я сообщу». Глюки, найденные на
   устройстве, становятся отдельными задачами, а не блокируют приёмку.

## Варианты

1. **Оставить прежнюю модель.** Плюсы: максимальная осторожность, ни один
   сценарий не считается принятым без физической проверки. Минусы: статусы
   продолжают расходиться с фактами; приёмка отстаёт от разработки на недели;
   владелец фактически не может принять накопленное; при найденном глюке
   неясно, к какому уже слитому PR он относится. **Отклонено.**

2. **Отменить проверку на устройстве полностью и не вести её.** Плюсы: простая
   модель. Минусы: теряется возможность поймать дефекты, которые автотесты не
   видят (аппаратные особенности, реальный WebDAV, реальные аудиокодеки).
   Владелец прямо сказал, что будет сообщать о найденных глюках, — значит
   обратная связь сохраняется, но её нельзя записывать в сценарии, поскольку
   она приходит вне плановых проверок. **Отклонено.**

3. **Приёмка по автоматическим проверкам, ручная проверка — вне планового
   процесса** (выбрано). Сценарий считается **принятым**, когда выполнены все
   автоматические условия: PR слит в `main`, CI на точном HEAD зелёный
   (сборка, JUnit, lint, Room schema, GMS scan, detekt, Roborazzi), независимое
   ревью пройдено. Отдельный статус «проверено на телефоне» **исключается** как
   плановая стадия. Найденный на устройстве глюк заводится отдельной задачей и
   исправляется обычным порядком.

## Решение

1. **Единственный итоговый статус приёмки — «принято по автоматическим
   проверкам».** Он означает: код в `main`, CI точного HEAD зелёный, ревью
   пройдено. Других статусов приёмки нет.

2. **Плановая проверка на устройстве исключается.** Из процесса удаляются:
   статус `state:device-test`, требование «Huawei PASS» как условие закрытия
   Issue, шаблон отчёта владельца по сценариям, графа «Проверено на телефоне» в
   `SCENARIOS.md`. Статус `H` в колонке «Проверка» перестаёт быть обязательной
   стадией и не записывается в «Последний результат».

3. **Обратная связь с устройства не отменяется, но меняет форму.** Если владелец
   находит дефект, он сообщает о нём: заводится Issue с меткой `bug` и обычным
   приоритетом, исправление идёт по общему процессу. Запись такого дефекта —
   не «PASS», а отдельная задача со ссылкой на затронутые сценарии.

4. **Доступ к устройству остаётся инструментом разработки, а не стадией
   приёмки.** Когда телефон подключён по ADB, исполнитель может установить
   подписанную Stable Preview, запустить приложение, снять скриншоты, собрать
   logcat и проверить конкретное поведение — это ускоряет диагностику, но не
   создаёт отдельного статуса.

5. **Существующие записи приводятся в соответствие.** Для сценариев, чьи PR уже
   слиты и чей CI зелёный, «Последний результат» переписывается на «принято по
   автоматическим проверкам» с указанием PR и прогона CI. Для сценариев с
   записями «ожидает Huawei» без слитого кода статус меняется на «в работе» либо
   «нет данных» — по факту, а не по прежней шкале.

## Обоснование

- Владелец — единственный пользователь продукта и единственный, кто платит за
  задержку приёмки. Его модель («принято, пока не сообщил о глюке») снимает
  необходимость формального PASS по каждому пункту.
- Автоматические гейты уже покрывают то, что раньше проверялось руками: 376
  JUnit/Robolectric-тестов, Roborazzi-эталоны обеих тем, Room schema v1–v7,
  GMS-free APK, detekt с базовой линией. Реальный риск плановой ручной проверки
  для офлайн-плеера — аппаратные особенности, которые дешевле ловить по факту
  жалобы, чем регрессионным прогоном 84 сценариев.
- Смена модели снимает корень расхождений: статус перестаёт зависеть от
  действия, которое выполняется по желанию и с произвольной задержкой.

## Последствия

- `AGENTS.md` §4: правило «не отмечать проверку на устройстве без сообщения
  владельца» заменяется правилом о приёмке по автоматическим проверкам.
- `WORKFLOW` §1/§2/§3/§6: Huawei PASS как источник результата и
  `state:device-test` как состояние задачи удаляются; закрытие Issue происходит
  после merge и полного исполнения критериев.
- `SCENARIOS.md`: графа «Последний результат» получает значения «принято по
  автоматическим проверкам»; легенда переписывается; записи приводятся в
  соответствие; `Треб.`/`Проверка` сохраняют букву `H` как историческую
  информацию о том, что сценарий допускает ручную проверку, но она не
  обязательна.
- `TESTING.md`: раздел «Ручная проверка на Huawei» заменяется разделом
  «Проверка на устройстве как инструмент диагностики»; шаблон отчёта владельца
  удаляется.
- `AUDIT_PROTOCOL` и `REVIEW_REPORT_TEMPLATE`: упоминания обязательного
  Huawei PASS как условия merge удаляются.
- Метки GitHub: `state:device-test` больше не используется; существующие Issue с
  этой меткой требуется перевести в `state:review` или закрыть.
- Риск: дефекты, видимые только на устройстве, будут обнаружены позже — по
  сообщению владельца. Это принятая цена, а не недосмотр.

## Как проверить

1. `docs/SCENARIOS.md` не содержит обязательных стадий ручной проверки; легенда
   описывает единственный статус приёмки.
2. `AGENTS.md`, `WORKFLOW`, `TESTING`, `AUDIT_PROTOCOL`, `REVIEW_REPORT_TEMPLATE`
   не требуют Huawei PASS и не содержат `state:device-test`.
3. Ни один действующий документ не описывает шаблон отчёта владельца по
   сценариям.
4. `python -m unittest discover -s tools -p 'test_*.py'` зелёный; CI на точном
   HEAD зелёный.
5. Открытых Issue с меткой `state:device-test` нет.

## Когда пересмотреть

- Если на устройстве проявятся дефекты, которые автотесты систематически не
  ловят (аппаратный WebDAV, кодеки, работа службы в фоне), — вернуть
  ограниченный набор регрессионных сценариев как отдельный процесс.
- Если появится второй пользователь или публичная публикация — вернуть
  формальную приёмку до релиза.
