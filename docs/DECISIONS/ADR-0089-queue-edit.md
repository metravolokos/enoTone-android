# ADR-0089 — Ручная правка очереди Media3 (M6-0/8a)

**Дата:** 2026-11-14  
**Статус:** Предложено в Draft PR M6-0/8a; правила по умолчанию требуют подтверждения владельца  
**Связано:** ADR-0075, ADR-0086, M6-0/3, M6-0/8b

## Контекст

Контекстная очередь запускается через `PreviewAudioPlayback.playQueue` и по частям заполняет реальный Media3 timeline (`StagedPlaylistPlan`). Перемешивание хранит полную стабильную перестановку; текущая позиция и структура очереди сохраняются отдельно по ADR-0075. Изменение списка только в UI или замена через `setMediaSources` прервали бы воспроизведение и нарушили восстановление. Значки и точки вызова в UI развиваются параллельно в D4a; 8a не меняет экраны.

## Варианты

1. **Полностью пересоздавать очередь `setMediaSources`.** Плюсы: простой расчёт списка, одинаковый путь для play/restore/edit. Минусы: пересоздание текущего MediaPeriod, риск слышимой паузы/повторных WebDAV GET, потеря положения при shuffle. **Отклонено**.
2. **Менять Media3 timeline на месте, стабильный `ShuffleOrder`, отдельный чистый планировщик.** Плюсы: текущий источник и позиция сохраняются, штатные команды MediaSession/гарнитуры сразу используют новый следующий трек, модель покрывается JVM-тестами. Минусы: нужно обновлять все кэши и полную перестановку; незавершённый staged timeline приходится согласовывать. **Выбрано**.
3. **Копить правки до завершения асинхронного наполнения.** Плюс: не блокирует главный поток при больших очередях. Минусы: отложенная видимость результата, более сложные события и отмена при повторном нажатии. **Отложено** как возможное улучшение после измерений Huawei.

## Решение и правила

- `QueueEditPlanner` принимает физический порядок ID, перестановку shuffle, текущий ID, `PlayNext(ids)` или `Append(ids)`; возвращает целевую раскладку, набор перенесённых ID и результат. Вне Android, сети и Media3.
- Пустая очередь: обе команды запускают выбранные треки как новую очередь через `LibraryViewModel` и `PlaybackConnection.playQueue`, поскольку остановленная служба не имеет учётных данных; в сохранённой очереди вызов `EnoTonePlaybackService.insertNext/append` меняет её на месте.
- «Играть следующей»: выбранные ID подряд непосредственно за текущим **в порядке воспроизведения**, а не за физическим индексом shuffle. «В конец»: за последним в этом порядке. Новые ID при shuffle добавляются физически в конец и включаются в явно рассчитанную перестановку — случайного перемешивания уже запланированных треков нет.
- Дубликат существующего ID переносится, не копируется. Текущий ID всегда исключается из переноса; если выбран только он — `ALREADY_PLAYING`. Несколько выбранных ID сохраняют порядок и дедуплицируются.
- Предел 10 000 (`PlaybackQueue.MAX_TRACKS`). Уже существующие ID можно перемещать при заполненной очереди. Лишние новые не добавляются, возвращается `QUEUE_FULL` с количеством реально обработанных.
- Repeat, позиция текущего трека, `playWhenReady` и текущий MediaPeriod не меняются. Обычная очередь использует `moveMediaItem`/`addMediaSources`; при shuffle физические старые элементы остаются на местах, после вставок устанавливается точная `DefaultShuffleOrder`.
- Для правки в ходе staged наполнения **принудительно завершаем только локальное построение всех MediaSource**, не выполняя WebDAV GET, затем меняем очередь. Это исключает позднюю дозапись устаревших частей. Цена — возможная разовая задержка главного потока на большом списке; измерить на Huawei 3590/10000 и при необходимости заменить на вариант 3.
- `WebDavMedia3DataSource.Factory` хранит общий потокобезопасный набор маршрутов; новые треки добавляются с собственными size/ETag. Обновляются `activeRoutes`, `mediaIdIndices`, `originalTrackIds`, `expectedQueueSize`, `configuredShuffle`. Предыдущая `TransientMediaCache` предзагрузка следующего отменяется; новая выбирается по Media3.
- После успешной правки вызывается `writeLayoutAndPosition` с новой случайной `queueRevision`. `sourceKey` получает вид `edited:<account-hash>` (никаких адресов или путей); сверка источника при восстановлении и сохранении длительности принимает исходный хэш и этот маркер. Версия JSON **не меняется**, прежние сохранённые файлы читаются, проверка whitelist сохраняется. Прежняя структура защищает от оборванной двухфайловой записи.
- `LibraryViewModel` экспонирует `onPlayNext(tracks)`, `onAppendToQueue(tracks)` и `queueMessages` (`SharedFlow`) для Snackbar в 8b. До 8b никакие меню, Snackbar и экраны не добавляются. Служебные значки `playlist_play` / `playlist_add` — два vector drawable в `:core:ui`, регистрация в `EnoIcons`; для `enotone-design` предложено затем дополнить `tools/build_ui_icons.py` без изменения текущего дизайн-репозитория.

## Последствия

Дополнительных модулей, зависимостей, миграций Room и сетевых запросов ради правки нет. Данные очереди остаются только хэшами. При убийстве процесса возможна прежняя целая ревизия, если новая ещё не успела записаться, но не смешанная структура. Пользовательский UI будет добавлен после слияния D4a и 8a в 8b.

## Как проверить

- JVM: одна/несколько песен, shuffle, перенос дубликата, текущая песня, пустая очередь, переполнение 10 000, старый `sourceKey`, round trip JSON.
- Robolectric: восстановленная служба, вставка, штатный `seekToNextMediaItem`, следующая ревизия, пересоздание службы, сохранение repeat-one.
- CI точного HEAD: Gradle build/JUnit/lint/detekt; PLAY-01/02/07, REST-01/04 не регрессируют.
- Huawei только после 8b: QED-01…QED-06; звук без паузы, shuffle и repeat, гарнитура/уведомление, staged 3590, восстановление после закрытия; обе темы. Не считать пройденным без отчёта владельца.
