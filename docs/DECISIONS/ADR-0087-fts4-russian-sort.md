# ADR-0087 — Поиск FTS4 и русская сортировка

Дата: 2026-11-14 | Статус: предложено в Draft PR M6-0/7; ревью Claude и решение владельца необходимы.

## Контекст

В текущем каталоге поиск треков — поиск подстроки в памяти; буквы ё и е отличаются.
Сортировка по Unicode-кодам даёт неудобный порядок русских названий.
Room v5 уже содержит длительность и плейлисты. Переход обязан сохранить все
данные существующей Stable Preview, обложки и очередь. Каркас D3 не менять.

## Варианты и выбор

**Поиск**: (А) нормализованный поиск в памяти, без миграции, но линейный на
каждый ввод; (Б) FTS4 unicode61 с перестраиваемым производным индексом,
быстрый поиск по началу слов и AND. Выбрано Б.

**Хранение**: (А) внешняя content-sync FTS + SQL-триггеры — меньше повторения,
но SQL не воспроизводит Kotlin-нормализацию ё/е и й/и; (Б) самостоятельная
таблица track_search с локальным обновлением и восстановлением из Room.
Выбрано Б. TrackId и sourceKey не индексируются токенизатором; текст включает
title, artist, album, albumArtist, genre, fileName без расширения.
Нормализованный индекс не источник истины: при первом чтении после миграции
создаётся из уже сохранённых тегов без сети, а последующие чтения сверяют
актуальность; явные обновления выполняются при импорте и записи тегов.
Запросы и приватные строки не логируются.

**Collator**: (А) java.text.Collator (ru, SECONDARY), доступный JVM и Android,
без новых библиотек; (Б) android.icu.Collator, привязанный к Android и плохо
подходящий для существующих чистых JVM-тестов. Выбрано А, с ThreadLocal,
поскольку Collator не потокобезопасен.

## Семантика

- LibraryText.searchKey: NFC → NFD, убрать комбинирующие диакритические знаки,
  но восстановить «й» из «и + U+0306»; ё → е, é → e, lowercase ru,
  схлопнуть пробелы. Й и и не отождествлять.
- FTS4: пользовательские слова становятся параметризованными безопасными
  выражениями вида "слово*" с AND; OR, NEAR, дефисы, кавычки и звёздочки
  не становятся операторами.
- Изменение с подстроки на начало слова: «ми» находит «Мираж», «ираж» — нет.
  Пустой запрос — без FTS; поиск по группам остаётся в памяти.
- Порядок треков/альбомов/исполнителей — ru Collator с последним стабильным
  ключом id/key. Ведущее The с пробелом не учитывается при сравнении
  артистов и авторов, но не меняет название, ключ группы или обложки.
  «Неизвестный альбом» остаётся в конце.
- В LibraryViewModel задержка 150 мс, прежние результаты остаются видимыми
  до ответа, устаревшая задача отменяется.
- Миграция 5→6 добавляет только таблицу FTS; данные не сбрасываются.

## Фактический порядок Collator

На тестовой Java 21 с ru SECONDARY набор упорядочился так:
пустое название → 9 → Aha → The Beatles → Zebra → Бобр → Еж →
Ёж → Ива → Йод → Яблоко.
Итак, пустые, затем цифры, латиница и кириллица; е перед ё.
Это JDK-наблюдение, а не гарантированный результат на Huawei.
Отдельных правил для «Разные исполнители» не добавляем.

## Paging — за рамками реализации

Пока ViewModel загружает все треки для группировки и очереди, Paging только
«Песен» мало снизит память и пересечётся с D4. Автономный ориентировочный
JVM-замер (без SQLite/Android) для 3590/20000/50000 синтетических записей:
95/131/256 мс на создание каталога и группировку; память растёт линейно.
Нужны реальные профили на устройстве до выбора порога N.

Ожидается решение владельца: (а) отложить Paging до подтверждённого N;
(б) Paging списка песен в D4; (в) Paging и перенос группировки в SQL.
В M6-0/7 никакой Paging не реализуется.

## Проверка

Обязательны JVM-тесты нормализации/сортировки, DAO FTS, миграции v5→v6
и v1→v6 с сохранением строк, проверка экспортированной схемы 6.json,
зелёный CI точного HEAD, затем Huawei UPD-01/04, REST-01 и SRCH-01…05
после установки Stable Preview поверх текущей. Полную переиндексацию не запускать.
