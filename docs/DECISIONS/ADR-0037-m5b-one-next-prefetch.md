# ADR-0037 — M5-B: один следующий трек после полной загрузки текущего

Дата: 2026-11-09. Статус: Draft до Android CI и Huawei smoke.

## От чего отталкиваемся
M5-A принят владельцем: на Huawei Preview #122 текущий файл скачивался даже во время паузы, запуск первого звука ускорился благодаря стадийной Media3-очереди; PR #27 объединён в main после зелёного CI на точном HEAD. Владелец специально отметил, что докачивается **только текущий** файл. Это штатное ограничение M5-A, которое снимает M5-B.

## Решение
- **Без параллельных полнофайловых GET.** Сохраняем `CacheWriter` из Media3 и один `Executors.newSingleThreadExecutor`. Пока текущий не перешёл в `CachePhase.COMPLETE`, следующая полная загрузка не запускается. Callback успешного current `CacheWriter.cache()` поступает в main thread, где Media3 выбирает фактический следующий ID.
- Для выбора использовать `player.nextMediaItemIndex` и `player.getMediaItemAt(index)`, а не следующий номер в Room. Это учитывает Media3 shuffle/repeat/текущую стадию очереди. `NextPrefetchSelection` допускает **не более одного** другого элемента с положительным размером; при повторе одного и отсутствии следующего ничего не скачивает.
- При смене трека или Stop `stopCurrent()` отменяет оба worker-задания и инвалидирует callbacks/generation. Повторный запуск prefetch после смены режима shuffle/repeat переопределяет только следующий кандидат, не сбрасывая полностью загруженный текущий.
- Режим cache-off по-прежнему вообще не инициализирует SimpleCache и не запускает предзагрузку: оставляем честное сравнение скорости. В cache-on Media3 из private `cacheDir` воспроизводит ранее сохранённые spans; общая политика M5-A: максимум 256 МиБ на один полный файл, общий LRU 512 МиБ, резерв диска 128 МиБ. При отказе предзагрузки обычное WebDAV streaming остаётся доступным.
- Отдельные статусы текущего и следующего в UI. Состояние текущего COMPLETE не заменяется индикатором следующего. Никаких названий файлов, URL, токенов и учётных данных в уведомлениях/диагностике/логе. HTTP 206, Content-Range, per-item ETag/size, запрет redirect и GMS-free проверки не меняются.

## Нюансы и ограничения
- **Не скачиваем все 3590 файлов** и не делаем новых PROPFIND/индексации тегов. На один текущий трек в максимуме один следующий кандидат; при ручном переключении новый текущий получает приоритет, предыдущий prefetch отменяется.
- Следующий выбирается **в момент окончания текущей загрузки**, поэтому изменение shuffle после того, как next уже начал загружаться, может потребовать отмены и нового GET. Это не неконтролируемый параллелизм, но возможны лишние байты при частом переключении режимов.
- Если стадийное наполнение Media3 ещё не успело добавить следующий item, предзагрузки до его появления может не быть; `onTimelineChanged` повторно проверяет отсутствие кандидата после COMPLETE.
- Нет гарантии, что обычный Media3 откроет следующий трек без нулевой паузы при плохой сети, и нет измеренной экономии трафика. Более строгий startup/audio handoff и бюджет data usage — отдельные приёмочные тесты.
- Временные файлы удаляются при завершении MediaSessionService/новом запуске; не появляется persistent offline storage.

## Приёмка
1. JVM `NextPrefetchSelectionTest`: один реальный next в изменённом shuffle-порядке, отсутствие prefetch для repeat-one/конца очереди/неизвестного ID, 3590 синтетических элементов.
2. Static contract: next только по onComplete current и из `player.nextMediaItemIndex`, один worker, stop отменяет оба; пароли не в URL/Intent/логе.
3. Точный полный Android/JUnit/lint/Room/GMS-free/signing/APK CI на HEAD PR.
4. Huawei новой Preview: один раз импортировать **только список**, включить cache-on и один не слишком маленький MP3. На паузе проверить, что **сначала текущий** достиг COMPLETE; затем отображается **«Следующий трек: предзагрузка X/Y КиБ»** и `COMPLETE`, пока первый на паузе. Затем Next: следующий должен воспроизводиться из локально подготовленных данных, без длительного переподключения. Проверить shuffle/repeat-one и Stop, что после отмены предзагрузка не продолжается. Названия файлов, логины/пароли и личные скриншоты в публичный GitHub не загружать.
