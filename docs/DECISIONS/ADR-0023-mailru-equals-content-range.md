# ADR-0023: Совместимость Content-Range с Cloud.Mail.ru (разделитель =)

Дата: 2026-11-08. Статус: в проверке CI и Huawei.

## Реальное подтверждение
Preview #42 вернул обезличенный отчёт: `RANGE/BAD_CONTENT_RANGE/FORMAT_EQUALS_SEPARATOR`, HTTP 206, первый GET, 0 прочитанных байт. Ожидаемый диапазон `0-65535/10944026`. Сам заголовок не экспортировался. Наша классификация `FORMAT_EQUALS_SEPARATOR` означает: строка `Content-Range` **начинается с `bytes=`**, но не соответствует старой грамматике `bytes start-end/total`. Это подтверждает разделитель, но не доказывает правильность остальных чисел.

## Решение
В WebDavRangeReader явно допускаются **только**:
- RFC-синтаксис `bytes <start>-<end>/<total|*>`;
- серверная форма `bytes=<start>-<end>/<total|*>`.

Далее **обязательны** HTTP 206, точные start/end по запросу, тот же известный total (либо стандартное `*`), длина тела строго n байт, проверка ETag/If-Range при наличии сильного ETag, Content-Encoding identity и запрет redirect. Неверные значения не рассматриваются как успешный ответ.

Парсер по-прежнему применяет `matchEntire`: ни расширенные единицы, ни произвольный текст, ни второй `=` не допускаются. Фиксированные обезличенные коды и числа в UI сохранены. Пользовательские URL/имена/ETag/пароль не выводятся.

Лимиты не меняются: максимум 8 МиБ/128 GET/40 с и 64 КиБ RAM-блок, один файл, без массовой обработки 3590 файлов.

## Тестирование
MockWebServer для `bytes=` на двух последовательных диапазонах с проверкой полученных байтов и If-Range; неверный start/end/total, double equals и чужая единица отклоняются; `bytes=.../*` с коротким телом отклоняется. Существующие стандартные `bytes ...`, no-redirect, GMS gate и Room schema checks остаются.

## Приёмка
Нужен зелёный CI нового точного HEAD и проверка одного файла на Huawei в новом изолированном Preview. Даже если Range пройдет, извлечение тегов MediaMetadataRetriever ещё может выдать самостоятельную ошибку. До подтверждения одного файла нельзя запускать массовые запросы.
