# ADR-0093: Выход из состояния ошибки воспроизведения

**Дата:** 2026-11-15
**Статус:** принято в PR задачи `BUG-playback-error-recovery` (#148); решение о поведении — владелец, 2026-11-15
**Связано:** ADR-0032 (MediaSessionService), ADR-0075 (сохранение очереди), аудит [AUDIT_2026-11-14](../audit/AUDIT_2026-11-14_main-2761ae9.md) находка A-12

## Контекст

После `onPlayerError` Media3 оставляет плеер в `STATE_IDLE` и сохраняет
`playerError`. `Player.play()` в этом состоянии только выставляет
`playWhenReady` — источник не готовится, звука нет, ошибка не сбрасывается.
`PreviewAudioPlayback.resume()` вызывал ровно `player.play()`, а `prepare()`
выполнялся лишь при `deferredPrepare`, то есть только при восстановлении
очереди из чекпоинта.

Второе обстоятельство обнаружилось при разборе задачи: `MediaSession.Builder`
получал **сырой `ExoPlayer`**. Кнопка Play в уведомлении, на гарнитуре и в
Bluetooth-контроллере идёт в `Player.play()` напрямую, минуя
`PreviewAudioPlayback`. То есть это два разных пути, и правка одного из них
оставила бы половину случаев нерабочей.

Последствие для пользователя: любая сетевая ошибка — обрыв, таймаут, смена
Wi-Fi↔LTE, 5xx — оставляет тупик. Play не работает нигде до повторного выбора
трека в списке, а на экране висит «Ошибка… код N».

## Варианты

### Вариант A — Play повторяет текущий трек

`prepare()` + `play()` на текущем элементе.

**Плюсы:** минимальная правка; предсказуемо; ничего не переключается.
**Минусы:** при устойчивой ошибке (файл повреждён на сервере, стабильный 5xx по
этому URL) каждое нажатие Play снова упирается в ту же ошибку. Пользователь
попадает в цикл и должен сам догадаться выбрать другой трек.

### Вариант B — Play переходит к следующему треку (принято владельцем)

`seekToNextMediaItem()` + `prepare()` + `play()`.

**Плюсы:** обходит локальную ошибку файла; совпадает с привычным поведением
плееров; одним нажатием возвращает музыку.
**Минусы:** если ошибка сетевая и общая для всей очереди, пользователь увидит
цепочку ошибок — по одной на нажатие. Требует граничного случая на последнем
треке, иначе тупик возвращается.

### Вариант C — отдельная кнопка «Повторить» в интерфейсе

Ошибка остаётся, но пользователь получает явное действие.

**Плюсы:** честнее всего показывает состояние.
**Минусы:** требует UI-работы и строк, а внешние контроллеры (уведомление,
гарнитура, Bluetooth) такой кнопки не имеют — там Play всё равно должен
что-то делать. Это отдельная находка аудита (A-18), не замена выхода из ошибки.

## Решение

Принят **вариант B** с двумя оговорками, зафиксированными в политике:

- **repeat-one** важнее перехода: включённый повтор одного означает, что
  пользователь явно хочет этот трек, поэтому Play запускает текущий с начала;
- **последний трек очереди**: переходить некуда, поэтому текущий с начала —
  иначе на последнем треке Play снова оказался бы в тупике.

Политика вынесена в чистую функцию `PlaybackErrorRecoveryPolicy.actionFor`
(три входа: `hasError`, `hasNext`, `repeatOne`), чтобы решение проверялось
JUnit без Media3 и устройства.

`MediaSession.Builder` получает `ErrorRecoveringPlayer` — `ForwardingPlayer`,
который делегирует **всё, кроме** `play()`: при `playerError != null` вызов
уходит в ту же политику, иначе — в обычный `super.play()`. Обёртка не меняет
timeline, метаданные и команды, поэтому уведомление продолжает работать как
раньше.

## Обоснование

Вариант A оставляет пользователя в цикле на локальной ошибке файла — это
худший исход из трёх для самого частого случая (один битый или перезалитый
файл). Вариант C не решает задачу для внешних контроллеров, где кнопки
«Повторить» физически нет. Вариант B даёт работающий Play везде и обходит
локальную ошибку; его слабое место (общая сетевая ошибка) смягчается тем, что
следующее нажатие каждый раз пробует новый трек, а не тот же самый.

## Последствия

- Play после ошибки работает одинаково в приложении, уведомлении, на гарнитуре
  и в Bluetooth-контроллере.
- Нормальные переходы не затронуты: политика срабатывает только при
  `playerError != null`. Автоматическое восстановление при `STATE_ENDED`
  (`PlaybackContinuationPolicy`, регресс #132) не менялось.
- `repeat-one` и последний трек не попадают в тупик.
- Остаётся технический долг: пользователь по-прежнему видит только числовой код
  ошибки без объяснения причины и без выбора «повторить этот трек». Это A-18,
  отдельная задача с UI-работой.

## Как проверить

1. `PlaybackErrorRecoveryPolicyTest` — 6 тестов: обычный Play ничего не
   переключает; ошибка + есть следующий → `NEXT`; ошибка + последний трек →
   `RESTART_CURRENT`; repeat-one важнее перехода; ни одна ошибочная комбинация
   не возвращает `PLAY`.
2. `:app:testDebugUnitTest` с `QueueEditServiceTest`, `NowPlayingUiTest`,
   `PlayerViewModelTest` — обёртка не сломала жизненный цикл сервиса.
3. Устройство (после merge, отдельным подтверждением владельца): на середине
   трека включить авиарежим → дождаться ошибки → Play из уведомления → играет
   следующий трек. Сценарий `PLAY-08`.
