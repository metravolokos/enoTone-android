# ADR-0103 — восстановление legacy-состояния незавершённого выхода

**Дата:** 2026-11-21. **Статус:** принято, реализовано в PR #241 (`af721333`); Issue #240 закрыта.
**Риск:** R — затрагивает путь выхода аккаунта и порядок персистентных операций
(WORKFLOW §6: (3) путь или атомарность записи, (4) вход/выход аккаунта).
**Связано:** ADR-0080 (порядок выхода), PR #239 / Issue #237 (журнал доказательств),
Issue #240, `SignOutMarker`, `PendingSignOutRecovery`, `FirstRunPhasePlanner`,
`docs/SCENARIOS.md` OUT-02…OUT-05.

## Контекст

`ADR-0080` задаёт порядок выхода: остановить плеер → индексаторы → удалить треки
и плейлисты Room → освободить обложки → сбросить checkpoints → удалить вход из
Keystore → снять флаг незавершённого выхода. Android может завершить процесс между
любыми двумя шагами.

PR #239 (`c8bac329`) добавил в журнал `SignOutMarker` два новых свидетельства:
`sign_out_cleanup_confirmed` (очистка Room, обложек и checkpoints завершена) и
`sign_out_source_key` (хеш аккаунта, по которому ограничена очистка). Новая
логика `PendingSignOutRecovery` завершает прерванный выход только при наличии
обоих свидетельств. Без них состояние остаётся fail-closed: приложение не
открывает ни основной экран, ни форму входа.

Проблема (Issue #240): журналы, созданные **до** #239, содержат только флаг
`sign_out_pending`. Если такой журнал остался в состоянии «флаг есть, вход уже
удалён», пользователь заблокирован: он не может ни войти, ни повторить выход —
повтор требует сохранённого входа, а форма входа ждёт иного состояния.
`SignOutMarker.markCleanupComplete` конструктивно отказывает без `sourceKey`,
поэтому «дописать» доказательство из старого журнала нельзя, не нарушив
запрет Issue #240 на обход cleanup proof.

## Варианты

1. **Полная очистка данных приложения и снятие флага.** При старте, если флаг
   установлен и вход отсутствует, стереть Room, обложки, очереди и настройки,
   затем снять флаг и открыть форму входа. Плюсы: просто, гарантированно
   разблокирует пользователя. Минусы: удаляет данные, которые `ADR-0080:21`
   требует сохранять (тема, страницы, режимы обложек, неидентифицирующая
   диагностика); удаляет записи Room, принадлежащие другому `sourceKey`, хотя
   `RemoteTrackDao.countOtherSources` и сценарий OUT-05 существуют именно для их
   сохранения; удаление базы противоречит `AGENTS.md:29`; провоцирует повторный
   полный импорт, разрешённый только по отдельному подтверждению владельца
   (`AGENTS.md:28`). **Отклонено.**

2. **Запросить у пользователя email и выполнить очистку заново.** Показать экран
   с полем email; по нему восстановить `sourceKey` и выполнить
   `AccountSignOut` с новым журналом, получив настоящее доказательство. Плюсы:
   строгое соблюдение `ADR-0080`, очистка ограничена одним аккаунтом. Минусы:
   требует нового экрана, которого нет в `design/`, а по `AGENTS.md §2` это
   блокирует задачу меткой `design-needed`; лишний шаг там, где удалять уже
   нечего; email — персональные данные, ввод которых ради восстановления
   нежелателен. **Отклонено как основной путь; сохранено как страховка** (см.
   «Решение», п. 4).

3. **Оставить fail-closed навсегда, задокументировав ограничение.** Плюсы: ноль
   риска для данных. Минусы: пользователь остаётся заблокированным; единственный
   доступный ему выход — «Очистить данные» в настройках Android, то есть полная
   потеря, но руками и с худшим UX. Проблема не решается, а откладывается.
   **Отклонено.**

4. **Позиционное доказательство: восстановление без удаления данных (выбрано).**
   Факт отсутствия записи входа при установленном флаге сам по себе доказывает
   завершение очистки, потому что удаление входа — последний шаг перед снятием
   флага. Доказательство опирается не на записанное свидетельство (его нет), а на
   неизменность порядка операций в `AccountSignOut`: шаг `CREDENTIALS` выполняется
   последним.

## Решение

Реализовать восстановление по позиционному доказательству.

**Признак.** `SignOutMarker.pending(context) == true` **и** `LocalCredentialVault.restore(context) == null`.
`restore()` возвращает `null` только при отсутствии записи; повреждённая запись или
недоступный ключ бросают исключение (`LocalCredentialVault.kt:56-63`), поэтому
«пусто» и «не читается» различаются без новых проверок. Состояние с исключением
сохраняет текущее fail-closed поведение.

**Действия при подтверждённом признаке:**

1. `LocalCredentialVault.clear(context)` — идемпотентно: удаляет остаток записи и,
   если он есть, ключ Keystore (`LocalCredentialVault.kt:65-71`).
2. Удалить служебные файлы `enotone-signout-<64 hex>.keys` из `noBackupFilesDir`.
   В них только хеши ссылок на обложки, персональных данных нет
   (`AccountArtworkFileCleanup.kt:99-102`).
3. `SignOutMarker.finish(context)` — снять флаг.
4. Планировщик первого запуска переводит поток на `LOGIN`.

**Чего восстановление не делает:** не вызывает `deleteTracks`, `deleteArtwork`,
`resetCheckpoints`, не удаляет и не пересоздаёт базу Room, не трогает обложки,
настройки темы и страниц, диагностику, очереди воспроизведения, не запускает
индексацию и не переиндексирует медиатеку.

**Обоснование.**

- Очистка уже выполнена: `deleteCredentials` — последний шаг перед `finish`, а
  запись manifest предшествует удалению Room. Проверено на всей истории:
  во всех **84** first-parent-коммитах от `ae0a6bab` (появление `SignOutMarker`)
  до HEAD `CREDENTIALS` ни разу не был не последним; запись manifest ни разу не
  оказалась после `deleteAccountData` (в 82 коммитах до `c8bac329` инвариант
  держался inline-формой `if (manifest.read() == null) manifest.save(...)`, с
  `c8bac329` — через `manifest.ensure`).
- `ADR-0080` не нарушается: его порядок не меняется, шаги только завершаются.
- Данные владельца не удаляются, поэтому риск несоизмеримо ниже, чем у варианта 1.
- `AGENTS.md:29` и `AGENTS.md:28` соблюдаются: база не удаляется, переиндексация
  не запускается.
- Запрет Issue #240 на обход cleanup proof соблюдается: доказательство не
  подделывается, а заменяется другим, проверяемым свойством системы — порядком
  операций.

**Страховка от ложноположительного вывода.** Если в Room есть строки треков
(таблица `remote_tracks`), а ни одного файла `enotone-signout-*.keys` нет, позиционное
доказательство не принимается: такая комбинация несовместима с завершённой
очисткой. Поток остаётся fail-closed и требует решения владельца по варианту 2
(отдельный экран). Для проверки добавлен read-only запрос `RemoteTrackDao.countAll()`
(считает все строки таблицы, без фильтра по аккаунту): он покрывает худший случай —
установку, где могли остаться строки нескольких аккаунтов. Схема Room не меняется.

## Последствия

- Пользователь с legacy-журналом разблокирован; после обновления он видит форму
  входа, настройки оформления сохраняются.
- Новые журналы (с `cleanup_confirmed`) продолжают обрабатываться как в #239;
  путь позиционного доказательства для них не применяется.
- Состояние «вход не читается» (повреждённый конверт, недоступный ключ Keystore)
  остаётся fail-closed, как сейчас (`ACC-06`).
- Тексты интерфейса для заблокированного состояния требуется уточнить: текущая
  строка утверждает «вход сохранён, повторите выход», что в legacy-состоянии
  неверно — входа нет.
- Открытым остаётся дефект, обнаруженный при разборе: временный аудиокэш
  `cacheDir/enotone-m5-temporary-audio` не очищается при выходе
  (`TransientMediaCache.kt:42`; `AndroidAccountSignOutPort` не содержит обращений
  к кэшу). Он не входит в scope #240 и требует отдельной задачи.

## Как проверить

1. Поведенческие тесты (JVM/Robolectric) на каждое окно обрыва:
   после `begin`, после удаления Room, после обложек, после checkpoints,
   после удаления записи vault, после удаления ключа Keystore, до `finish`
   и после него. Повторный запуск восстановления идемпотентен.
2. Отрицательные сценарии: повреждённый vault → fail-closed; флаг со сохранённым
   входом → прежний безопасный повтор выхода; Room непуст без manifest →
   fail-closed по страховке.
3. Регрессия #239: `PendingSignOutRecoveryTest` остаётся зелёным, включая тест
   `legacy empty vault without proof or source key remains fail closed`, который
   заменяется тестом нового контракта с явным обоснованием в описании PR.
4. `OUT-02`, `OUT-03`, `OUT-04`, `OUT-05`, `D6-FR-09`, `ACC-01`, `ACC-06`
   остаются в силе; `SCENARIOS.md` обновляется только по сообщению владельца.
5. Android M0 CI на точном HEAD; два независимых ревью класса R.
6. Huawei: разрушительные проверки выхода — только по отдельной команде владельца.

## Когда пересмотреть

- Если появится штатный путь, при котором запись входа удаляется не через выход
  (например, миграция хранилища), позиционное доказательство перестаёт быть
  верным.
- Если порядок шагов `AccountSignOut` изменится так, что `CREDENTIALS` перестанет
  быть последним.
- Если будет принят вариант 2 и появится экран ручного завершения выхода.
