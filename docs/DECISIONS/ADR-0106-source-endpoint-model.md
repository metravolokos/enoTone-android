# ADR-0106 — Модель источника: настраиваемый endpoint и типы источников

**Дата:** 2026-11-28. **Статус:** **Принято владельцем 2026-11-28** (Вариант 1). Документация — [PR #312](https://github.com/metravolokos/enoTone-android/pull/312); первый срез — [Issue #313](https://github.com/metravolokos/enoTone-android/issues/313). Индекс [ADR](README.md) обновляется этим же PR.
**Риск:** R (затрагивает путь/атомарность записи персистентных данных и вход аккаунта — WORKFLOW §6 п. 3–4).
**Связано:** [R-6.1b](REQUIREMENTS.md), [R-4.2](REQUIREMENTS.md), [R-3.4](REQUIREMENTS.md), [ADR-0003](ADR-0003-webdav.md), [ADR-0010](ADR-0010-sources.md), [ADR-0014](ADR-0014-flat-listing.md), [ADR-0018](ADR-0018-webdav-range-one-file.md), [ADR-0031](ADR-0031-media3-one-track-playback.md), [ADR-0080](ADR-0080-permanent-login-sign-out.md); исследование — [WEBDAV_SOURCES_RESEARCH](../WEBDAV_SOURCES_RESEARCH.md); первый срез — [Issue #313](https://github.com/metravolokos/enoTone-android/issues/313).

## Контекст

Музыка читается только из жёстко зашитой папки `/AllMusic` на `https://webdav.cloud.mail.ru/`. Хост и путь продублированы сторожевыми проверками минимум в семи местах (см. исследование §2.1). Владелец хочет:

1. задавать **произвольную папку** Cloud.Mail.ru (при первом импорте или после выхода и повторного входа);
2. подключать **Yandex.Disk** по тому же WebDAV-транспорту;
3. работать с **локальными файлами**;
4. по возможности объединить локальные файлы с облаком (отложено отдельным ADR).

Проблема не в «втором хосте»: `sourceKey = SHA-256(email)`, а хост и корень **нигде не персистятся**. Тот же email с другой папкой/сервисом даёт общий `sourceKey`, из-за чего библиотеки смешиваются, а совпадающие ETag/size дают прямую коллизию `trackId` (исследование §2.4). Настраиваемая папка — не хотелка, а предпосылка для Яндекса (там корень — весь диск).

Ограничение текущей модели: один `PROPFIND Depth: 1`, «файлы непосредственно в папке». Настраиваемая папка **не** включает рекурсию.

## Варианты

### Вариант 1 — Endpoint-модель + типизированный источник (принят)

Ввести конфигурацию `SourceEndpoint(provider, host, basePath, rootFolder, usernameKind, authKind)` и `libraryId = SHA-256(normalizedAccount + canonicalOrigin + canonicalRoot)` в формате 64 hex. Разделить «источник байтов» (WebDAV Range vs локальный SAF) и «код медиатеки» (каталог, теги, очередь, обложки). Дефолт Mail.ru `/AllMusic` сохраняет **существующий** ID.

Плюсы:
- закрывает R-6.1b и открывает Яндекс без второго сетевого кода;
- устраняет смешивание библиотек (endpoint-aware ID);
- локальные файлы ложатся как отдельный `authKind`, без фиктивного HTTP-слоя;
- каждая фаза (A–D из исследования §8) самодостаточна и проверяема.

Минусы:
- меняет персистентность (envelope v2), идентичность и маршруты воспроизведения — класс R;
- многоточечная правка (≈7 guard'ов + propagation-цепочки);
- требует решить семантику «смена источника при живом аккаунте».

### Вариант 2 — Только настраиваемая папка Mail.ru

Оставить один облачный провайдер, вынести только корневую папку в конфигурацию.

Плюсы: наименьший объём; закрывает пункт 1; не трогает auth-типы.
Минусы: не закрывает Яндекс и локальные файлы; шов под источники не создаётся; при следующей фазе идентичность и сетевой код придётся менять всё равно.

### Вариант 3 — Полный мульти-источник сразу (облако + несколько облаков + локальные + объединение)

Плюсы: одна большая абстракция `MusicSource`.
Минусы: высокий риск; при отложенном едином сетевом слое (R-3.4) и незакрытом смешивании это преждевременно; ревью почти невозможно; противоречит ранее принятому решению делать `MusicSource` вместе с единым HTTP-слоем.

## Решение

Принять Вариант 1 и выполнять **фазово**. Первый срез **A1** вынесен в [Issue #313](https://github.com/metravolokos/enoTone-android/issues/313).

**A1 — настраиваемая папка Cloud.Mail.ru и вынос endpoint (первый срез).**
- Конфигурация источника: `provider` + `host` + `basePath` + `rootFolder`; в A1 только `CLOUD_MAILRU`.
- Хранение — envelope **v2**; v1 читается как Mail.ru `/AllMusic`, данные Room не мигрируют.
- **Идентичность не меняется:** `sourceKey = SHA-256(email)`, `trackId` прежний.
- Смена папки/источника — **только через выход и повторный вход**; при живом входе поле папки недоступно (порядок [ADR-0080](ADR-0080-permanent-login-sign-out.md)).
- Убрать хардкод host/path из 7 сторожей и пробросить endpoint по цепочкам импорта/тегов/обложек/воспроизведения; диагностика и тексты — из конфигурации.

**A2 (отложено) — endpoint-aware library ID.** `libraryId = 64-hex SHA-256(нормализованный аккаунт + канонический origin + канонический корень)`; Mail.ru `/AllMusic` сохраняет прежний `SHA-256(email)`. Нужен только когда появится мульти-библиотека (Фаза D). До A2 смена цели возможна исключительно через выход, поэтому смешивание невозможно: выход стирает всю медиатеку этого `sourceKey` (ADR-0080).

**Фазы после A** (детали — [WEBDAV_SOURCES_RESEARCH §8](../WEBDAV_SOURCES_RESEARCH.md)):
- **B — Yandex.Disk:** тот же WebDAV-транспорт; предпосылки — **платный Yandex 360** (с 22.06.2026 WebDAV только на нём; аккаунт у владельца есть) и **capability-probe** (Range/ETag публично не подтверждены).
- **C — локальные файлы (SAF):** отдельная роль источника; нужен экран выбора папки (`ACTION_OPEN_DOCUMENT_TREE`) — при отсутствии макета в `design/` останавливается меткой `design-needed`.
- **D — объединение локального и облачного:** отдельный ADR; сюда же переезжает endpoint-aware library ID (A2).

Обязательные правила:
1. `libraryId` — 64-hex SHA-256(нормализованный аккаунт + канонический origin + канонический корень); для Mail.ru `/AllMusic` — прежний `SHA-256(email)`. (Вводится в A2/D; в A1 идентичность прежняя.)
2. Envelope v2 хранит провайдер и корень; v1 читается как Mail.ru `/AllMusic` (без миграции данных).
3. Один активный облачный источник за раз; смена источника/папки — только через явный вход (первый импорт либо выход+вход), не «на лету».
4. Границы flat-листинга (`Depth: 1`, без рекурсии) сохраняются, пока не принято отдельное решение.
5. Raw endpoint/корень не попадают в Room как новая колонка, в логи, бэкап, Intent; канонизация один раз.
6. Существующие защиты (same-origin, no-redirect, точный `206`/`Content-Range`, strong `If-Range`, flat-child) сохраняются; новые терпимости — только по таблице исследования §7.

## Обоснование

- Endpoint-модель — минимальная абстракция, которая одновременно закрывает пункт 1, открывает Яндекс и создаёт шов под локальные файлы, не вводя `MusicSource` целиком.
- Endpoint-aware ID устраняет подтверждённый риск смешивания данных при смене цели (§2.4) и не требует менять схему Room ради идентичности.
- Разделение «байты vs медиатека» соответствует выводу владельца «сетевой код отделить от кода медиатеки» и не заставляет локальные файлы идти через HTTP.
- Фазовость снижает риск класса R: каждая фаза принимается автоматическими проверками (ADR-0104) отдельно.

## Последствия

- R-6.1b переводится из ❌; R-4.2 остаётся ❌ до единого сетевого слоя, но создаётся шов.
- Меняются: сторожа хоста/пути (7 мест), envelope/vault, диагностика и тексты, маршруты воспроизведения, propagation фоновых цепочек.
- Существующая установка Mail.ru `/AllMusic` не мигрирует и не теряет данных.
- Яндекс и локальные файлы остаются невыполненными до своих фаз и предпосылок (тариф/проба/дизайн выбора папки).

## Как проверить

- Поведенческие JUnit/Robolectric (без новых строковых контрактов, AUDIT_PROTOCOL §88-89): `/Music`, `/MP3/Collection`, alternate host/base path, тот же email с разными корнем/хостом, неполный листинг, пустой `207`, non-`207`.
- Отрицательные: смена источника при живом аккаунте блокируется до явного входа; старый ID Mail.ru `/AllMusic` не меняется.
- `tools/mock_webdav.py` параметризуется под произвольный корень.
- Exact-HEAD CI (сборка, JUnit, lint, Room schema, GMS scan, detekt, Roborazzi); независимое ревью класса R (два ревьюера).
- Для фаз B/C — отдельные capability-probe и (для C) решение по дизайну выбора папки.

## Когда пересмотреть

- При вводе единого сетевого слоя (R-3.4) — пересмотреть шов `MusicSource`/ByteSource.
- При принятии рекурсии вместо flat-листинга.
- При изменении формата envelope после v2.
