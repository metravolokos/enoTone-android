# ADR-0027 — Быстрый разбор MP3/FLAC вместо многократных Range-чтений декодером

Дата: 2026-11-08. Статус: Draft, до CI и испытания на Huawei.

## Почему меняем подход
Подтверждено на Huawei: Cloud.Mail.ru содержит плоскую /AllMusic (3590 аудиофайлов). Локальная Room хранит список и теги одного файла. Универсальный Android MediaMetadataRetriever при проверке отдельных файлов потребовал **39–50 Range GET и 2,375–3,125 МиБ**. Эти замеры разных файлов нельзя сравнивать как ускорение. При прямом умножении на 3590 треков массовый индекс был бы чрезмерно долгим и дорогим по трафику. LRU четырёх блоков уменьшает только повторные GET, не решая основную проблему.

## Новая стратегия — metadata-first
- MP3: ID3v2.3/v2.4 заголовок и только нужные текстовые фреймы TIT2/TPE1/TALB/TPE2, либо ID3v1 в конце, если ID3v2 отсутствует. Крупный APIC пропускается по длине фрейма **без скачивания картинки**.
- FLAC: сигнатура fLaC, STREAMINFO, заголовки блоков; целиком **пропускать PICTURE, padding, seek table** и читать только Vorbis Comment с UTF-8 полями TITLE/ARTIST/ALBUM/ALBUMARTIST.
- Первая тестовая реализация намеренно **не** поддерживает сжатые/зашифрованные ID3-фреймы, unsynchronization/extended-header ID3, необычные кодировки, чрезмерно крупные комментарии, MP4/M4A/OGG/Opus. Такие файлы возвращают фиксированный код без автоматического запуска дорогого извлекателя.
- Синтетические заголовки и теги в unit-тестах не содержат пользовательских данных. Теги нормализуются через существующий AudioTagFields; title fallback из имени файла возможен, но вывод «встроенный title» считается отдельно.
- Сетевой бюджет **fast-парсера**: не более 6 разных блоков по 64 КиБ и 96 КиБ запрошенных байтов метаданных. При этом 64-КиБ GET-блок и действующие транспортные ограничения 8 МиБ, 128 запросов, 40 с, HTTPS, HTTP 206, точные Content-Range, ETag/If-Range, отсутствие redirects остаются.
- Новый opt-in UI **«Быстро прочитать MP3/FLAC — один файл»**. Сохраняет результат одного файла в Room по существующей проверке версии, выводит только код результата, флаги **встроенных** тегов, количество GET, байт и факт записи. Старую кнопку MediaMetadataRetriever не удаляем до сравнения на Huawei.
- Нет фонового индексатора, нет массовых 3590 вызовов, нет новых разрешений, миграций или автоматической сетевой активности.

## Почему не обрабатывать сразу всю медиатеку
1. Проверить корректность на одном MP3 с ID3v2, MP3 с ID3v1 и FLAC с Vorbis Comments. Сравнивать **один и тот же файл** с прежним методом, а не разные треки.
2. Зафиксировать 1–3 HTTP GET как инженерную цель для типичных файлов (это **не гарантированный факт**); измерять также скачанные байты и процент распознанных тегов.
3. Только после замеров определить резервный медленный путь для неподдерживаемых разметок/форматов, а затем отдельный план ограниченного фонового индексатора с паузой/возобновлением и Room checkpoint.
4. Лимит частоты и объёма не повышать, особенно для мобильного трафика.

## Основание формата
- FLAC metadata/Vorbis Comment: RFC 9639 §§8.1/8.6 — https://www.rfc-editor.org/rfc/rfc9639.html
- ID3v2.3 структура и фреймы — https://id3.org/id3v2.3.0
- ID3v2.4 frame size — https://github.com/id3/ID3v2.4/blob/master/id3v2.40-structure.txt

CI на точном HEAD: Kotlin/Android compile, JUnit с синтетическими MP3/FLAC (включая большую APIC/PICTURE), MockWebServer Range, lint, GMS-free, Room schema v1 и подпись изолированной Preview. Затем Huawei: установить новый Preview, импортировать список, один раз нажать fast-кнопку для MP3 или FLAC, прислать **только числовой отчёт и код результата**, без значения тегов/имён/ETag/email. Старые Preview и исходную базу не удалять.
