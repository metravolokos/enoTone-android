# ADR-0047 — M1: фоновая индексация без привязки к Wi-Fi

Дата: 2026-11-09. Статус: Draft до exact-HEAD CI и испытания на Huawei.
Заменяет **политику сети и lifecycle** из ADR-0046; лимиты и checkpoint ADR-0046 остаются в силе.

## Требования владельца и сверка с исходным ТЗ
- В первоначальном задании M1 была предусмотрена индексация в фоне (предлагался WorkManager). На практике PR #41/ADR-0046 реализовали foreground-only coroutine и останавливались в MainActivity.onStop — это **не соответствует** заданию.
- Владелец уточнил: **условия Wi-Fi для работы не нужны**, а **продолжение индексации после сворачивания приложения и блокировки экрана обязательно**.
- Сканирование остаётся только по **явному действию пользователя**. Само открытие плеера, прослушивание и перезапуск устройства не должны включать скрытую индексацию 3590 файлов.

## Решение
1. Запускаем самостоятельный **Service с foregroundServiceType=dataSync** из видимой Activity по кнопке «Начать». Android показывает собственное постоянное уведомление с числовым прогрессом и действиями «Пауза» и «Стоп». Основной Compose-экран лишь наблюдает за StateFlow, не владеет Job. `onStop()` Activity не управляет индексатором.
2. Доступ к сети **через любой активный тип подключения**. Нет Wi-Fi-only флага, опции мобильного разрешения или отслеживания типа сети. Нет автоматического retry-storm: существующий WebDAV Range reader сам остановит сессию по сетевой ошибке и сохранит коды.
3. Вне Activity фоновый компонент вызывает **тот же** `ManagedTagIndexSession` и `PilotTagIndexer`. Не меняем установленные границы: **4 порции максимум**, каждая ≤60 GET/4 МиБ/~180 с; общие ≤240 GET/16 МиБ; пауза 1,5 с. Без рекурсивного PROPFIND, без повторного импорта /AllMusic.
4. **Пароль только в RAM:** при нажатии кнопки Account/email и app-password передаются в `ManagedScanRuntime` внутри того же процесса; в Intent, PendingIntent, уведомлении, Room, логе и резервной копии этих значений нет. Даже пользователь, разрешивший Keystore-хранение, не даёт согласие на фоновый автозапуск. Служба использует `START_NOT_STICKY`; при убийстве процесса не восстанавливает сессию без нового нажатия.
5. После **каждого** обработанного файла SQLite/Room сохраняет результат CAS по ETag/версии. Пауза, Стоп, экран блокировки, остановка процесса не требуют повторного PROPFIND или повторной обработки уже отмеченного файла. При открытии плеера пользователь может начать следующую ограниченную сессию на основании той же Room.
6. Для Android 14+ объявляем `FOREGROUND_SERVICE_DATA_SYNC`. Для API 29+ передаём тип в `startForeground`. Для Android 15+ реализуем `Service.onTimeout()` и останавливаемся при системном ограничении; **не обещаем бесконечный фон**. Производители (Huawei) могут применять дополнительные ограничения энергосбережения — требуется реальная проверка.

## Почему не WorkManager в этом срезе
Исходное ТЗ предлагало WorkManager. Он пригоден для отложенных и гарантируемых повторных работ, **но** его long-running worker в Android 16 расходует JobScheduler-квоту даже с foreground уведомлением. Для уже инициированной пользователем короткой (максимум четыре порции) операции прямой `dataSync` foreground service проще и точнее. WorkManager/JobScheduler для отложенных автоматических запусков — отдельная задача с отдельным согласием и расписанием. Не использовать GMS. Официальные сведения: https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running и https://developer.android.com/about/versions/15/behavior-changes-15.

## Отвергнутые альтернативы
- Продолжать индексацию в Activity после `onStop()`: ОС уничтожит Activity; нет надёжного уведомления и управления, привязка к Compose жизненному циклу.
- Игнорировать Android foreground service type: SecurityException на современных targetSdk.
- Сканировать неограниченно все 3590 сразу: превышение сетевого бюджета, непредсказуемое поведение сервера и батареи.
- Передавать учётные данные в Intent или восстанавливать работу через BOOT_COMPLETED: нарушение требований безопасности и Android 15 запрет запуска dataSync FGS при boot.

## Проверки и критерий принятия
- CI точного HEAD: Gradle Android/Lint/JUnit, Room schema, GMS scan, APK, Python contract.
- Huawei Stable Preview **с тем же app ID/подписью**, обновление поверх предыдущей; список 3590 и индекс 62 должны остаться. Без очистки данных.
- Явный Start, затем свернуть приложение, заблокировать экран на одну-две минуты и проверить рост агрегатов GET/обработанных. Не публиковать названия треков.
- Pause из уведомления, возврат в приложение, проверить неизменность счётчиков, Resume по кнопке, Stop и повторный запуск с сохранённым checkpoint.
- Отдельно проверить без Wi-Fi (если есть разрешённое мобильное подключение); тип сети не должен блокировать запуск.
- В случае выключения устройства/force-stop гарантируется лишь **сохранность checkpoint**, а не автоматическое продолжение без явного повторного запуска.
