# ADR-0022: Поддержка RFC 9110 Content-Range с неизвестным размером

Дата: 2026-11-08. Статус: эксперимент до CI и Huawei.

## Контекст
Huawei Preview #40: `RANGE/BAD_CONTENT_RANGE/HTTP 206/1 GET/0 байт`. Диагностика показала `FORMAT`: ожидаемые `0-65535/10944026`, полученные числа неизвестны, так как формат не принят парсером. Реальное значение HTTP-заголовка неизвестно и не публикуется.

Стандарт [RFC 9110 §14.4](https://www.rfc-editor.org/rfc/rfc9110.html) разрешает `Content-Range: bytes 0-65535/*` (неизвестный полный размер). Наш собственный парсер ошибочно признавал такую форму некорректной. Это **правдоподобная гипотеза**, но не доказанная причина ответа Cloud.Mail.ru.

## Решение
- Принимать только два формата: `bytes start-end/knownTotal` и стандартный `bytes start-end/*`.
- **Обязательно** совпадение начала и конца с выданным запросом; проверять ровно ожидаемое количество полученных байтов, HTTP 206, отсутствие redirect, Content-Encoding identity, ETag при его наличии.
- Путь и `fileSize` из ранее сохранённого WebDAV XML по-прежнему определяют ограничения random access. Если сервер вернёт другой числовой total — прежний строгий отказ.
- При `/*` фиксировать только числовой счётчик успешно принятых диапазонов неизвестного размера; сырые заголовки в логи/UI не выводить.
- Если заголовок не распознан, различать дополнительные фиксированные коды `FORMAT_EQUALS_SEPARATOR` и `FORMAT_UNEXPECTED_UNIT`, без публикации содержимого.
- Лимиты прежние: 8 МиБ суммарно, 128 запросов, до 40 секунд, 64 КиБ RAM-блок, только один аудиофайл.
- Никаких изменений Room, пользовательских файлов и закрытых ключей.

## Тестирование
MockWebServer: HTTP 206 с `bytes start-end/*` на первом и втором блоке, EOF, счётчик, точные полученные байты; неверный конец с wildcard строго отклоняется; `bytes=...` и чужой unit отклоняются с фиксированными кодами. Остальные тесты WebDAV, lint, Room schema v1, GMS scan, SHA и подпись APK обязательны.

## Приёмка
После зелёного CI новый Preview с отдельным applicationId. На Huawei импортировать список один раз, проверить теги **одного** файла. Если снова `FORMAT`, повторять тест без новой диагностической информации не надо: понадобится более подробная обезличенная классификация формата или проверка заголовка в локальном безопасном окружении.
