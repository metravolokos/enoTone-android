# ADR-0039 — M6-B: перемотка внутри текущего трека

Дата: 2026-11-09. Статус: Draft до CI и Huawei smoke.

## Контекст

После принятой на Huawei Preview #129 функциональности M6-A владелец явно отклонил использование прежней фирменной палитры. PR #29 возвращён к **стандартным цветам Material Design**, прошёл CI #135 и объединён в main. Дальнейшие дизайн-решения Android пока не согласованы.

В исходном ТЗ M3 и M5 требовалась перемотка внутри трека, в том числе локальное чтение уже скачанного файла. У Media3 ExoPlayer уже есть seek в MediaSession и временный read-only CacheDataSource, однако на основном экране **нет доступного пользователю ползунка**. M6-B закрывает этот конкретный пробел без перестройки WebDAV, кэша и плейлиста.

## Решение

1. Показывать на экране выбранного трека время от начала и известную длительность, обновляя данные из привязанной MediaSessionService/ExoPlayer раз в 500 мс. Длительность `C.TIME_UNSET`/неизвестная/неположительная отображается как `--:--`; ползунок недоступен.
2. Стандартный Material3 `Slider` с доступным `contentDescription` на русском и английском, **без новой цветовой темы**. Пока пользователь перетаскивает ползунок, показывать целевую позицию и не заменять её обновлениями таймера. Отправлять **один** `seekTo` после отпускания, не открывать новое HTTP-соединение на каждом движении пальца.
3. UI не выполняет HTTP и не знает URL, пароль или удалённые пути. Единственный метод в private `EnoTonePlaybackService` — `seekToFraction(fraction)`, разрешённый только при доступной `Player.COMMAND_SEEK_IN_CURRENT_MEDIA_ITEM`. Pure Kotlin `PlaybackSeekPolicy` проверяет duration и конечность fraction (нет NaN/Infinity), ограничивает целевое время `[0, durationMs]`.
4. Сохранить действующий M5 CacheDataSource: закэшированные участки при новом seek Media3 читает с приватного диска, отсутствующие — через прежний строго проверенный HTTPS WebDAV HTTP 206 Range транспорт. **Мгновенность** любого seek и **доказанное отсутствие новых сетевых запросов** при 100% кэше можно подтвердить только реальными замерами Huawei; функциональная работа ползунка не доказывает экономию трафика.
5. Повтор, случайный порядок, контекстная очередь до 3590 файлов, фоновое воспроизведение, предзагрузка current→next и приватность MediaSession остаются прежними. Новый PROPFIND, массовая индексация тегов и GET всех файлов не добавляются.

## Контроль качества и приёмка

- JVM `PlaybackSeekPolicyTest`: неизвестная длительность, NaN/Infinity, ограничение отрицательных и выходящих за 1 долей, время `MM:SS` и `HH:MM:SS`. Static test проверяет Player seek permission, отсутствие новых путей/логов/Intent extras и наличие доступного Slider.
- CI на **точном PR HEAD**: mock WebDAV, Android assemble/JUnit/lint, Room schema, strict GMS-free APK/dependency scan, isolated Preview app ID/signing и артефакт GitHub.
- Huawei в отдельной Preview: один раз сохранить плоский список `/AllMusic`; начать знакомый MP3/FLAC; проверить позицию и длительность, остановить на паузу и дождаться current COMPLETE. Переместить ползунок **назад и вперёд**, отпустить, проверить новый фрагмент и отсутствие ошибки. После Resume и переключения Next убедиться, что позиция относится к новому текущему файлу. Проверить доступность ползунка и отсутствие изменения стандартных цветов Material Design.
- Не переносить личные файлы, URL, имена/теги, учётные данные или скриншоты в публичные GitHub комментарии; результаты можно описывать только числами и статусами.

## Не входит

Перерисовка интерфейса или утверждение палитры, AB-repeat, ускорение неоткрытых участков, ручное управление порядком очереди, воспроизведение offline после перезапуска, режим Wi-Fi-only и выпуск релизной подписанной версии.

## Дополнение после отрицательного Huawei Preview #138 (2026-11-09)
Владелец наблюдал остановку после окончания текущего и невозможность продолжить после ручного Next. Факт: элемент очереди меняется, но состояние остаётся Pause, длительность следующего ещё неизвестна. Исходную причину автоматического ENDED по скриншотам нельзя установить достоверно.

Выбрано минимальное исправление без смены WebDAV/CacheDataSource: (а) явные кнопки Next/Previous трактуются как намерение начать проигрывание нового элемента, с prepare при ENDED/IDLE; (б) для неожиданного STATE_ENDED c playWhenReady=true, существующим next, без audio-focus suppression и вне repeat-one — одна отложенная перепроверяемая попытка продолжить. При обычной Media3 AUTO-транзиции ничего дополнительно не делаем. Не используем безусловный play() в каждом onMediaItemTransition: это нарушило бы добровольную Pause и аудиофокус. Не выполняем бесконтрольный retry при HTTP-ошибках и не меняем кэш/потоки.

Новый PlaybackContinuationPolicyTest покрывает остановку на последнем, Pause/focus suppression и repeat-one; Python contract проверяет wiring. Ни один тест на JVM не доказывает реальную связку Media3 + Huawei; **PR остаётся Draft до exact-HEAD CI и повторного теста в новой Preview**.
