# ADR-0091 — Отказ от FTS4: поиск по подготовленным ключам в памяти

**Дата:** 2026-11-15. **Статус:** решение владельца принято 2026-11-14 в 23:45 («отказаться от индекса»); реализация — Draft PR #143, не слита.

## Контекст и факт

После M6-0/7 (#128, ADR-0087) Room v6 содержит FTS4 `track_search` с `unicode61`. На Huawei, Stable Preview 677, «Диагностика → Поиск по песням» показала `sqlite=3.32.2 tracks=3647 index=0`; `EXPLAIN QUERY PLAN` для FTS c JOIN и без JOIN возвращает `SQLiteException`. Предположение о влиянии OEM SQLite / `unicode61` не подтверждено точным текстом ошибки и **не является доказанным корнем**; его больше не расследуем по решению владельца.

Запрос через FTS давал пустые результаты и мог блокировать чтение Room («Читаем локальную медиатеку» в сборке 675). Срочный #136 убрал вызов FTS из UI, оставив сам индекс и его синхронизацию. Рабочий RAM-поиск на том же Huawei: «маль» → **19 из 3647**, но **110–130 мс** на запрос из-за повторной нормализации всех песен.

## Рассмотренные варианты

1. **Исправлять дисковый индекс:** FTS4 с другим токенизатором (без `unicode61`), либо FTS5. Плюсы — потенциально быстрый индексный поиск на больших библиотеках. Минусы — OEM-совместимость не проверена; новый вариант миграции и дополнительные таблицы, поддержка инкрементального индекса, SQL-подстроки не совпадают с текущим `containsAllTerms`. Высокая стоимость регрессии на устройстве.
2. **RAM-поиск с ключами, предрасчитанными при загрузке (выбрано).** Плюсы — отсутствие зависимостей от FTS, одинаковая семантика подстроки на Android/JVM, сохранение порядка и полей, простая миграция и возможность тестировать на синтетических данных. Минусы — O(N) на запрос, дополнительные RAM-строки и время первичной подготовки каталога; при росте библиотеки нужен повторный замер.

**Решение:** вариант 2. Отмена FTS — решение владельца. Новые зависимости, настройки, Paging и изменение дизайна не вводятся.

## Контракт и границы

- `OfflineTrackRow.normalizedSearchKey` вычисляется **один раз при создании неизменяемой записи**: название (включая файловый fallback), исполнитель, альбом, Album Artist, жанр. `copy()` с изменёнными полями создаёт новый ключ.
- Группы «Альбомы», «Артисты», «Авторы» и их ключи строятся **один раз при загрузке снимка** вне главного потока, вместе с каталогом/обложками. При обновлении данных, смене учётной записи и повторном чтении кэш пересоздаётся или очищается.
- Каждый поисковый запрос нормализуется один раз. Каждое слово — **подстрока** одного уже нормализованного ключа (логическое AND); пустой запрос показывает весь список. `ё/е`, диакритика, регистр, пробелы и различение `й/и` — прежние правила `LibraryText.searchKey`. Порядок результатов не меняется. Сортировка ru Collator и игнорирование `The` у исполнителей из ADR-0087 **остаются**.
- Никаких MATCH, FTS-таблиц, DAO, синхронизации индекса или диагностических FTS-запросов в живом коде. `LibrarySearchTrace` остаётся: обезличенные длина запроса, результат, `applied` и `ms=`; без названий, запросов, путей, email.
- Room v7: явная миграция 6→7 `DROP TABLE IF EXISTS track_search` под `SQLiteException`, ошибку показывать только фиксированным кодом без исходного текста. Если OEM не позволяет DROP, устаревшая таблица не входит в перечень сущностей v7 и не должна блокировать обновление. Удалять `remote_tracks`, `playlists`, `playlist_items`, обложки или файл очереди **нельзя**. Полную переиндексацию не запускать.

## Проверка и критерии пересмотра

1. JVM/Robolectric: один подготовленный ключ на экземпляр, повторные запросы не пересчитывают данные; русский/английский, ё/е, регистр, диакритика, два слова, пустой запрос и эквивалентность старому `containsAllTerms`. Проверка сортировки не меняется.
2. Room: тест 6→7 с непустым FTS, треками, плейлистами, позициями и `firstSeenEpochMs`; успешная цепочка 1→7; KSP-экспорт `7.json` в репозитории. Точный HEAD CI должен быть зелёным.
3. Huawei: установка поверх 677; все данные и обложки/очередь на месте, экран загрузки не зависает; «маль» на «Песнях» 19 из 3647, английский запрос находит; быстрый ввод/стирание без чужих результатов; кнопки «Проверить поиск» нет; в «Последний поиск» измерено **`ms≤20`**. Если медленнее, записать реальное число в PR — не утверждать PASS без отчёта владельца.
4. **Пересмотр:** медиатека приблизится к **20 000 песен** или измеренный поисковый запрос превысит **100 мс** на устройстве. До этого никаких новых индексов/Paging без отдельного ADR и решения владельца.

## Последствия

- ADR-0087 частично заменён (только FTS). Исторические схемы 1…6 остаются неизменными для миграций.
- Меньше записи и блокировок SQLite при импорте/чтении тегов, зато O(N) RAM-фильтрация и кэш текстов в оперативной памяти.
- Проверка Huawei выполняется владельцем после CI; ревью и слияние — Claude, **только по команде владельца**.
