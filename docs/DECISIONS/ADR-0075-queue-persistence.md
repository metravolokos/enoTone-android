# ADR-0075 — M6-0/3: сохранение и восстановление очереди

Дата: 2026-11-12 | Статус: кандидат (Draft; до ревью владельца и Huawei) | Основание: ADR-0074, шаг 3.

## Контекст

Завершение процесса теряет очередь, выбранный трек, позицию, shuffle и repeat. В Huawei Preview #111 создание Media3 timeline из всей библиотеки (3590 источников) синхронно занимало ~3,3 с. Поэтому нельзя повторять массовый вызов setMediaSources при восстановлении. Сохранённые учётные данные допускаются только по добровольному выбору пользователя. Room v5 занята M6-0/6; интерфейс заморожен на ADR-0073.

## Рассмотренные варианты

1. **Два JSON-файла в noBackupFilesDir (выбрано).** Плюсы: редкая запись большого списка и дешёвый частый checkpoint; нет миграции Room и backup. Минусы: две атомарные операции не образуют одну транзакцию, нужен контроль ревизий и строгий валидатор.
2. **DataStore Preferences/Proto.** Плюсы: транзакционное обновление. Минусы: новая инфраструктура и сериализация большой очереди при каждом checkpoint, дополнительная настройка исключения из backup.
3. **Таблица Room.** Плюсы: атомарные транзакции и индексы. Минусы: незапланированная миграция схемы, конфликт с будущей Room v5, смешение жизненного цикла каталога и playback.

Для JSON-кодека выбран **Gson 2.13.2**, объявленный в version catalog и THIRD_PARTY_LICENSES (Apache-2.0): org.json на обычной Android-free JVM без Robolectric содержит заглушки, а kotlinx-serialization потребовал бы нового compiler plugin. Используются только JsonObject/JsonArray/JsonParser без рефлексивной сериализации: отдельные R8 keep-rules не нужны.

## Решение

- **Большой файл** `noBackupFilesDir/enotone-queue-v1.json`: формат v1, исходный (не перемешанный) список SHA-256 `trackIds`, `sourceKey` (SHA-256 аккаунта), `shuffleEnabled`, полная перестановка `shuffledIndices` при включённом shuffle, `savedAtEpochMs`, случайная `queueRevision` (UUID). Пишется только при создании новой очереди и смене shuffle; также при восстановлении, если отфильтрованы пропавшие треки. Список ID и перестановка проходят полную валидацию **в фоновом I/O executor**, не при 12-секундном таймере.
- **Маленький файл** `noBackupFilesDir/enotone-position-v1.json`: `selectedTrackId`, `positionMs`, `repeatMode`, `shuffleEnabled`, `savedAtEpochMs`, `queueRevision`, `version`. Запись при смене трека, repeat, паузе, каждые 12 секунд активного проигрывания, при onTaskRemoved/onDestroy. Порог 5 с для обычных изменений, срочные трек/режимы и lifecycle обходят порог. Снимки коалесцируются. Запись на одном I/O executor: temp → fsync → rename; сначала layout, потом position.
- **Контроль согласованности:** валидный position с другой ревизией или несовпадающим shuffle означает разрыв двухфайловой транзакции и запрещает восстановление. Если файл позиции отсутствует или повреждён, но layout цел, восстановить **первый** трек на позиции 0 с repeat off, сохранив очередь/shuffle. **Чужая версия любого из файлов** → сохранённой очереди нет. Повреждённый layout, чужая версия, недопустимые ID/перестановка → очереди нет. Дубликаты и поля вне whitelist отвергаются. Ни пути, ни теги, ни названия, ни ETag, email, пароль, Authorization или URL не сохраняются.
- Восстановление возможно только при **добровольно сохранённом** LocalCredentialVault и совпадающем sourceKey; Room локально разрешает ID в QueueTrack, отбрасывая удалённые и `missingScans > 0`. Если выбранный исчез — следующий существующий, позиция 0; перестановка shuffle фильтруется и индексы пересчитываются.
- **StagedPlaylistPlan при восстановлении:** синхронно готовится seed из выбранного трека и до двух соседей с каждой стороны (не более пяти); остальные добавляются Handler-порциями максимум по 32 элемента без долгого блокирования UI, даже пока ExoPlayer в IDLE. Первого `prepare()` и HTTP GET до явного Play нет. Точная `DefaultShuffleOrder(shuffledIndices, seed)` назначается через `setShuffleOrder` **только после полного заполнения** timeline; затем действует сохранённый repeat. При быстром нажатии Play до завершения фонового заполнения временный порядок может отличаться — измерять на Huawei. Обычный `playQueue` также использует staged timeline.
- Для диагностики добавлено **только числовое** `restoreSeedMs` — длительность синхронной подготовки на главном потоке. Цель на Huawei для 3590 треков — около **50 мс или менее**, фактическое время до аппаратного измерения не подтверждено; чистый JUnit проверяет, что план содержит всего пять seed элементов. Диагностика доступна в существующем техническом разделе, визуальное направление не изменено.
- При opt-in входе и найденной очереди запуск приложения **осознанно открывает существующую медиатеку**, чтобы мини-плеер показывал трек на паузе. Если очереди нет, Home остаётся стартовым экраном. Это переход в уже существующий экран, без нового дизайна.
- **Явная команда `stopPlayback()` удаляет оба checkpoint** — «остановить воспроизведение» означает забыть очередь. Android «Остановить»/force-stop в системных настройках не является этой командой и должно оставить ранее сохранённый checkpoint (callback при force-stop не гарантирован).
- `MediaSession.Callback.onPlaybackResumption` для автономного Bluetooth-возобновления после смерти процесса оставлен отдельным PR, без заглушек.

## Последствия и риски

Room, WebDAV, обложки, индексатор, GMS-gate и Material 3 не меняются. Оба файла находятся вне Android backup; удаление данных удаляет оба. Раз в 12 секунд переписывается только небольшой checkpoint, а не ~240-КБ очередь (экономия записи на флеш). При внезапном убийстве процесса позиция может отставать от фактической до очередного checkpoint. При сбое между записью layout и position несовпадение ревизий надёжно блокирует некорректное восстановление.

## Как проверить

- JUnit без Android runtime: JSON round-trip обоих файлов и shuffle, повреждения/неизвестная версия, отсутствие секретов, несовпадающая ревизия, отсутствие position с fallback на первый трек, все три случая пропавших треков, биективность перестановки и fake-clock троттлинг; 3590 треков → seed ≤5 и порции ≤32.
- CI на точном HEAD: Kotlin/assemble, JUnit, lint, Room schema, GMS-free APK scan; отдельный Huawei тест после получения подписанной Stable Preview из `main` и разрешения владельца.
- Huawei: 3-й трек/середина/shuffle/repeat-all → смахивание либо Android «Остановить» → mini-player paused, точный Next и позиция; отсутствие GET до Play; отсутствие opt-in vault → нет восстановления. В настройках диагностики отметить числовое `restoreSeedMs` для очереди 3590 и убедиться, что основной поток не зависает.
