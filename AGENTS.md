# AGENTS — правила работы над enoTone

Этот файл — первое, что читает любой агент или человек перед изменением репозитория.

## 1. Минимальный маршрут чтения по роли

**Новый чат начинает с текущего GitHub, а не с истории предыдущих чатов.**

- **Диспетчер (read-only):** docs/WORKFLOW.md, ROADMAP/DESIGN_PLAN, открытые Issues/PR и зависимости. Не проводить общий аудит исходников при ответе «что дальше?».
- **Исполнитель:** AGENTS.md, утверждённая GitHub Issue, MODULE_MAP и только относящиеся к ней CURRENT_DECISIONS, ADR, SCENARIOS, TESTING и код. Если выявлена скрытая зависимость — изучить её.
- **Ревьюер (по поручению проверить PR):** Issue, base/HEAD SHA, diff, CI, AUDIT_PROTOCOL и бланк docs/REVIEW_REPORT_TEMPLATE.md (отчёт начинать с бланка, проверять `tools/review_helper.py`); **опубликовать заключение комментарием или review в PR**. Код в чужой ветке не изменять без разрешения. Внешний аудит без поручения комментировать PR остаётся read-only.
- **Архитектурный/полный аудит:** CURRENT_DECISIONS, REQUIREMENTS, индекс ADR, ARCHITECTURE, KNOWN_ISSUES, OPEN_QUESTIONS и релевантные реализации.

Исторические документы в docs/archive/ не описывают текущие решения. Исходное ТЗ уступает более поздним решениям владельца.

## 2. Этап разработки и дизайн

**Текущий этап не фиксируется в AGENTS.md:** ROADMAP/DESIGN_PLAN задают разрешённую последовательность, `state:ready` в GitHub Issue — конкретную готовую работу. Действующее направление — Android v2, принятые ADR-0084, ADR-0086, ADR-0088 и **ADR-0090**; исторический ADR-0073 заменён как визуальное руководство.

- **Дизайн живёт в [`design/`](design/README.md)**: решения, генераторы, эталоны, исходники холста. Ресурсы (`ic_eno_*`, `bandit_*`, `eno_colors`, wordmark, launcher) переносятся только `design/tools/sync_android.py`, руками не правятся. Правила работы с дизайном — [`design/AGENTS.md`](design/AGENTS.md).
- **`design-needed`:** если для задачи нужен значок, поза, цвет, состояние или экран, которого нет в `design/`, — эта часть работы останавливается: issue с меткой `design-needed`, в PR и отчёте «заблокировано дизайном: #N». Без Material-подмен, «похожих» путей и заглушек.

## 3. Жёсткие ограничения (нарушать нельзя)

- Без GMS / Play Services / Firebase, без телеметрии, без сетевых вызовов кроме WebDAV пользователя и явно включённого ИИ-API. Только HTTPS. GMS-gate в CI не ослаблять и не «белить» маркеры.
- Учётные данные и пути к личной музыке — никогда в Git, логи, backup, crash, Room, Intent. После успешной WebDAV-проверки вход **всегда** сохраняется в Android Keystore AES-GCM ([ADR-0080](docs/DECISIONS/ADR-0080-permanent-login-sign-out.md), O-09), `security-crypto` запрещён. «Выйти» сначала останавливает воспроизведение и индексаторы, удаляет данные и обложки аккаунта; Keystore очищается **последним**.
- **Обложки:** мастер до 1200 px в постоянном `filesDir/enotone-artwork-v2`, без автоматического LRU и удаления; режимы `ON_DEMAND` / `AUTO_AFTER_IMPORT`; одна выбранная обложка реального альбома на всех экранах; «Неизвестный альбом» не смешивать; никаких массовых image GET во время PROPFIND/индексации тегов ([ADR-0067](docs/DECISIONS/ADR-0067-permanent-album-artwork.md)).
- **Импорт/обновление — одно действие**, инкрементальное. Полную переиндексацию 3590 файлов запускать **только после отдельного подтверждения владельца**, никогда ради UI-проверки.
- Room: только миграции без потери данных, схемы экспортируются и коммитятся. Существующую базу на устройстве владельца не удалять.
- Проверки на устройстве — инструмент диагностики, а не стадия приёмки ([ADR-0104](docs/DECISIONS/ADR-0104-auto-acceptance.md)). При подключённом ADB исполнитель может поставить подписанную Stable Preview `app.enotone.android.preview` поверх предыдущей, снять скриншоты и logcat для разбора конкретного дефекта. Без удаления приложения и данных; `.preview.rN` для этого не используется.
- Плейлисты: будущая обложка плейлиста — ссылка на существующий мастер альбома, без копирования. **Не писать «плейлисты реализованы»**, пока нет UI.

## 4. Процесс

- Координация нескольких агентов — по [docs/WORKFLOW.md](docs/WORKFLOW.md); канонический статус и приоритет задачи — в labels GitHub Issue; диспетчер read-only, исполнитель работает только после захвата, ревьюер публикует замечания в назначенном PR.

- Ветка — каноническое имя из Issue по docs/WORKFLOW.md §5 (после атомарного захвата); Conventional Commits, небольшие PR; `main` не менять напрямую.
- Merge — только при зелёном CI **точного HEAD** PR (сборка, JUnit, lint, Room schema, GMS scan, APK), независимом ревью и **явной команде владельца**. Порученный агент выполняет squash; ветки не удалять (WORKFLOW §6).
- Каждое архитектурное решение — ADR по шаблону: контекст; **минимум два варианта** с плюсами/минусами; решение; обоснование; последствия; как проверить. Заменять принятый ADR только новым ADR и **обновлять индекс `docs/DECISIONS/README.md`** (статус старого и нового).
- **Приёмка — по автоматическим проверкам** ([ADR-0104](docs/DECISIONS/ADR-0104-auto-acceptance.md), решение владельца 2026-11-21). Сценарий считается принятым, когда PR слит в `main`, CI на точном HEAD зелёный (сборка, JUnit, lint, Room schema, GMS scan, detekt, Roborazzi) и независимое ревью пройдено. Отдельного статуса «проверено на телефоне» нет: плановая ручная проверка исключена. Найденный на устройстве дефект заводится отдельной Issue с меткой `bug` и исправляется обычным порядком.
- Не добавлять новые тесты, проверяющие наличие строк в исходниках (`tools/test_*_contract.py`). Тестировать поведение: JUnit / Robolectric / Compose UI.
- **Пороги сложности** ([AUDIT_PROTOCOL §4](docs/AUDIT_PROTOCOL.md#4-механизм-сокращения)): новый модуль, внешняя runtime-зависимость или пользовательская настройка — только через ADR с решением владельца; базовая линия detekt не растёт; изменение проверки в существующем тесте внутри PR-исправления — только с обоснованием в описании PR.
- Каждый PR перечисляет ID затронутых сценариев из [SCENARIOS](docs/SCENARIOS.md) и обновляет их «Последний результат» значением «принято по автоматическим проверкам» с указанием PR и прогона CI после merge.
- Не добавлять заглушки, выдающие себя за готовые функции.
- **Этапы и дизайн:** новые этапы, изменения макета и работа с ресурсами — только в утверждённой Issue с учётом ROADMAP/DESIGN_PLAN и design/; без решения владельца не начинать следующий этап. Не смешивать несвязанные функциональные и визуальные работы.
- **Каждый PR обновляет строки [REQUIREMENTS](docs/REQUIREMENTS.md)**, которые он затрагивает: статус и доказательство. Требование нельзя молча пропустить, удалить или считать выполненным без доказательства. Отмена или изменение требования — только решением владельца (ADR или дата сообщения), строка переводится в ⛔.

## 5. Документация — дисциплина

- `docs/STATUS.md`, `docs/KNOWN_ISSUES.md`, `docs/TESTING.md` описывают **только текущее** состояние: устаревшее заменять, а не дописывать вниз. STATUS — не длиннее двух страниц.
- Хронология — в `CHANGELOG.md` (одна запись на PR); подробные журналы при необходимости — в `docs/archive/`.
- В конце работы над PR обновить: STATUS, CHANGELOG, KNOWN_ISSUES (убрать исправленное), индекс ADR, при необходимости CURRENT_DECISIONS, ROADMAP, OPEN_QUESTIONS.
- Язык документов, отчётов и коммитов — русский; идентификаторы в коде — английские. Комментарии объясняют «почему».
- В Git — только обезличенные числа и коды ошибок, без скриншотов с именами треков.

## 6. Сборка

`./gradlew :app:assembleDebug testDebugUnitTest lintDebug detekt` — подробности в [docs/TESTING.md](docs/TESTING.md). Новый код не должен добавлять замечаний detekt ([ADR-0076](docs/DECISIONS/ADR-0076-quality-tooling.md)), даже пока detekt не блокирует CI.
